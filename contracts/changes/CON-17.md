# CON-17 The tls_upgrade action in the scenario contract

Contract. Scenario schema `contracts/schemas/scenario.schema.json` and the scenario rules of `tools/contracts/validate.py`. The change takes the finding of ENG-20. The owner approved it.

Version. The scenario contract moves from v0.3 to v0.4. The change adds one action keyword, which a reader can see in the schema, so it takes a minor number, as CON-04 (v0.2) and CON-10 (v0.3) did. Every v0.3 scenario stays valid and keeps its meaning. The module manifest schema (v0.3), the test configuration schema (v0.2), the controller API, and the agent protocol keep their versions. A module that uses `tls_upgrade` needs an engine that compiles it, which `fps-flow` does since ENG-20, so no `engine_api` number moves.

Change. `$defs/action/properties` gains `tls_upgrade`, an object with the required `profile` (a name of a TLS profile of the run, a non empty string) and the optional `role` (`client` or `server`, which defaults to the role of the side) and `server_name` (a non empty string that a client handshake verifies and sends as SNI). `additionalProperties` is false. The action upgrades the transport of the running session to TLS in place, as STARTTLS does, and every later action of the side runs over TLS. `contracts/README.md` gains the row in the action table, and the paragraph on the validator names the new rule.

Semantic rule. `tools/contracts/validate.py` reports an error for a `tls_upgrade` in a flow with `l4: udp`, at any depth of `loop` and `branch`, with the message "tls_upgrade applies only to TCP flows". The tests in `tools/contracts/test_contracts.py` cover a valid scenario, the action inside a loop, a UDP flow (direct and nested), and malformed bodies. The validator does not check that the named profile exists, because the profiles belong to the run and not to the scenario.

Compatibility. The change is additive. The controller embeds a copy of the scenario schema (`controller/internal/registry/schema/scenario.schema.json`), which this change refreshes byte for byte, because `TestEmbeddedScenarioSchemaMatchesContract` compares the two. The controller therefore accepts the keyword. It does no engine work, and the agent builds no TLS profiles yet (AGT-14), so a session of a plan that holds `tls_upgrade` fails with reason `internal` until that package lands.

Outside the catalog paths, for the coordinator. `fps-flow` accepts `tls_upgrade` in a UDP flow today, and the runtime fails such a session at the action. The validator now rejects it earlier. To give both validators the same verdict, `check_action` of `fps-flow` should reject it with a new `LoadError` kind (ENG-20 suggested `TlsUpgradeOnUdp`), and a case in `engine/fps-flow/tests/fixtures/verdicts.yaml` with its fixture would then run in both the Rust test and `test_fixtures.py`. That is an ENG change.
