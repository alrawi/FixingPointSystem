# CON-13 Capture download over the agent connection

Contract. Agent control protocol in `proto/fps/agent/v1/agent.proto`.

Versions. The protocol moves from 0.2.1 to 0.2.2. The header comment of the proto file and the comment in `buf.yaml` name the new version, and `contracts/README.md` lists it. The change adds a command and an RPC, which would normally take a minor number, but it takes a patch number for the reason that CON-11 gave. The controller admits agents by the major and minor part of `Capabilities.engine_api` (`DefaultEngineAPIs` lists `0.1` and `0.2`), and `tools/contracts/check_plans.py` compares major and minor too, so 0.3.0 would make the controller refuse every agent until the controller list changes. The controller gates the new command by the full version: it sends `fetch_capture` only to an agent whose `engine_api` is 0.2.2 or later, as it does for the 0.2.1 settings. The Rust agent reports 0.2.2 because it parses the new messages, and it answers the command with `ERROR_CODE_UNIMPLEMENTED` until AGT-09. The controller must treat that answer as "this agent cannot serve the file" and not as a protocol fault.

Decision. The owner chose to stream the file over the existing mutually authenticated agent connection. The agent dials the controller, so the controller cannot call the agent, and the transfer has to start from the agent. Two shapes were possible.

1. Chunk messages on the `Session` stream. This needs a credit or acknowledgement scheme, because the heartbeat, the command results, and the counter snapshots share the stream, and one slow reader would hold all of them behind the data. Every acknowledgement is one more message on the stream that carries the heartbeat.
2. An upload RPC that the agent opens when the controller asks. The call is a separate HTTP/2 stream on the same connection, so the transport gives it its own flow control window, and a slow controller reader stalls the upload and not the heartbeat.

This change takes the second shape. The controller asks with a command on `Session`, and the file travels on a client streaming call of the same service and the same connection and certificate. The `Session` stream carries two small messages per transfer, `FetchCaptureCommand` and `FetchCaptureResult`, and no data.

Changes.

- `ControllerService` gains `UploadCapture(stream UploadCaptureRequest) returns (UploadCaptureResponse)`.
- `SessionResponse.body` gains `fetch_capture` (9, `FetchCaptureCommand`), and `CommandResult.result` gains `fetch_capture` (9, `FetchCaptureResult`).
- `FetchCaptureCommand` carries the plan id, the capture id, `start_offset`, a controller chosen `transfer_id`, and `max_chunk_bytes`. The capture must be finished, which means that `StopCaptureResult` exists. The agent answers at once with `FetchCaptureResult`, which repeats the `transfer_id` and carries `total_bytes`, the `digest` of `StopCaptureResult`, and the chunk size that the agent will use, and then opens `UploadCapture`. The failures use the existing codes: `NOT_FOUND` for an unknown plan or capture or a file that the retention removed, `FAILED_PRECONDITION` for a capture that has not ended, `INVALID_ARGUMENT` for an offset above the file size or a bad `transfer_id`, `RESOURCE_EXHAUSTED` when the agent already serves a transfer, and `UNIMPLEMENTED`. `ErrorCode` stays as it is.
- `UploadCaptureRequest` is a oneof of `open`, `chunk`, and `end`. `open` carries the `transfer_id`, the `session_token` of the session that carried the command, the capture id, and the start offset. Each `CaptureChunk` carries an `offset` and 1 to 262144 bytes, and the chunks cover the file from `start_offset` to its end in ascending order without gap or overlap. `CaptureEnd` carries `total_bytes` and the `sha256:` digest of the whole file, which equals the digest that `StopCaptureResult` reported.
- `UploadCaptureResponse` carries `received_offset` and `verified`. The controller answers once, after it read `end`.
- Chunk size. No chunk exceeds 262144 bytes (256 KiB), the agent sends at most the smaller of that limit and `max_chunk_bytes`, and gRPC message limits (4 MiB by default) are not reached.
- Flow control. HTTP/2 window updates bound the bytes in flight on the upload stream, so the proto defines no credit message. The agent serves one transfer at a time, and the upload runs in its own task, so heartbeats and results continue on `Session`. A controller that stops reading stalls only the upload, and it ends the call with a status or lets the heartbeat timeout of its own session decide.
- Resume. The controller keeps the bytes that it received, and when the call breaks it sends a new `FetchCaptureCommand` with a new `transfer_id` and `start_offset` equal to the bytes it holds. The file does not change, because a finished capture is immutable, so the digest in `CaptureEnd` covers the whole file and the controller verifies the bytes of all attempts together. `received_offset` of an answer, or the count of bytes the controller read before the break, is the offset to resume at.
- Authorization. The call rides the mutually authenticated connection, so the identity is the certificate, as for `Session`. The `transfer_id` is single use and bound to the agent and the session that received the command, so an upload that names an unknown or used id ends with `NOT_FOUND`, a second concurrent call with one id ends with `ALREADY_EXISTS`, and a transfer ends with `ABORTED` when its session ends. An agent that never gets the upload call within the heartbeat timeout of the command is a failed transfer for the controller.

Compatibility. The change is additive on the wire and in the proto file.

- `buf breaking` with the `FILE` rules reports no finding against `origin/main` at fa2f0bc, which holds 0.2.1, and `buf format` and `buf lint` pass. `buf breaking` does not treat a new RPC as a break, and no existing message, field number, enum value, or RPC changes. Field number 9 was unused in `SessionResponse.body` and in `CommandResult.result`, and the file declares no `reserved` range.
- Wire level: an agent of 0.2.1 or earlier cannot decode the new arm, which arrives as an unknown field with no `body` set, and answers `INVALID_ARGUMENT` at best, so the controller sends `fetch_capture` only to an agent whose `engine_api` is 0.2.2 or later. An old controller never sends the command, and an agent never opens `UploadCapture` without one. A controller of 0.2.1 that receives a call to the new RPC answers `UNIMPLEMENTED`, which the generated `UnimplementedControllerServiceServer` does by default.
- JSON mapping: the canonical plan form has no new fields, and `examples/plans/http_dns_smoke.json` stays valid and canonical.
- Source level: code that implements `ControllerService` by hand must add `UploadCapture`. In this repository these are the two fake controllers in `engine/fps-agent/tests/session.rs` and `run_control.rs`, which return `UNIMPLEMENTED`. The Go `Manager` embeds `UnimplementedControllerServiceServer`, so it keeps compiling once `controller/internal/agents/agentpb` is regenerated. The Rust agent builds its types from the proto file at build time, so its mirrors follow the file, and `tests/contract.rs` checks the numbers and a round trip of every new message. The agent match on `SessionResponse.body` is exhaustive and gains an arm that answers `UNIMPLEMENTED`.
- `tools/contracts/test_plans.py` lists the oneof arms and the methods of the service, so it names the new arm and the new RPC.
- Not specified here: where the controller stores the file and for how long, which CTL-14 decides, and how long the agent keeps a finished capture file, which AGT-09 makes configurable. The commands of `fetch_capture` and `UploadCapture` define the bytes on the wire and nothing about storage.
