# CON-15 Capture and criteria contract gaps

Contract. Controller OpenAPI document `contracts/openapi/fps-api-v1.yaml` and agent control protocol `proto/fps/agent/v1/agent.proto`. The change closes gaps that CTL-14, AGT-07, and AGT-09 found. The owner approved it.

Versions.

- OpenAPI moves from 0.5.0 to 0.6.0. The change adds an operation and optional response fields, which a reader can see in the document, so it takes a minor number, as CON-12 and CON-14 did. Nothing depends on the minor part of the REST version. `api.APIVersion` follows, because `capabilities_test.go` compares it with `info.version`. `openapi/fps-metrics.yaml` stays at 0.3.0.
- The protocol moves from 0.2.2 to 0.2.3. The change adds two fields and no command, so it takes a patch number for the reason that CON-11 and CON-13 gave: the controller admits agents by the major and minor part of `Capabilities.engine_api`, and a 0.3.0 would make it refuse every agent until its list changes. The header comment of the proto file, `buf.yaml`, and `contracts/README.md` name the new version. The Rust agent reports 0.2.3 because `tests/contract.rs` ties `ENGINE_API` to the header comment.

REST changes.

- New operation `stopCapture`, `POST /runs/{id}/captures/{capture_id}:stop`, scope `run`, no request body, answer 200 with the `Capture`. It ends the capture on every agent without downloading it. The state becomes `completed` (or `failed` when no agent delivered an end), and the files are then ready for `downloadCapture`. It is idempotent: a capture that already ended answers with its state. The path follows the `:stop` and `:reserve` style of the document. The CTL-14 finding named this operation or a `ready` state. A new enum value would have been breaking for a client that switches on `state`, so the change keeps the three states and states that `completed` means that the files are ready to download. A download of a running capture still ends it, as CTL-14 does.
- `Capture` gains the optional `files`, an array of the new schema `CaptureFile`, ordered by agent identity. `CaptureFile` has the required `agent` (the agent identity) and the optional `started`, `error` (why the agent did not start), `packets`, `bytes`, `dropped`, and `digest` (`sha256:` and 64 hex digits). The numbers and the digest are known once the agent reported its end. The properties are the ones that the controller already keeps per agent (`captures.AgentFile`), so the download no longer is the only place that names the agents (`X-FPS-Capture-Agents` and `X-FPS-Capture-Missing` stay).
- `startCapture` request. The property `port` stays required, and its description now says what it names. `export_tls_keys` keeps its type and default, and its description says what it does with agent protocol 0.2.3.

Decision on the capture port. The REST contract requires `port` and the agent refused every port (AGT-09 finding), so no capture started through the controller. The change keeps `port` required, for three reasons. AGT-12 makes the agent accept a port and record only sessions whose server port matches, and its end to end script starts the capture through `POST /v1/runs/{id}/captures` with a port, so it needs no contract change. `captures.Service` rejects an empty port, and making it optional would change the controller and would need a rule for "every port" across agents that nobody asked for. Making a required request property optional later is additive, so the decision can be revised without a break. The protocol still lets `StartCaptureCommand.port` be empty, which means every port of the plan, and an agent that implements AGT-12 keeps that meaning.

Protocol changes.

- `StartCaptureCommand` gains `export_tls_keys` (8, `bool`). When true, the agent puts the TLS key log lines of the captured sessions into the file. When false, or when an agent of 0.2.2 or earlier skips the field, the agent decides on its own, as it does today. The controller already accepts the REST field and can now pass it on.
- `Criterion` gains `labels` (4, `map<string, string>`). It mirrors the `where` filter of the test configuration: a series counts when its labels equal every entry. The `side` label (CON-08, values `client` and `server`) is the case that AGT-07 needed. A criterion without a `side` label keeps the client default (the server side in a plan without client workers), so every plan of 0.2.2 means the same.
- Field numbers 8 and 4 were unused and the file declares no `reserved` range.

Compatibility. The change is additive.

- `buf breaking` with the `FILE` rules reports no finding against `main`, because the change adds fields only (checked by CI, because `buf` could not run in the sandbox of this package). The REST change adds an operation, optional response properties, and a schema, and removes or changes nothing. The repository has no automatic OpenAPI breaking check yet (CON-16 plans one), so this was verified by reading the diff.
- Wire level. An agent of 0.2.2 skips `export_tls_keys`. It also skips `labels`, and then it would count every series of the metric and give a different verdict. So the controller must send a criterion with `labels` only to an agent whose `engine_api` is 0.2.3 or later, as it does for the 0.2.1 settings, or evaluate such a criterion itself. The Rust agent of this change reports 0.2.3, parses `labels`, and refuses a plan with a labeled criterion (`InvalidArgument`, "labels are not applied by this agent") until an AGT package applies them, because a silent skip would measure another rule. The canonical JSON form carries the field as `criteria[].labels`; the standalone plan file parser still rejects it (unknown field), which is the safe behaviour.
- REST clients. A client that ignores `files` and never calls `stopCapture` sees no difference.

Examples. `examples/tests/dns_zone.yaml` names the first party scenario `dns/lookup_a` instead of `dns/resolve`, which only the example module `contracts/examples/modules/dns` has, so the test runs against the agent (AGT-07 finding). The example module is unchanged, so no module digest changes. `tools/contracts/validate.py` validates `dns_zone.yaml` against `modules/dns` (the table `FIRST_PARTY_TESTS`) and the other examples against the example modules as before.

Generated code. `sdk/python/fixingpoint/_generated.py` (`stop_capture`, `Capture.files`, `CaptureFile`) and `ui/src/api/schema.d.ts` are regenerated. The Rust types come from the proto file at build time.

Outside the catalog paths.

- Rust mirrors in `engine/fps-agent`: `src/capabilities.rs` (`ENGINE_API` 0.2.3), `src/convert.rs` (the refusal above and the field in the test helper), `tests/contract.rs` (field numbers and round trips of both fields), `tests/detect.rs` (the version).
- Go, for the coordinator. `controller/internal/agents/agentpb` and `controller/internal/api/api.gen.go` are regenerated by the coordinator. After that: `controller/internal/api/unimplemented.go` needs `StopCapture(w, r, _ Id, _ string)` answering 501 (the new `ServerInterface` method), `controller/internal/api/capabilities.go` names 0.6.0, and `controller/internal/wiring/wiring_test.go` lists `stopCapture` in `pendingOps` until the captures package serves it. The two tests that validate `dns_zone.yaml` against the example modules (`wiring/settings_test.go`, `store/locations_test.go`) need the first party `dns/lookup_a`, for example by replacing the scenario name with `dns/resolve` in the loaded text. Serving `stopCapture`, filling `Capture.files` from `captures.AgentFile`, passing `export_tls_keys` and labels in the commands and plans, and gating labels by `engine_api` are CTL work.
