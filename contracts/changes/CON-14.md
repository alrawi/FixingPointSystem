# CON-14 Signature headers and calibration history in the REST contract

Contract. Controller OpenAPI document `contracts/openapi/fps-api-v1.yaml`. The change documents what CTL-28 and CTL-24 already do. The owner approved it.

Versions. OpenAPI moves from 0.4.0 to 0.5.0. The change adds optional request headers, a response, and an optional response field that a reader can see in the document, so it takes a minor number, as CON-07 and CON-12 did. Nothing depends on the minor part of the REST version. `api.APIVersion` follows, because `capabilities_test.go` compares it with `info.version`. `openapi/fps-metrics.yaml` stays at 0.3.0.

Compatibility. Every request and response that was valid stays valid, so the change is additive. A client that sends no signature header and ignores `calibration` sees no difference. A client that already sends the headers keeps working, because the controller has read them since CTL-28. The repository has no automatic OpenAPI breaking check, so this was verified by reading the diff: no path, operation, parameter, required field, enum value, or schema property was removed or changed in type, and the only new request parameters are optional.

- `installModule` (`POST /v1/modules`) gains the optional header parameters `X-Module-Signature-Key-Id` (the key id) and `X-Module-Signature` (the 64 byte Ed25519 signature over the module tree digest, standard base64). A request sends both or neither. The two responses that the controller already answers are now named: 400 when only one header is present, the signature is not base64, or the archive is broken, and 403 when the controller refuses the signature (modified archive, unknown, revoked, or expired key, key id mismatch, truncated signature, or no signature while a trust store is configured and unsigned modules are not allowed) or the token scope is too low. Both use `application/problem+json`.
- `Run` gains the optional `calibration`, an array of at most 256 `CalibrationStep` objects, oldest first. It is absent for a run without a `throughput_bps` objective and while the factor stays at one. The controller keeps the newest 256 steps (`maxCalibrationSteps`).
- `CalibrationStep` has the required properties `time` (date-time), `factor`, `target`, and `sessions_per_second`, and the optional `entries` (array of `CalibrationEntry`) and `multipliers` (object of number by mix entry id, which CTL-12 fills for byte weighted mix control and which is absent otherwise). `CalibrationEntry` has the required `id`, `bytes_per_session`, and `measured`. The numbers use `format: double`, so the generated Go type is `float64` and not `float32`.
- The Go struct `runs.CalibrationStep` has no JSON tags, so the contract names (snake case) are the ones that the REST layer produces. `runs.ToAPI` maps the struct to the generated type, which is the minimum edit that makes the field appear.
- Generated code. `sdk/python/fixingpoint/_generated.py` and `ui/src/api/schema.d.ts` are regenerated (the SDK generator ignores header parameters, so `install_module` is unchanged, and the new `Run.calibration` and its two types appear). `controller/internal/api/api.gen.go` must be regenerated with `go generate ./internal/api`, which the coordinator does on the branch.
- Outside the catalog paths. The header parameters make the generator add `InstallModuleParams` and a third argument to `InstallModule`, so `controller/internal/api/unimplemented.go` and `controller/internal/registry/http.go` take the new argument and still read the headers from the request. `controller/internal/runs/rest.go` maps the calibration steps, `rest_calibration_test.go` checks the JSON names, and `controller/internal/api/capabilities.go` names version 0.5.0.
