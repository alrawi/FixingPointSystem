## Done and verified

Cause (from the code, no capture: netem is unavailable here). In `own_serve` the own acceptor answers the bulk with 8 bytes and then `shutdown()`. `Host` sends the FIN in a segment of its own after the data (`flags::FIN | flags::ACK`, empty payload, host.rs near line 2563), so the acceptor always sends two back-to-back sequence-consuming segments. With 1 percent loss on the link, when the answer is lost and the FIN arrives, the kernel opener has a hole and sends a SACK block; a retransmitted answer that arrives twice gets a duplicate SACK (RFC 2883). The own server sends nothing wrong. Rate is about 1 percent of runs per loss row, which matches a flake. The unconditional `opener.sack_segments == 0` was too strict whenever frames are dropped.

Fix. With `loss` the check becomes `opener.sack_segments <= acceptor.data_segments + 2` (data segments including retransmissions, plus the FIN and one FIN again): every opener ACK with a SACK block answers one acceptor segment that took sequence space. Without loss it stays `== 0`. Test `the_opener_reports_holes_only_for_what_the_acceptor_sent`. `cargo test -p fps-tcp --lib wiretap`, fmt, clippy pass.
