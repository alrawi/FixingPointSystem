## Goal

The interop_kernel row "own client to kernel server, bottleneck with tail drop, loss switches on" fails with "peer process: the peer did not report in time". Show the cause and fix the stall (or, only if the transfer is shown to progress, widen the timeout). The row must pass 50 runs in a loop.

## Done and verified

- Cause: the own client spun in `Host::expire` (reorder timer re-armed for the same reading of the clock), holding the stack lock, so it could not report its 90 s timeout. Read with gdb (thread 2 in `arm_conn` from `on_probe_timer` Reo, now fixed at 873221) and with a trace of the state at the timer. Not a slow transfer.
- Reproduced in the sandbox (`ip` package installed with apt; veth and tbf work, netem does not): 5 hangs in about 80 runs of the row before the fix.
- Fix in `recovery.rs` (`rack_detect`) and `host.rs` (`on_probe_timer`), unit test `a_flight_of_the_delivered_segments_reading_sets_no_reordering_timer` (fails without the fix).
- After the fix: 200 of 200 runs of the row pass; the whole `interop_kernel` binary passes; `cargo test -p fps-tcp-own --lib` 222 passed; clippy and fmt clean; `fps-tcp` bottleneck and lossy tests pass.
