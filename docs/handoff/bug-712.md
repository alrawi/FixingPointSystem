## Done and verified

- Session 52 (client 10.201.0.2:40000, server port 5587) is complete in the capture (handshake, data, FINs) and its keys are embedded. The check found no ClientHello for it, so the keys were not the problem.
- Cause: the check runs tshark with `-d tcp.port==5587,tls`, which decodes the clear text start of a STARTTLS session as TLS. TLS rejects it, and tshark then offers the segment to the dissector of the other port. Wireshark registers TCP port 40000 for SAP NI (`tshark -G decodes`), SAP NI accepts the data, owns the conversation, and the ClientHello stays hidden. Ports are allocated in sequence, so a run fails only when the sampled session lands on 40000 or another registered port, which is why main passed ten times. Rewriting that client port to 40001 or 40100 in the same capture makes all 8 sessions decode.
- Fix: the probe also decodes the client ports of the sampled sessions as TLS, so no other protocol can claim the session.
- Regression test `test_a_client_port_that_wireshark_registers_does_not_hide_the_handshake` moves one fixture session to port 40000. It fails without the fix and passes with it (`python3 -m pytest realism/tests/test_encryption.py`, 36 passed).
- 30 runs of the check on the failing CI capture: 30 of 30 pass (7 of 8 before). Same on the committed fixture.

## Decisions taken in this package

Decode the client ports as TLS rather than switching the STARTTLS port to the smtp dissector, because the labels carry no STARTTLS protocol and a schema change is out of scope. The fix also covers direct TLS on any port.

## Pitfalls

Any tshark check that decodes a port with `-d` can lose a session to a protocol registered on the other port of the pair. `tshark -G decodes | grep '^tcp.port'` lists them.
