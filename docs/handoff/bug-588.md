## Goal

The unit test `worker::tests::an_error_from_a_loop_ends_only_that_worker` of `engine/fps-backend-afxdp` fails intermittently (panic at `worker.rs:310:39`, `reports[0].error` is `None`). Find the real cause, fix the worker code if its behavior is wrong, and make the test deterministic without a sleep as synchronization.

## Done and verified

1. Cause: `run` checked `stop` before the first turn (`while !stop.load(..)`). `Workers::stop` can set the flag before a worker thread is first scheduled, and then that loop took no turn and ended with no error. This is a defect of the worker code and not only of the test, because a queue that is broken from the start would be reported as cleanly stopped. Which worker ran at all depended on thread scheduling.
   Before the fix the test failed 69 of 2000 runs (the test binary run in a shell loop). After the fix it failed 0 of 2000, 0 of 2000 pinned with `taskset -c 0`, and 0 of 1000 (both modes) with four busy loops on the 2 CPU sandbox.
   Fix: `run` takes at least one turn before it honors `stop`.
   New test `a_loop_takes_one_turn_even_when_the_stop_came_first` calls `run` with the stop flag already set and has no threads, so it is deterministic. It fails on the old code on every run.
   `spinning_workers_stop_promptly_and_count_idle_turns` lost its 20 ms sleep, which was a sleep as synchronization (it relied on the thread running before the stop). The guaranteed first turn now makes `idle_turns > 0` certain. It also failed on the old code when the thread started late.
   Scan of the other worker tests: `one_worker_per_queue_serves_its_own_queue` synchronizes on a round trip, `a_worker_pins_to_a_cpu_or_reports_why_not` returns before the loop, and `dropping_workers_stops_them` asserts nothing about turns. None has the race.

## Decisions taken in this package

A worker takes one turn before it honors stop. The cost is at most one turn of latency on stop, and a queue error cannot hide behind an early stop.

## Pitfalls

A shell loop of the test binary (`for i in $(seq 2000); do BIN TEST --exact -q; done`) shows the race at about 3.5 percent without load. `taskset -c 0` hid it, so use both modes.
