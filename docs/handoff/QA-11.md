## Decisions taken in this package

- What the logs of the original run say (job logs are readable with `gh api repos/$FPS_REPO/actions/jobs/ID/logs`, only the artifacts are blocked). Attempt 1 of run 43158088031 is the only real parser failure: its mix job failed with `Mix parser errors | 10 findings from tshark, zeek`. Attempts 2 and 3 are the same finding again for another reason: the mix job of attempt 2 passed with 0 findings (client run `run_fff8389d...`), and the report job of attempts 2 and 3 downloaded the `gate2-mix` artifact of attempt 1 (artifact id 13917600329, client run `run_a48cc9ec...`), because attempt 2 uploaded a second artifact with the same name and the download took the first. Attempt 3 reused the mix job of attempt 2. Attempt 4 ran every job again and passed. So there are two causes: a flaky capture with 10 parser findings, and a report job that reads a stale artifact after a partial rerun.
- Cause of the findings. Run 43233842055 of this branch (commit 934c974), attempt 3, failed its mix job with 31 tshark findings and none from Zeek, and the new log lines named them: 1 `pcp` malformed packet in an `http2` session (TCP 198.18.0.22:44322 -> 198.19.0.4:8082) and 30 `manolito` malformed packets in an `aux` UDP stream of 200 packets (198.18.0.57:41170 -> 198.19.0.7:23394, the RTP media of a call). `tshark -G decodes` (4.2.2, the version of CI) binds TCP 44322 to `pmproxy` and UDP 41170 to `manolito`, and both are the client ports of the sessions. The kernel picks the client port at random, so tshark decodes the payload with a dissector that does not fit and reports malformed packets. No fault of the agent, the modules, or the controller. The same applies to the 10 findings of the original run (artifacts unreadable, so not proven) and explains why the finding comes and goes by chance: 922 TCP and UDP ports are bound, 39 of them at 32768 or above.
- The rule is the port collision rule, documented in `tests/gates/gate2/README.md`: a tshark finding does not count when the client port of its session is bound to a dissector for the transport and the server port is not bound to the same dissector. It holds only with a complete `mix/parser-findings.json`, never for Zeek, and the log and report still print each collision. I did not narrow the port range of the namespace instead (`net.ipv4.ip_local_port_range` via `mix.sh`), because that changes the traffic and raises the reuse of 5-tuples (QA-09), and no run could show that it holds.
- The stale artifact is fixed in `.github/workflows/qa-gate2.yml`, which is outside this package's paths, so the pull request does not change it. The coordinator applies `overwrite: true` to every `actions/upload-artifact@v4` step of `modules`, `mix`, `image` (see the Shared page notes of the log entry).
- The findings go in the report (`Parser findings` sections), in `mix_findings.py` lines on stderr, and in `mix/parser-findings.json`. The report section covers the module stage as well.

## Pitfalls

- The sandbox blocks the blob host, so run artifacts cannot be downloaded, but `gh api repos/$FPS_REPO/actions/jobs/ID/logs` returns the job log. Job ids of earlier attempts come from `.../actions/runs/ID/attempts/N/jobs`.
- A re-run that runs only failed jobs reuses the logs of the successful jobs of the earlier attempt, so two job ids can show one log.
- The `qa-gate2` concurrency group (`qa-gate2-${{ github.ref }}`) cancels a running run on each push, so read the previous run before pushing again.
- The sandbox worktree guard refuses heredocs and `cd` in one command; write files with the editor tools.
