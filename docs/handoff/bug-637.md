## Goal

An agent whose certificate the controller refuses ends on its own within the redial limit, in every run. The cause is in `engine/fps-agent`, not in the test.

## Done and verified

1. Reproduced: 6 failures in 2500 runs of `a_certificate_that_the_controller_refuses_is_a_permanent_failure` (0.24%), 1 in 1000 in an earlier loop. A failing run is a hang: the test times out at `WAIT`.
2. Cause: the agent is a real bug, not a test race. In a hung run, debug prints showed the session stuck in `Register` (`s1 registering`, no `lost`), and `ss -tanp` showed no established connection on either side, only the two listeners. The connection is gone, yet the `Register` call never completes with an error. `session()` bounded only the dial (`CONNECT_TIMEOUT`); `Register` and the opening of the session stream had no timeout, and a call that never ends is not a session that ends, so `RedialPolicy` (and the redial limit) never ran.
3. Fix: `Register` and the session stream open run under `CALL_TIMEOUT` (5 s). A timeout is the new transient `Lost::Unanswered`, so the policy bounds the wait, and the next dial sees the close (the existing close-after-handshake confirmation) and ends permanently.
4. After the fix, 3000 of 3000 passes under CPU load (two busy loops on 2 CPUs). `cargo test -p fps-agent` passes, `cargo clippy -p fps-agent --all-targets` is clean.

## Decisions taken in this package

`CALL_TIMEOUT` equals `CONNECT_TIMEOUT` (5 s), above the 3 s redial limit of the test, so a hung first dial adds up to 5 s and the test still ends well inside `WAIT` (20 s). `WAIT` is unchanged.

Why the call hangs instead of failing (tonic channel buffer after a connection that closed during the h2 setup) was not traced further; the timeout bounds it either way.

## Pitfalls

The test binary is cheap (about 30 ms), so a loop of a few thousand runs finds the hang. Loop the single test with `--exact`.
