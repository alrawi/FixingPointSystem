# Modules

This page describes the protocol modules under `modules/`, which the MOD workstream owns. A module ships a manifest, scenarios, an optional native crate, fixtures, and tests, with the layout that the Modules section of [Coding Standards](Coding-Standards.md#modules) defines and the four proofs that [Testing](Testing.md#testing-a-new-module) requires.

## How a module plugs in

A module joins the build without any shared file edit. The workspace glob `modules/*/native` in the root `Cargo.toml` picks up its native crate, the rust job of `ci.yml` runs its Rust tests through `cargo test --workspace`, and a file `mk/mod-<name>.mk` adds its lint, test, and end to end targets. Decision D10 lets a first party module implement its template functions in Rust. The crate implements the `TemplateFn` trait of `fps-flow`, and the manifest lists the same functions under `functions`, as contract v0.2 requires. A catalog test in the module compares the two lists, so the manifest stays the single catalog that the validator and the controller read.

## The http1 module

MOD-01 added the `http1` module. Its two functions render complete HTTP/1.0 and HTTP/1.1 messages with a length delimited body or, in HTTP/1.1, a chunked body. They check every text argument before they write a byte, so a header value with a line break fails the session with `extension_invalid_argument` instead of producing a broken frame. The module README lists the parameters, their defaults, and the header order.

The six scenarios cover a single fetch, keepalive browsing with a chunked page and several embedded objects, length delimited and chunked uploads, and HTTP/1.0 with and without keepalive. A receiving side finds a header block with the pattern `\r\n\r\n`, reads a length delimited body with `expect bytes`, and reads a chunked body with the pattern `0\r\n\r\n`. The chunk pattern is safe because `fill()` never produces a carriage return.

We test the module at four levels.

1. `make lint-mod-http1` validates the manifest and every scenario with `tools/contracts/validate.py`.
2. The scenario tests run both sides of every scenario over the in memory duplex and parse both directions with the framing rules of RFC 9112.
3. The transcript test compares the bytes of every scenario at seed 42 with golden files under `modules/http1/tests/testdata/`.
4. `fixtures/capture.sh` records 200 sessions in the QA-01 harness over the kernel TCP backend, 120 in the clear and 80 over TLS, and the realism runner scores the capture. nDPI 4.2.0 classifies every plain session as HTTP and every TLS session as TLS, and tshark reports no parser errors.

The example `fixture_peer` drives the interpreter over kernel sockets without the agent. Both sides walk the scenarios in manifest order and run the sessions one after another, so the n-th accepted connection belongs to the n-th client session and both sides draw from the same session generators. The workflow `mod-http1` scores the committed fixture and records and scores a fresh capture as root on every change. The client peer assigns every session its own source port (MOD-21), because a source port that the kernel picked twice for the same destination merged two sessions into one 5-tuple and made the parser error check fail on some fresh captures, and `capture.sh` checks that the capture holds as many sessions as the peers ran.

### HTTPS scenarios

MOD-04 added four scenarios that run the http1 exchanges over TLS. `https_fetch` (Chrome 136, TLS 1.3, port 8443) and `https_fetch_tls12` (Safari 18.5, TLS 1.2, port 8445) repeat `single_fetch`, and `https_keepalive_browse` (Firefox 139, TLS 1.3, port 8444) and `https_keepalive_browse_tls12` (Edge 134, TLS 1.2, port 8446) repeat `keepalive_browse`, each with the `User-Agent` of its browser. Each side upgrades its connection with `tls_upgrade` as the first action after `connect` or `accept`. The client names a browser profile of the [TLS module](Transport.md#browser-profiles-and-ja4) and the SNI `www.example.test`, and the server names `server-tls13` or `server-tls12`, which accept one version each. The browsers offer `h2` and `http/1.1`, the servers select `http/1.1`, and the certificate comes from the run authority of the TLS module. Each scenario has its own port, so a capture tells the profiles apart by `server_port`.

**Why `tls_upgrade` and not the `transport` keyword.** Since CON-18 the flow keyword `transport: {module: tls, profile: ...}` is sugar for a leading `tls_upgrade` on both sides with one profile name, but these scenarios use different client and server profiles, so they keep explicit `tls_upgrade` actions. Before CON-18 `Scenario::load` rejected the keyword, so no engine runs it. The action `tls_upgrade` of ENG-20 is the way that runs, and the agent will serve it once AGT-14 builds the TLS profiles. Until then the scenarios run in the module harness. `tests/common/tls.rs` holds the profile registry, which the scenario tests and the `fixture_peer` share. It follows `fps_runtime::TlsProfiles`, but it builds a fresh connector for every client session. A connector that stays across sessions resumes TLS 1.3 sessions, and the resumed ClientHello adds `pre_shared_key`, which changes the JA4. A connector without a resumption store leaves out `session_ticket`, which changes it too. The first handshake of a connector is the only one with the JA4 that the profile documents.

**Tests.** `tests/https.rs` checks the negotiated version, ALPN, and SNI on both sides, that the wire starts with a ClientHello and carries no HTTP, that a TLS 1.2 server shows its certificate and a TLS 1.3 server hides it, that the key log names the ClientHello random of the wire and holds the secrets of its version, and that the JA4 of the ClientHello (computed by `realism/ja4.py`) equals the `expected_ja4` of the profile. The golden transcripts of the https scenarios hold the plaintext above the TLS layer, because the handshake bytes depend on random keys.

**Fixture.** The peers share a run authority across processes: the server writes its certificate to a file and the client trusts only that. The client writes the secrets of every handshake to a key log, and `capture.sh` injects the log into the capture with `editcap --inject-secrets`, so the capture carries its keys as a decryption secrets block and every reader decrypts it without a sidecar. The labels file `expected.yaml` gives the four ports a `tls_profile` each and the `expected_ja4` of the profile. The realism runner scores the capture as follows.

| Check | Result on the committed capture |
|---|---|
| Conformance (nDPI 4.2.0, payload only) | 120 of 120 plain sessions are HTTP, 80 of 80 TLS sessions are TLS |
| Parser errors (tshark 4.2.2) | 0 |
| Encryption (RLM-04) | 80 of 80 decrypt, and 80 of 80 ClientHellos have the JA4 of their profile |

**What nDPI sees inside TLS.** Nothing. nDPI classifies the https sessions as `TLS`, and it has no decrypted view, so the acceptance item "nDPI classifies at least 99% of decrypted fixture sessions as HTTP over TLS" cannot be read from the capture. `python3 -m realism decrypted` measures it instead, with the labels `realism/examples/decrypted/http1.labels.yaml` (MOD-22 moved the module from its own `decrypted_check.py` to this shared command of RLM-12). It decrypts the capture with tshark and the embedded keys, writes the plaintext of every TLS session as plain TCP sessions with the same addresses and ports, and scores that view with the realism runner and nDPI. The result is 80 of 80 sessions (ratio 1.0, threshold 0.99), and tshark reports no parser error on the view (the command does not count requests and responses, which the earlier script counted as 200 each). The test `tests/fixture.rs` runs the command on the committed capture, and it exits with 1 when a session does not decrypt or the ratio is below the threshold, which a capture without keys shows (0 of 80). The measurement has one limit: nDPI sees a synthetic view that we built from tshark's output, with fresh TCP framing, and not a capture of real plaintext traffic. It therefore proves that the decrypted bytes are HTTP that nDPI recognizes, and it says nothing about how nDPI treats the TLS record layer.

**Gaps.** The agent builds no TLS profiles yet (AGT-14), so a plan with these scenarios fails every session with `internal` until it does. The agent must register the profile names of the scenarios, the four browser profiles and `server-tls13` and `server-tls12`, and it must build a connector per session, or the JA4 of every session after the first no longer matches. Chrome, Edge, and Safari share one `expected_ja4`, so a JA4 check cannot tell their sessions apart, see the Transport page. The `server_name` of `tls_upgrade` is a literal, so changing the `host` variable of a scenario without changing the SNI breaks the certificate check.

## The content module

MOD-03 added the `content` module under [`modules/content`](https://github.com/alrawi/FixingPointSystem/tree/main/modules/content). It generates message bodies for the protocol modules that follow, such as `smtp`, `imap`, `pop3`, and `ftp`, and for the bodies of `http1`. Its native crate `fps-module-content` implements five template functions. `content.html` renders a page from head, navigation, and section templates, and `content.json` renders a paged API response with a growing `data` array. `content.text` renders prose in English, German, French, Spanish, Italian, Russian, or Chinese, and `content.email` renders a plain text body with a greeting, a reference line, and a signature. `content.binary` renders a PNG, GIF, JPEG, PDF, ZIP, or GZIP file, or raw bytes, with correct lengths, offsets, and checksums and without a compression library.

Every function takes a `size` in bytes and a `seed`. The output reaches the size and ends at most about 1 KiB above it, because a generator finishes the element that it writes. A seed of zero or more fixes the bytes. The default seed of -1 draws from the session generator, so a replay with the same run seed and session id reproduces the bytes, and every session still gets other content.

Every generator is synthetic. The crate builds its output from word lists and sentence grammars that we wrote for it, bundles no third party text, reads no file, and opens no connection. Names come from invented syllables, and addresses and links lie under the reserved `.test` domain. The module README carries the provenance note, and the manifest states `source: synthetic`.

The acceptance of MOD-03 is a duplicate payload ratio of at most 1% across 10,000 generated bodies. The test generates 10,000 bodies for each generator type, with the seed unset, with the seeds 0 to 9999, and at 512 bytes, and it fails when more than 1% repeat an earlier body. A generator type is `html`, `json`, `text` and `email` in each language, and `binary` of each kind. `make lint-mod-content test-mod-content` runs the checks. The module has no scenarios and no fixture capture, so the realism job does not score it.

## Known gaps

We record three gaps that later packages close.

1. `validate.py --modules modules/http1` treats every subdirectory of the module as a module and fails, so `lint-mod-http1` validates through a parent directory that links to the module.
2. The root `.gitignore` ignores `*.pcapng` outside `contracts/examples`, so module fixtures need `git add -f` until the ignore list allows `modules/*/fixtures/*.pcapng`.
3. The fixture comes from `fixture_peer` and not from the agent, because the agent does not run plans yet. Gate 1 records its capture through the agent.

## The dns module

MOD-02 added the `dns` module under [`modules/dns`](https://github.com/alrawi/FixingPointSystem/tree/main/modules/dns). Its native crate `fps-module-dns` holds an RFC 1035 codec with name compression, a parser for zone files in master file format, and four template functions. `dns.query` renders a query with a transaction id from the session generator, `dns.response` answers it from the zone or from one given address, `dns.answer_ip` returns the first address of an answer for a `set` action, and `dns.tcp_length` reads the two byte length prefix of a TCP message. The catalog extends the contract example by appending optional parameters and the function `tcp_length`, so every example call keeps its meaning. The module README lists every parameter and the answer rules.

The server answers as an authoritative server of the zone that the setting `zone_file` names, and of `zones/example.test.zone` without it. The shipped zone holds A, AAAA, CNAME, MX, TXT, NS, and SOA records with names under `.test` and addresses in the documentation ranges. It follows CNAME chains, answers a missing name with NXDOMAIN and the SOA record, and adds glue addresses to MX answers. A UDP answer longer than 512 bytes keeps only the question and sets TC, and the scenario `tcp_fallback` then repeats the question over TCP, where each side reads the length prefix with `expect bytes: 2` and the message with `expect bytes` of the bound length.

The seven scenarios are `lookup_a`, `lookup_aaaa`, `lookup_cname`, `lookup_mx`, `lookup_txt`, `nxdomain`, and `tcp_fallback`. We test the module at the same four levels as http1. The parser also survives 20,000 random inputs without a panic. The transcript files carry the flow id in their names, as in `tcp_fallback.udp.seed42.c2s.bin`, and a UDP transcript prefixes each datagram with its length so the file keeps the boundaries.

`fixtures/capture.sh` records 160 sessions in the QA-01 harness, 140 over UDP and 20 over TCP. TCP flows run over the kernel TCP backend, and UDP flows run over Tokio UDP sockets inside `fixture_peer` until the kernel UDP backend of TRN-02 merges. nDPI 4.2.0 classifies 160 of 160 sessions as DNS, and tshark 4.2.2 reports no parser errors. The workflow `mod-dns` scores the committed fixture and records and scores a fresh capture as root on every change.

MOD-19 added the setting `zone_file` under decision D12 item 22. A test configuration sets `modules.dns.settings.zone_file`, the manifest describes it with a settings schema, and `Dns::from_settings` loads the zone and rejects an unknown key, a file that cannot be read, a malformed zone with the file and line, and a zone without an SOA record. The loader accepts the subset of RFC 1035 master file syntax that the module README lists. `capture.sh` hands the setting to both `fixture_peer` processes, so the fixture capture comes from a configured zone, and the transcript tests show that the shipped zone given by setting renders the same bytes as the default.

The dns module adds two gaps to the list above. The setting does not reach an agent through the controller yet, because `fps.agent.v1.ModuleRef` has no field for module settings, so only the module level tests and the fixture peer apply it. Queries carry no EDNS OPT record, so the server applies the 512 byte limit of RFC 1035 to every UDP answer.

## The smtp module

MOD-07 added the `smtp` module under [`modules/smtp`](https://github.com/alrawi/FixingPointSystem/tree/main/modules/smtp). Its native crate `fps-module-smtp` implements ten template functions. `smtp.ehlo_reply` renders the multi line 250 reply with `PIPELINING`, `SIZE`, `AUTH`, and the other extensions, and `smtp.credential`, `smtp.address`, `smtp.recipients`, and `smtp.rcpt_to` generate synthetic user names, passwords with the prefix `Tst-`, and addresses under `.test`. `smtp.auth_plain` and `smtp.base64` build the tokens of `AUTH PLAIN` and `AUTH LOGIN`. `smtp.message` renders an RFC 5322 message with a `text/plain` part and an optional base64 attachment, `smtp.data` renders it as the payload of DATA with dot stuffing and the end line, and `smtp.repeat_line` repeats a reply line for a pipelined batch. The functions check every text argument before they write, so a line break in a header value fails the session with `extension_invalid_argument`.

The scenarios take the message body and the attachment from the content module through nested calls, as in `smtp.message(..., body=vars.text, attachment=content.binary(kind='pdf', size=rand_int(vars.attachment_min, vars.attachment_max)))`. The manifest lists the content module under `requires`, so the validator accepts the calls, and the sizes of the attachments vary from session to session. A server finds the end of a message with the pattern `\r\n.\r\n`, and a client reads the multi line EHLO reply up to the pattern `\r\n250 `. The text part of most messages holds a dot line and a line that starts with two dots, so every run exercises dot stuffing. The server cannot branch on what it reads, so it accepts every credential.

The six scenarios cover relay on port 25 (`relay`, `relay_pipelined` with RFC 2920 pipelining in both directions, and `text_only`) and submission on port 587 (`submission_plain` with an initial response, `submission_login` with the 334 challenges, and `submission_batch` with one authentication and several pipelined messages). We test the module at the same four levels as http1, and the scenario tests parse both directions with a model of RFC 5321 and decode the attachments. A fifth proof checks the capture with Zeek. `fixtures/zeek_check.py` fails unless `smtp.log` has a row for every message, `files.log` has every attachment with all of its bytes, and `weird.log` has no `smtp` entry. The `realism` workflow runs it through `capture.sh` on a fresh capture, and the `mod-smtp` workflow runs it on the committed one.

The module has no STARTTLS scenario. A flow binds its transport once, at `connect` or `accept`, and the TLS module wraps a whole session, so no action can upgrade a running flow after `220 Ready to start TLS`. The submission scenarios run in the clear on port 587. A STARTTLS scenario needs an engine action that hands the stream of a running flow to a transport module, with each side choosing its TLS role.

The smtp module adds three gaps to the list above. The server accepts every credential. The committed capture comes from a loopback recording and not from the namespace harness, until `capture.sh` runs there. The agent registers the native functions of `http1` and `dns` only, so `smtp` and `content` calls fail in a plan until the agent maps them.

MOD-20 added the scenario `starttls_submission` to the smtp module, and `ehlo_reply` gained the parameter `starttls`. The client reads the `STARTTLS` offer, sends `STARTTLS`, reads the `220` reply, and both sides run `tls_upgrade` (the client with `firefox-139`, the server with `server-tls13`). Inside TLS the client sends `EHLO` again, authenticates with `AUTH PLAIN`, and sends a message with a PDF attachment. The fixture runs this scenario on port 5587, so the labels can tell it from the plain submission sessions on 587. The fixture is recorded with the exported keys (`editcap --inject-secrets`), and the encryption check of the realism runner decrypts all 8 sessions and matches the JA4 of every ClientHello. nDPI 4.2.0 labels these sessions `SMTP`. Zeek cannot decrypt, so `python3 -m realism decrypted` has tshark decrypt the capture and build a decrypted view of plain sessions, which nDPI scores as `SMTP` and whose Zeek parser errors it scores, and `capture.sh` has Zeek read the kept view with the checks of `zeek_check.py` when Zeek is installed. The Zeek part is proven by the CI run only, because the sandbox that wrote it has no Zeek.

## The imap module

MOD-08 added the `imap` module under [`modules/imap`](https://github.com/alrawi/FixingPointSystem/tree/main/modules/imap). Its native crate `fps-module-imap` implements fourteen template functions. A flow has neither counters nor a way to branch on what it reads, so the functions do both jobs. `imap.next` counts the client tags up from `A001` and the message numbers of a loop, and `imap.tagged(last, ...)` reads the tag out of the command line that the server just consumed, so every tagged response carries the tag of its command. `imap.fetch(last, message)` parses the `FETCH` command, renders the data items in the order that the client asked for them, and writes each body item as a literal `BODY[] {n}` followed by exactly `n` bytes of a MIME message from the content module. `imap.select_data`, `imap.search_reply`, `imap.store_reply`, and `imap.expunge_reply` render the untagged responses of the other commands, and `imap.search_hit` lets the client read a message number out of a `SEARCH` response and fetch that message.

The client sends literals as well. `imap.literal_marker` writes `{n}`, and the server reads the command line from `last`, saves it with `set`, takes the size with `imap.literal_size`, answers with a `+` continuation request, and reads exactly that many bytes with `expect bytes`. The scenarios `login_append` (the password and an `APPEND` message are literals) and `idle_push` (`+ idling`, a pushed `EXISTS`, and `DONE`) use continuation requests. The saved command line also lets the server complete `IDLE` after the `DONE` line and an `APPEND` after its literal.

The five scenarios are `mailbox_sync` (a message list and the header fields of every message), `fetch_messages` (whole messages with PDF, JPEG, or ZIP attachments from a read-only `EXAMINE`), `search_store` (`SEARCH`, `FETCH`, `STORE`, `EXPUNGE`, and `CLOSE`), `login_append`, and `idle_push`. The scenario tests parse both directions with a model of RFC 3501 and check the tag sequence, the continuation requests, the literal sizes, the `SELECT` data, and the decoded attachments. The transcript test compares seed 42 with golden files.

Two things that we learned about nDPI 4.2 shape the module. The IMAP dissector decides within the first eight payload packets and needs a `LOGIN` that names a user, so every scenario logs in at once with `LOGIN` and a quoted or literal password, and a port of the dissector to Python classifies all 40 sessions of the committed capture as IMAP at their fifth payload packet. The dissector also sets IMAPS for any flow that carries an `AUTHENTICATE` command, so a scenario with `AUTHENTICATE PLAIN` would count as a miss, and the module ships none. The function `imap.auth_plain` stays for a later scenario.

MOD-20 added the scenario `starttls_mailbox`. The greeting and the first `CAPABILITY` list `STARTTLS` and `LOGINDISABLED`, the client sends `STARTTLS`, and both sides run `tls_upgrade` (the client with `safari-18.5`, the server with `server-tls12`, so the session runs on TLS 1.2). Inside TLS the client asks for `CAPABILITY` again, which lists `AUTH=PLAIN`, logs in, selects `INBOX`, downloads two messages, and logs out. The fixture runs it on port 1143 with embedded keys, and the realism runner decrypts all 8 sessions and matches the JA4. nDPI 4.2.0 labels these sessions `IMAPS`, unlike the smtp sessions, and the labels accept exactly that. The decrypted view that `python3 -m realism decrypted` builds is classified as `IMAP`, and Zeek reads it for parser errors, because Zeek ships no IMAP analyzer. Both mail modules share two gaps. The browser profiles offer the ALPN ids `h2` and `http/1.1`, which a mail client does not send, and the server profiles select none, so the agent needs a mail client and a mail server profile without ALPN.

The module has no log check like `zeek_check.py` of the smtp module, because we could not confirm that the Zeek release of the realism job logs IMAP messages. The realism job requires that Zeek parses the capture without a parser error, and `tshark` dissects all 720 IMAP packets of the committed capture and the attached messages without a warning. The committed capture comes from a loopback recording and not from the namespace harness, as with the smtp module, and the agent does not dispatch `imap` calls until the registry of AGT-13 exists.

## The pop3 module

MOD-09 added the `pop3` module under [`modules/pop3`](https://github.com/alrawi/FixingPointSystem/tree/main/modules/pop3). Its native crate `fps-module-pop3` implements thirteen template functions for plain POP3 on port 110. `pop3.banner` draws the timestamp banner `<pid.clock@host>` of the greeting, and `pop3.apop_digest(greeting, secret)` lets the client read that banner out of the greeting line in `last` and compute the MD5 digest of banner and secret, as RFC 1939 section 7 specifies, with a small MD5 in the crate and a synthetic secret. The server side answers each command with one function that reads the command line from `last`. `pop3.stat_reply`, `pop3.list_reply`, and `pop3.uidl_reply` derive sizes and Dovecot style unique identifiers from one mailbox number, so `STAT` and `LIST` agree. `pop3.retr_reply` and `pop3.top_reply` write the status line, the message from the content module with every line break as CRLF and a second dot before every line that starts with a dot, and the closing dot line. The client reads a single line answer up to `\r\n` and a multi line answer up to `\r\n.\r\n`, which stuffed content never contains.

The six scenarios are `retrieve_all` (`CAPA`, `USER` and `PASS`, `STAT`, `LIST`, `UIDL`, and `RETR` of messages with PDF, JPEG, or ZIP attachments), `apop_login` (`APOP` with the banner digest, accepted, then the same listing commands and one `RETR`), `apop_fallback` (`APOP` rejected with `-ERR [AUTH]`, then `USER` and `PASS`, as fetchmail does), `top_preview` (`TOP n lines` for several messages, then `RETR`), `fetch_delete` (`RETR` and `DELE` for each message, then `RSET`), and `poll_new_mail` (`STAT` and `UIDL` only, the short session of a polling client). The text part of the messages in `retrieve_all` and `fetch_delete` has a line with a single dot and a line that starts with two dots, so dot stuffing is on the wire in the capture. The scenario tests parse both directions with a model of RFC 1939 and check the announced `RETR` sizes against the unstuffed messages, the number of lines that `TOP` returns, and the command sequence of each scenario. The transcript test compares seed 42 with golden files.

The nDPI 4.2 dissector of POP3 shapes the module. It counts `+OK` and `-ERR` packets and a short list of commands (`AUTH`, `APOP`, `USER`, `PASS`, `CAPA`, `LIST`, `STAT`, `UIDL`, `RETR`, `DELE`, and `STLS`), and it gives up on a packet that is neither at the twelfth payload packet or later, so `QUIT`, `TOP`, and `RSET` count as noise. It detects POP3 when the sum of `+OK` packets and distinct commands reaches 3 and either a `PASS` has named a password or more than three `+OK` packets have passed. The second condition never holds, because the counter is a bit field of two bits (`mail_pop_stage:2`) and wraps after 3. nDPI 4.2 therefore identifies a POP3 session only after a `PASS` command. A session that logs in with `APOP` alone stays unknown, and `ndpiReader` guessed the 8 `apop_login` sessions of our first capture by port only, which the realism runner counts as a miss. A scenario with `USER` and `PASS` is detected at the `PASS` packet, the fourth payload packet. The module keeps `apop_login` for the exchange that RFC 1939 describes, and its `capture.sh` leaves the scenario out of the fixture with `--skip apop_login`. `apop_fallback` is the APOP scenario that the fixture records, and nDPI identifies it at packet 6. `ndpiReader` 4.2.0 classifies all 40 sessions of the committed capture as POP3 with the confidence `DPI`. The module has no STLS scenario for the reason that the smtp module gives, and ENG-20 adds the engine action that a scenario needs.

The module has no Zeek log check, for the reason that the imap module gives. `tshark` dissects all 744 POP3 packets of the committed capture without a malformed packet or a warning. The committed capture comes from a loopback recording and not from the namespace harness, as with the smtp and imap modules, and the agent does not dispatch `pop3` calls until the registry of AGT-13 exists.
## The ftp module

MOD-10 added the `ftp` module under [`modules/ftp`](https://github.com/alrawi/FixingPointSystem/tree/main/modules/ftp). Its native crate `fps-module-ftp` implements eleven template functions. The control channel scenarios log in with synthetic credentials and send `SYST`, `FEAT`, `PWD`, `CWD`, `TYPE`, `SIZE`, `ALLO`, `PASV`, `EPSV`, `LIST`, `RETR`, `STOR`, and `QUIT` with the replies of vsftpd 3.0, including the multi line `FEAT` reply. Every `LIST`, `RETR`, and `STOR` moves its bytes over a passive mode data connection that a spawned flow opens, so the module is the first to use the `spawn` action of [Scenario instances](Engine.md#scenario-instances). The files come from `content.binary`, and the listings come from `ftp.listing`.

The data connection takes its port from the control connection. The server draws a port, binds it to the variable `data_port` with `set`, spawns the data flow so that the listener exists, and announces the port with `ftp.pasv_reply` or `ftp.epsv_reply`. The client reads the reply into `last`, binds `ftp.pasv_port(last)` or `ftp.epsv_port(last)` to its own `data_port`, sends the transfer command, and spawns the same flow, which dials `{{ vars.data_port }}` because a spawned side reads every `set` of its parent. The k-th spawn of the client meets the k-th spawn of the server, so `batch_download` runs one data flow per file.

The scenario language has no action that waits for a spawned flow and no read until close, so the sizes travel as they do in the protocol. `SIZE` and `213` tell the client the length of a download, `ALLO` tells the server the length of an upload, and a listing has the number of lines that the variable `list_entries` gives. Because `content.binary` writes at least the size that it is asked for, the server measures a file with `ftp.length(content.binary(..., seed=vars.file_seed))` and sends the same file in the data flow, which a fixed seed makes possible. The server waits 10 to 40 ms before it sends `226`, because the control flow cannot see when the data flow ends.

The five scenarios are `list_pasv`, `retr_epsv` (a PDF over EPSV), `stor_pasv` (a ZIP file), `mixed_session` (a listing, a download, and an upload on one control connection, which makes one control and three data connections), and `batch_download` (the variable `files` downloads). The scenario tests run every scenario as a scenario instance over an in memory network and check one control connection and exactly one data connection per transfer, to the announced port, with the right bytes. The transcript test records the control connection and every data connection with seed 42. The module has no active mode (`PORT` needs the client address, which a scenario cannot read) and no `AUTH TLS` scenario.

The acceptance of MOD-10 is one control and one data connection per transfer. The session structure check of the realism runner (RLM-08) covers the count and the ordering but not the announced data port, the FIN of both sides, or active mode, and the committed capture mixes five scenarios on one client, so `fixtures/structure_check.py` stays. It reads the capture with the CAP-01 extractor `python3 -m capture sessions --payloads` and counts them. It matches each data connection to its control connection by address and time, compares the data port with the number in the 227 or 229 reply, and fails on a refused, repeated, orphaned, or reset connection. The committed capture of 8 sessions per scenario holds 40 control and 80 data connections, and the check passes. The first loopback recording had one refused data connection per transfer, because the client dialed before the server side of the spawned flow had bound the port, so the server now spawns before it announces the port, and the check caught the refusals. nDPI labels only the control connections, because a passive data connection carries a file without a protocol of its own. The check `zeek_check.py` requires a `PASV` or `EPSV` row in `ftp.log` and an `FTP_DATA` file in `files.log` for every transfer, the data ports of those files to equal the announced ports, and a `RETR` or `STOR` row for every file transfer, and Zeek 9.0.1 of the CI job passes it. The agent dispatches only `http1` and `dns` today, so a plan with an ftp scenario needs the dispatch of AGT-13 for `ftp` and `content`.

## The http2 module

MOD-05 added the native crate of the `http2` module under [`modules/http2/native`](https://github.com/alrawi/FixingPointSystem/tree/main/modules/http2/native). `fps-module-http2` implements twenty template functions for RFC 9113 frames and RFC 7541 header compression, and MOD-06 added the manifest, four scenarios, and a fixture that call them. The encoders write the connection preface (`http2.preface`), `SETTINGS` and its acknowledgment, `HEADERS` with `CONTINUATION` frames, `DATA` with padding and `END_STREAM`, `WINDOW_UPDATE`, `PING` and its acknowledgment, `GOAWAY`, and `RST_STREAM`, and `http2.frame` writes any frame from its fields. A list of headers is text with one `name: value` per line, and a header that starts with a colon is a pseudo header.

The module is the first with state. A connection has one HPACK encoder and one decoder, and the dynamic table of each lives in the module value, which the agent clones for every session and every side of a flow. `http2.headers` writes through the encoder, and a server reads with `http2.headers_decode`, so a second request on a connection can use the table entries that the first one added. The encoder makes a choice for every field and the module documents each one. An exact match of name and value is an indexed field. A field whose name is `authorization`, `proxy-authorization`, `cookie`, or `set-cookie` is a literal that is never indexed, and the argument `index` set to `all` lifts that rule for a scenario that wants those fields in the table. `index` set to `off` writes literals without indexing, and a field larger than the table gets the same treatment. Every other field is a literal with incremental indexing, and the name comes from the static table first and from the dynamic table second. `huffman` takes `auto` (code a string only when that makes it strictly shorter), `always`, or `never`, and the argument `table_size` makes the encoder open its next block with a dynamic table size update. A `SETTINGS` frame that sets `header_table_size` also sets the size that the decoder of the same module value accepts.

A flow cannot parse a frame with a variable, because `set` renders to text and corrupts binary data, so a flow reads frames the way the engine allows. It reads the 9 octets of the header with `expect: {bytes: 9}`, takes `http2.frame_length(last)`, `http2.frame_stream(last)`, and `http2.frame_field(last, 'flags')` into variables, which are decimal numbers, and reads the payload with `expect: {bytes: "{{ vars.length }}"}`. The payload stays in `last`, and `http2.headers_decode(last, flags=vars.flags, type=vars.type)` decodes it, collects fragments of `CONTINUATION` frames until `END_HEADERS`, and renders `name: value` lines that `http2.header_value` searches. `http2.data_payload`, `http2.settings_value`, `http2.data_frames`, and `http2.headers_frames` complete the readers. The last two count the frames that a body or a header block takes, so a loop can read them. The scenario `tests/data/h2c_flow.yaml` is a test scenario for the idiom, and the flow test runs both of its sides through the interpreter.

The crate has four proofs. The Appendix C.2 to C.6 vectors of RFC 7541 decode to the listed headers and encode to the listed octets, with one exception that the test documents. C.6 with `huffman` set to `auto` ties on the length of `307`, which the RFC codes, so the test compares a round trip and checks the exact octets with `always`. The `h2` crate 0.4, which Cargo.lock already holds through the HTTP stack of the engine, serves as a dev dependency. An `h2` server accepts the frames of this crate, with a dynamic table, `CONTINUATION`, padding, a priority, and split `DATA`, and this crate parses and decodes what an `h2` client writes. The fuzz tests use a seeded loop on stable Rust, because cargo-fuzz needs nightly. `fuzz_short` runs 300 rounds with every `cargo test`, and `fuzz_60s` runs for 60 seconds under `cargo test -p fps-module-http2 --release --test fuzz -- --ignored fuzz_60s`. A round feeds random and mutated octets to the decoders, checks that the encoder and decoder agree on every block, and calls every function with random arguments. 461350 rounds ran without a panic.

MOD-06 added four scenarios, [`h2c_browse`](https://github.com/alrawi/FixingPointSystem/blob/main/modules/http2/scenarios/h2c_browse.yaml) and `h2c_upload` with prior knowledge on ports 8082 and 8081, and `https_browse` and `https_upload` over TLS 1.3 with ALPN `h2` on ports 8443 and 8444, with the profiles `chrome-136` and `firefox-139` on the client side and `server-tls13-h2` on the server side. They show six concurrent streams with interleaved DATA frames, browser shaped SETTINGS with `SETTINGS_ENABLE_PUSH` 0, WINDOW_UPDATE flow control, PING, and a graceful two step GOAWAY. The server waits for the connection preface, because nDPI reads the client as the first sender. The fixture scores clean in tshark (no parser errors, and 180 requests with 180 responses inside the 40 TLS sessions). nDPI 4.2.0 has no HTTP/2 protocol and reports the cleartext sessions as Unknown, so the HTTP/2 measurement needs a newer `ndpiReader`, which `realism/ci/build-ndpi.sh` builds from the nDPI release 4.14 (cleartext 40 of 40 HTTP2, decrypted TLS view 40 of 40 HTTP2 in the CI run), and the realism runner reads its `|` separated flow file directly since RLM-12. The module [README](https://github.com/alrawi/FixingPointSystem/blob/main/modules/http2/README.md) has the numbers.

The agent does not dispatch `http2` calls yet. The module is stateful, so `engine/fps-agent/src/modules.rs` needs a registration with the `Http2` value, which the agent clones per session and side, and not the `stateless!` form that the other modules use.

## The smb2 module

MOD-12 added the native crate of the `smb2` module under [`modules/smb2/native`](https://github.com/alrawi/FixingPointSystem/tree/main/modules/smb2/native). `fps-module-smb2` implements thirty seven template functions for the messages of MS-SMB2 that a file transfer needs, and MOD-13 added the manifest, the three scenarios, and the fixture that call them.

Ten request encoders write NEGOTIATE, SESSION_SETUP, TREE_CONNECT, CREATE, READ, WRITE, CLOSE, QUERY_DIRECTORY, TREE_DISCONNECT, and LOGOFF, and eleven response encoders write the answers to them and the error response. Every function writes one complete message behind the 4 octet transport header of direct TCP, so a `send` action puts it on port 445 as it is. The offsets inside the bodies follow the layouts of MS-SMB2, a negotiate that offers 3.1.1 carries the preauthentication and encryption contexts, and a READ or WRITE charges one credit for every 64 KiB. The module has no state. The ids that tie messages together are arguments, which the flow takes from the responses that assign them.

The NTLM functions write a synthetic exchange. `smb2.ntlm_negotiate`, `smb2.ntlm_challenge`, and `smb2.ntlm_authenticate` write the three NTLMSSP messages of MS-NLMP inside the SPNEGO tokens of RFC 4178, `smb2.spnego_accept` writes the final token, and `smb2.ntlm_session_key` derives the session key that both sides share from the authenticate message and the password. The NTLMv2 response is computed in full from the user and the password, and the test checks the NT hash, the NTOWFv2 key, the proof, and the session base key against the vectors of MS-NLMP section 4.2. The exchange sends no message integrity code and no key exchange, so the exported session key is the session base key. `smb2.sign` signs a message with HMAC-SHA256 under that key, which is the signature of SMB 2.0.2 and 2.1. SMB 3.x signing and encryption are not part of the module.

A flow reads a message the way it reads an HTTP/2 frame. It reads the 4 octet transport header with `expect: {bytes: 4}`, takes `smb2.message_length(last)`, and reads the message with a second `expect`. After that `smb2.header_field(last, 'session_id')`, `smb2.body_field(last, 'file_id')`, and their relatives give text that a `set` action binds, and `smb2.security_blob(last)` and `smb2.data(last)` give octets for a nested call. A `set` action keeps text, so a token that must stay intact travels as `smb2.hex(...)` and comes back with `smb2.unhex(vars.name)`. A flow has no arithmetic and no loop counter, so `smb2.add(vars.mid)` numbers the messages of a loop and `smb2.chunks(total, size)` counts the requests that move a file. Session ids use 64 bits, and a template integer is signed, so a session id travels as the two's complement integer. The scenario `tests/data/smb2_flow.yaml` is a test scenario for these idioms, and the flow test runs both of its sides through the interpreter.

The crate has five proofs. First, tshark 4.2.2 parses every message of four complete sessions (SMB 2.0.2, 2.1, 3.0.2, and 3.1.1) with no malformed packet and no warning or error of its expert system, and the test checks the commands, statuses, paths, NTLM fields, dialects, and sizes that tshark decodes. The sessions are written as TCP segments of 1400 octets, so tshark reassembles reads of up to 200000 octets. The test skips itself without tshark, unless `FPS_REQUIRE_CAPTURE_TOOLS` is `1`. Second, golden files under `native/tests/testdata/` hold the bytes of two sessions. Third, the readers return what the writers set, and every prefix of every message gives an error and never a panic. Fourth, the catalog test compares the rendered catalog with the engine manifest loader, and with `modules/smb2/manifest.yaml` as soon as the file exists. Fifth, the fuzz tests use a seeded loop on stable Rust. `fuzz_short` runs with every `cargo test`, and `fuzz_60s` runs for 60 seconds under `cargo test -p fps-module-smb2 --release --test fuzz -- --ignored fuzz_60s`.

The three scenarios are `browse`, `download`, and `upload`. Each starts with NEGOTIATE, the two SESSION_SETUP requests of a synthetic NTLMv2 authentication, and TREE_CONNECT, and ends with TREE_DISCONNECT and LOGOFF. `browse` lists the root directory and one subdirectory with QUERY_DIRECTORY until the server answers STATUS_NO_MORE_FILES, `download` reads a file of `file_size` octets in READ requests of `read_size` octets, and `upload` creates a file and writes `upload_size` octets in WRITE requests of `write_size` octets. A flow has no arithmetic, so the length of the last read or write is a variable of its own, `tail_size` or `upload_tail`, which must equal the size modulo the request size, or the request size when it divides the size. The [module README](https://github.com/alrawi/FixingPointSystem/blob/main/modules/smb2/README.md) gives the rule and the variables.

The fixture `smb2.pcapng` holds six sessions of each scenario, 18 in all, which `fixtures/capture.sh` records in the QA-01 harness with a source port of its own per session (MOD-21). nDPI 4.2.0 classifies 18 of 18 as `NetBIOS.SMBv23`, so `expected.yaml` accepts `SMBv23` and `SMB`, and tshark 4.2.2 reports no parser error. The 4 octet header of direct TCP, which starts every message, is also the NetBIOS session header of a session message, and nDPI needs nothing else. It classifies SMB only on port 445: the same scenarios on port 4450 are `Unknown`. The `realism` workflow records a fresh capture with nDPI 4.14.0, tshark 4.2.2, and Zeek 9.0.1, and its first run gave 18 of 18 sessions as `NetBIOS.SMBv23` and no parser error from tshark or Zeek.

The agent does not dispatch `smb2` calls yet. The module has no state, so the `stateless!` form of `engine/fps-agent/src/modules.rs` fits, as the log entry of MOD-12 describes.

## The ntp module

MOD-16 added the `ntp` module under [`modules/ntp`](https://github.com/alrawi/FixingPointSystem/tree/main/modules/ntp). Its native crate `fps-module-ntp` implements an RFC 5905 packet codec and three template functions. `ntp.query` renders a client request (mode 3) or the packet of a symmetric active peer (mode 1), `ntp.reply` answers it in mode 4 or mode 2, optionally as a Kiss o' Death packet, and `ntp.field` reads one header field into a variable for a `set` action. The functions are a unit value, because an NTP exchange needs no state, so the agent registers the module with one `stateless!` line.

The functions never read a clock. A scenario passes `now('epoch_ms')`, the built in function that ENG-25 added, as the `now_ms` argument, so the engine clock decides every timestamp, and a test that pins the clock gets equal bytes. The golden transcripts pin the client clock at 2026-11-10T12:00:00Z and the server clock 23 ms later, and the files record that instant in the test that writes them. The engine clock ticks in milliseconds, so the functions draw the position inside the millisecond from the session generator, and a timestamp can lie up to a millisecond after the frame that carries it. A server keeps its precision, root error, and clock update phase from reply to reply, because they follow from its reference identifier, and its reference timestamp moves forward once every 64 seconds for stratum 1 and once every 1024 seconds for a secondary server.

The five scenarios are `sntp_query` (poll exponent 0), `iburst` (four requests 2 seconds apart), `poll_cycle` (exponents 6, 6, and 7 with pauses of 64 and 128 seconds), `kod_rate` (a `RATE` Kiss o' Death reply, a back off, and a normal exchange), and `symmetric_peer` (modes 1 and 2). The pauses are the parameters `burst_gap_ms`, `poll_interval_ms`, and `poll_interval_long_ms`, because a delay takes a template but the language has no arithmetic.

nDPI 4.2.0 classifies NTP only when one side of the flow uses port 123. A capture of the same scenarios on port 5123 gave `Unknown` for every flow. The fixture therefore uses port 123, which works because the server has its own namespace in the QA-01 harness and `capture.sh` runs as root, and the in memory tests bind no port at all. `fixtures/capture.sh` records 30 sessions, 6 per scenario, with 1 second and 2 second poll pauses in place of 64 and 128 seconds so that a run takes about a minute, and `fixture_peer` gives each client session its own source port (MOD-21). nDPI labels 30 of 30 sessions `NTP`, and tshark 4.2.2 reports no parser error and no malformed packet.

The ntp module adds three gaps to the list above. The capture shows the poll exponents and the burst of a real client but not the 64 and 128 second spacing of its polls. The module sends no broadcast, control, or private mode packets, no extension fields, and no authentication. The agent dispatches only the modules of its registry, so a plan with an ntp scenario needs the registry line `stateless!(fps_module_ntp, Ntp),` and the dependency `fps-module-ntp` in `engine/fps-agent/Cargo.toml`.
## The mqtt module
MOD-18 added the `mqtt` module under [`modules/mqtt`](https://github.com/alrawi/FixingPointSystem/tree/main/modules/mqtt). Its native crate `fps-module-mqtt` implements twenty three template functions for MQTT 3.1.1 and MQTT 5.0: the encoders for `CONNECT`, `CONNACK`, `PUBLISH` and the answers of the QoS 1 and QoS 2 flows, `SUBSCRIBE`, `SUBACK`, `UNSUBSCRIBE`, `UNSUBACK`, `PINGREQ`, `PINGRESP`, and `DISCONNECT`, the variable byte integer, and a packet reader. No MQTT library fits, because the interpreter needs a writer and a reader that handle one packet at a time, so the crate writes both.
A packet has a variable length, so a flow reads it with one `expect` of one byte, six `expect` actions of `mqtt.feed(last)` bytes, and `mqtt.recv(kind)`. `feed` returns the size of the next read, which is one byte while the Remaining Length continues and the whole body after it, and a read of size 0 is a no-op. `recv` checks the packet against the standard and the kind that the flow expects, and `mqtt.field(name)` reads its fields as text. The module is stateful, because the version, the packet identifiers, and the reader belong to one session side.
The acceptance asks for realistic keep alive timing. `mqtt.pace` schedules each ping against an absolute due time, as `sip_rtp.pace` does for RTP, so a late wake shortens the next sleep and the pings keep their interval. The capture holds pings exactly 2 seconds apart, and a paused time test runs 200 pings at 30 seconds. The five scenarios are `publish_qos0`, `publish_qos1`, `publish_qos2`, `subscribe`, and `keepalive`, and `version` 4 or 5 selects the protocol version.
The fixture `mqtt.pcapng` holds 40 sessions with 40 different 5-tuples, which `fixtures/capture.sh` records in the QA-01 harness with a source port of its own per session. nDPI 4.2.0 classifies 40 of 40 as `MQTT`, tshark 4.2.2 reports no parser error, and the packets of both versions dissect. The `realism` workflow measures with nDPI 4.14, which the sandbox could not run. The agent does not dispatch `mqtt` calls yet, and the log entry of MOD-18 gives the registry line.

## Joining the realism job

RLM-03 added the workflow `realism`, which records a fresh capture of every native module that a change touches and scores it with nDPI, tshark, and Zeek, as [Realism](Realism.md) describes. A new module joins the job when it ships `native/Cargo.toml`, `fixtures/capture.sh`, and `fixtures/expected.yaml`, and its capture script takes the same arguments as the scripts of `http1` and `dns`. The module needs no edit to the workflow, because `python3 -m realism modules` finds it.
