## [2026-11-10] ingest | ENG-26 Datagram flows in instances and shared data ports

The instance runner of `fps-runtime` now opens UDP flows, and two concurrent instances that draw the same data port both succeed. The runtime tests run `call_pcmu` of the sip_rtp module, a SIP dialog with a spawned RTP flow, through a client runtime and a server runtime over loopback: four calls in one second, eight succeeded sessions on each side, 20 RTP packets of 172 bytes each way per call in the capture, and one 5-tuple per flow. A second test makes six calls draw the same RTP port, and all of them succeed.

The datagram opener follows `fixture_peer`. The client dials every flow with `Connector::connect_datagram`, which binds a socket of its own with a source port from the configured range. A server worker whose entry flow is UDP binds UDP sockets and starts one instance for the first datagram of each peer. Every other server flow waits on the port that its program renders, which is bound when the flow starts and released when the last session of the port ends. All sessions of a port share one socket, and a task per port sorts the datagrams by their source address, because several instances of a worker run at once and a socket that each session reads for itself would let them steal each other's datagrams.

The data port fix keeps the listener and does not change the draws. The draw is `rand_int`, a core function of `fps-flow`, and the client renders the same value from its own generator, so the runtime cannot move a port on one side without breaking the other. Every port is now served by one listener or socket for as long as any instance waits on it, and each incoming session goes to the waiter that expects the host it came from. An instance expects the host of its entry session, because all its flows dial from one source address. The new test with eight `mixed_session` instances on one data port failed in two of three runs on the code before this package (27 or 28 of 32 sessions) and passed in five of five runs after it.

The limit of the match is a shared source host. Two concurrent instances whose clients dial from the same host cannot be told apart by the runtime, and the older waiter takes the first session. A client pool with more hosts than concurrent sessions avoids it, and that is what the default selector gives. A datagram from a peer whose session already ended opens a new session, as in the kernel backend, so a late datagram of a finished call starts an instance on a UDP entry port that fails and ends.
