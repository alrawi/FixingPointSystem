## [2026-11-09] ingest | TRN-05 TLS client fingerprint profiles

We added four browser like client profiles to `fps-module-tls`, `chrome-136`, `edge-134`, `firefox-139`, and `safari-18.5`, in `modules/tls/native/src/browser.rs`. Each carries the `ClientProfile`, the `expected_ja4` that this implementation produces, the `browser_ja4` of the real browser, its sources, and a list of gaps. `ClientProfile` gained `sig_schemes`, which orders the `signature_algorithms` extension. The CI test `modules/tls/tests/ja4.rs` runs a real handshake per profile, computes the JA4 of the recorded ClientHello with `realism/ja4.py`, and asserts it equals `expected_ja4`. A second test reads the fingerprint from tshark 4.2 and asserts the same. Finding: rustls with the ring provider cannot reproduce a browser ClientHello. It offers 10 suites against 15 to 20, sends 11 extensions against 16 or 17, and cannot send SCT, application_settings, record_size_limit, delegated credentials, renegotiation_info, ECH GREASE (ring has no HPKE), or certificate compression (no decompressor). No profile matches its browser's JA4, and Chrome, Edge, and Safari end up with one fingerprint, `t13d1011h2_61a7ad8aa9b6_6d021c4c45cd`, while Firefox has `t13d1011h2_61a7ad8aa9b6_f674693fb0dc`. We described the gaps in [Transport](Transport.md#browser-profiles-and-ja4). The evidence is `docs/handoff/TRN-05.md` and the tests above.

### Shared page notes

- [Testing](Testing.md) and the `mod-tls` workflow: `.github/workflows/mod-tls.yml` runs only `cargo test -p fps-module-tls --test capture`, so the tshark half of the JA4 test does not run there. Add this step after the capture step: `- name: Check the JA4 of the browser profiles with tshark` with `env: FPS_REQUIRE_CAPTURE_TOOLS: "1"` and `run: cargo test -p fps-module-tls --test ja4 -- --nocapture`. The workflow's `paths` already include `modules/tls/**`, and python3 is on the runner. The Python half runs without it in the `rust` job of `ci.yml`, which runs `cargo test --workspace`.
- [Realism](Realism.md#encryption-check): a labels file takes the `ja4` of a profile from `expected_ja4` in `browser::BROWSER_PROFILES`, for example `tls.profiles.chrome-136.ja4: t13d1011h2_61a7ad8aa9b6_6d021c4c45cd`. The list form also accepts `browser_ja4`, but traffic from these profiles never carries it.
- [Implementation Plan](Implementation-Plan.md): a browser accurate fingerprint needs a TLS stack with free control of the suite list and the extensions, for example BoringSSL, whose license needs a review against GPL-3.0, or a patched rustls with a ClientHello hook. This needs an owner decision, and no work package covers it.
