## [2026-11-09] ingest | RLM-04 TLS decryption and JA4 checks

We added the `encryption` check to the realism report. A labels file with a `tls` section names the client profiles and the JA4 fingerprint of each, and a session rule with `tls_profile` ties sessions to a profile. The check samples up to `tls.sample` of those sessions, runs tshark once with the keys that a pcapng capture embeds and with an optional `--keylog` file, and counts a session as decrypted when tshark reads the Finished message of both sides. It computes JA4 for each sampled ClientHello with `realism/ja4.py`, which follows the FoxIO specification and reproduces its worked example `t13d1516h2_8daaf6152771_e5627efa2ab1`, and it compares the result with the profile and with the `tls.handshake.ja4` field of tshark 4.2. A mismatch fails the check and names the parts of the fingerprint that differ. The report format moved to 0.4.0. The evidence is `docs/handoff/RLM-04.md` and the tests `realism/tests/test_ja4.py` and `realism/tests/test_encryption.py`, which build TLS 1.2 and 1.3 captures from real handshakes and run the installed tshark for a matching and a mismatched profile, with embedded and sidecar keys. We described the check in [Realism](Realism.md#encryption-check).

### Shared page notes

- [Implementation Plan](Implementation-Plan.md): the realism report seam is at format 0.4.0 and has the `encryption` entry.
- [Testing](Testing.md): `test-rlm` now also runs `realism/tests/test_encryption.py`, which needs `tshark` and `openssl` and skips without them. The `rlm` workflow already installs tshark through `realism/ci/install-tools.sh`, and its runner has openssl, so the tests run there and in the `realism` workflow without a workflow change.
- [Transport](Transport.md) and TRN-05: a browser profile needs a documented JA4, because the labels file takes the expected value from the profile. The `ClientProfile` of TRN-04 has no JA4 field, so TRN-05 or the controller must supply the string per profile. TRN-05 acceptance reads "RLM-04 reports the expected JA4 value for every profile", which this check satisfies once a labels file lists the profiles.
- Metric catalog: the check leaves `metrics` empty. `realism.decrypted_ratio` and `realism.ja4_match_ratio`, both gauges with the label `application`, would let the controller read the check, as issue #89 proposes for parser errors.
