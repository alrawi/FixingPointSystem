## [2026-11-09] ingest | ENG-17 load WebAssembly extensions into sessions

`fps-runtime` now loads module extensions into sessions. `ExtensionSet` compiles each `extension.wasm` once, through `fps-wasm`, and checks its catalog against the manifest. `FlowRef::extensions` shares the set across every worker, and a session that calls a module of the set instantiates its own `WasmSession` at the first call. A per session `SessionHost` serves the `random-*` calls from `extension_rng`, which derives from the run seed, the module name, the session id, and the side through `session_rng`, so a replay reproduces the draws and the stream is separate from the template stream. A looping extension stops at its fuel limit and fails only its own session with `extension_error`, while other sessions on the same worker thread and the same compiled component succeed. A flow without an extension set takes no wrapper. `FailureKind::reason` needed no change, because ENG-15 already returns `extension_error` for every `TemplateError::Function`, which is how a `WasmFailure` reaches the renderer. We added the section [WebAssembly extensions in sessions](Engine.md#webassembly-extensions-in-sessions) to the Engine page. The evidence is `docs/handoff/ENG-17.md`.

## Shared page notes

- [Engine](Engine.md), crate table. The `fps-wasm` row now points at the new section, and the `fps-runtime` row can name `ExtensionSet` next to `RateControl`.
- Follow up for AGT-01 (`engine/fps-agent/`). The agent plan loader (`modules.rs`) does not read `extension.wasm` yet. For each plan module it should call `ExtensionSet::load_module_dir(&manifest, &dir, Limits::default())`, which returns `Ok(false)` for a module without an extension, and set `FlowRef::extensions` on every flow of the plan. The agent shares one `Arc<ExtensionSet>`. The extension digest is already part of the tree digest of the module.
- Follow up for `fps-flow`. `Manifest` does not read `extension.hooks`, so the runtime cannot skip `on-close` for a module that does not list it. The schema field exists in `contracts/schemas/module-manifest.schema.json`.
- Follow up for `fps-interp`. The interpreter has no seam for transport writes, timers, or received bytes, so the runtime calls `render` and `on-close` only. `send` and `set-timer` return `not-allowed`, `on-data` and `on-timer` are never called, and `on-open` runs at the first template call and not after `connect` or `accept`. A package that adds a per session extension hook to the interpreter closes this gap.
- Contract note for `contracts/extension/README.md`, repeated from ENG-11. It says one instance serves every session of a worker, while the engine instantiates once per session from one compiled component.
- The UDP path of `fps-agent` runs its own session loop and does not use `FlowRef::extensions`. UDP flows with extensions need the same wrapper, built with `ExtensionSet::session_functions` and a `SessionKey`.
- `Cargo.lock` gained one entry set: `fps-runtime` now depends on `fps-wasm`, `rand`, `tracing`, `wat`, `wit-component`, and `wit-parser`, all already in the lock file.
- The test component of `fps-wasm` refuses session id 13 in `on-open`. The runtime test uses client worker ids 20 and 21 so that no local session id 13 of worker 0 occurs, which is a property of the fixture and not of the runtime.
