## [2026-11-06] ingest | MOD-03 content generators

The new module `content` ships five native template functions: `content.html`, `content.json`, `content.text`, `content.email`, and `content.binary`. Each takes a `size` in bytes and a `seed`. A seed of zero or more fixes the bytes, and the default of -1 draws from the session generator, so a replay reproduces the bytes. Every generator is synthetic: it builds its output from word lists and sentence grammars that the crate holds, reads no file, opens no connection, and uses names from invented syllables and addresses under the reserved `.test` domain. The module README carries the provenance note. Text and email bodies come in English, German, French, Spanish, Italian, Russian, and Chinese. The binary kinds are PNG, GIF, JPEG, PDF, ZIP, GZIP, and raw bytes, with correct lengths, offsets, and checksums and without a compression library. The JPEG kind has the marker structure of a JFIF file but no image scan.

The generator tests measure the duplicate payload ratio over 10,000 bodies per generator type, with the seed unset, with the seeds 0 to 9999, and at 512 bytes, and require at most 1%. Further tests check determinism, the size bounds, and the framing of every format. We described the result in [Modules](../Modules.md#the-content-module).

### Shared page notes

- [Modules](../Modules.md): the table of existing modules has no row for `dns`. MOD-03 added its own row and the section "The content module", and left the dns row to the coordinator.
- Workflows: the module needs no workflow like `mod-dns.yml`, because it has no fixture capture and speaks no protocol. The Rust tests run in the rust job of `ci.yml` through `cargo test --workspace`, and `lint-mod-content` validates the manifest. If the coordinator wants a path filtered job anyway, it would run `make lint-mod-content test-mod-content` on changes under `modules/content/**` and `mk/mod-content.mk`. The tests take about 45 seconds in a debug build, because they generate 10,000 bodies for 25 generator types three times, so `cargo test --release -p fps-module-content` takes about 8 seconds.
- Realism: `python3 -m realism modules` finds modules by `native/Cargo.toml`, `fixtures/capture.sh`, and `fixtures/expected.yaml`. The content module has no capture script, so we expect the job to skip it. We could not run the job locally.
- Contracts: a module calls these functions by listing `{ module: content, version: ">=0.1" }` under `requires` in its manifest, as the scenario contract's function rule allows, and then writing `content.html(size=8192)`. The functions return bytes, so a `set` action can also bind the result. The dependent packages, the smtp, imap, pop3, and ftp modules, should do the same. We did not test a scenario of another module that calls `content`, because none exists yet.
- The root `Cargo.lock` gained the entry of the new crate `fps-module-content`, whose dependencies the workspace already uses.
