## [2026-11-10] ingest | UI-06 Agents and ports view

The web UI has an agents view at `/agents`. It lists every agent with its state, backend, cores, version, address, and labels, offers Reserve on an `online` agent and Release on a `reserved` one, and shows the ports of every agent (name, driver, speed) in a second table. It uses only `listAgents`, `reserveAgent`, and `releaseAgent` of REST OpenAPI 0.8.0, so `ui/src/api/schema.d.ts` did not change and `npm run check:api` passes. A failed action shows the `detail` of the problem in an alert, and a 409 or 404 re-reads the list so the view shows the state that the controller holds. The mock server now keeps agent states and implements both operations as `controller/internal/agents/rest.go` does (reserve answers 409 for an offline or busy agent and is idempotent, release always succeeds, 404 for an unknown id), exposes the live agents to tests, and `mock/agents.test.ts` validates the answers against the OpenAPI document with Ajv. `ui/src/pages/Agents.test.tsx` has component tests with literal values and axe scans, among them reservation conflicts for an agent that went offline or started a run after the list loaded. The section Agents and ports of [Web UI](Web-UI.md) has the details.

### Shared page notes

- [Web UI](Web-UI.md): it is the component page of this package and already holds the new section.
- The OpenAPI contract: it names no status code for a refused reserve and does not say who holds a reservation. The controller answers 409 for an offline or busy agent, and the view works with any problem. A later contract revision could name 409 for `reserveAgent` and add a `reserved_by` field to `Agent`, so the view can say who holds an agent (the controller keeps the holder internally). Reserving an already reserved agent succeeds, so the view cannot show a conflict between two users today.
