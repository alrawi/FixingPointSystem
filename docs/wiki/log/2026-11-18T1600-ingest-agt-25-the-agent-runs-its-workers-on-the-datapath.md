## [2026-11-18] ingest | AGT-25 the agent runs its workers on the datapath

AGT-25 runs the TCP and UDP workers of a forced AF_XDP run on the datapath of TRN-27 through the `Transport` of ENG-31, and removes the `Unimplemented` that AGT-24 left in `Prepared::start_on`. It edits only `engine/fps-agent/`, its handoff, this entry, and `Agent.md`. It changes no other crate and no workflow.

- `fps_agent::transport::DatapathTransport` (new) implements `fps_runtime::transport::Transport` over `Datapath::connector` (`connect`, `connect_udp`) and `Datapath::listen` and `listen_udp`. The datapath serves a port once for all server hosts, and the agent starts one server worker per plan worker and mix entry on the same port, so the transport listens once for each port and routes each accepted session to the `listen` call whose addresses hold `session.local_addr()`. A session for a host that no call holds, or whose queue is full (1024), is reset (TCP) or dropped (UDP). Two calls for one host of one port fail with `AddrInUse`.
- The transport owns a Tokio runtime on a thread of its own (the hub), because `Datapath::listen` spawns its accept tasks on the runtime of its caller and a worker runtime ends with its worker. The hub keeps one datapath listener for each port for the whole run: a port that a worker asked for by number stays open until the run ends, so the data ports of the instances (which bind when a waiter comes and release when the last one leaves) bind again at once, and a connection that arrives while nobody listens is reset by the hub. Nothing is left to the kernel. A listen on port 0 takes a port of the transport's choice (32768 to 60767) that closes with its call, so a long run with media ports does not collect listeners.
- `Prepared::start_on` sets the transport on every TCP and UDP worker of an AF_XDP run. `Active` owns the started backend and `Active::finish` stops it after the workers ended, so `Finished::lanes` and `RunSummary::lanes` carry the report of each lane, and the standalone mode logs `fps-agent: datapath lane N tcp frames .. udp datagrams sent .. delivered .. accepted ..`. A start that fails stops the backend before it returns.
- The UDP workers of `src/udp.rs` open their sessions through the transport when their `WorkerConfig::transport` is set (a client `connect_datagram`, a server `listen_datagram` for each address of its host range) and keep their kernel sockets and kernel listeners otherwise, so the kernel path is unchanged. The source host and the server host of a UDP connect without host come from the pools as before (`udp::source_addr`, the server pool slice of the worker).
- The `os_profile` of the client pool and of the server pool become `OwnConfig::client_os_profile` and `server_os_profile` through `OsProfile::builtin` (TRN-28), one profile for each side. An empty name leaves the side without a profile, and an unknown name is a plan error at `prepare` (`check_af_xdp`), before a queue binds.
- `assemble` no longer refuses a plan with a UDP flow on AF_XDP. IPv6 and DHCP are still refused with the package that adds them.
- `backend::start_on_queues` starts the same datapath on queues that the caller opened (`start_af_xdp` and it share `launch`), so the wiring is tested on in memory links without root. `AfXdpBackend` holds the datapath in an `Arc` and has `transport()`.

Evidence. `tests/afxdp_veth.rs` is the acceptance test. The helper keeps both mix entries of the example plan on two plan workers (a client slice and a server host each, so two server workers listen on 8080 and two on 53), gives the pools the profiles `windows11` and `linux6`, and runs the standalone `run` for 3 seconds on the veth pair. Sandbox run (root, kernel 6.18, debug build, 4 s): 87 client and 87 server sessions attempted, succeeded, none failed (http1 63, dns 24), verdict pass, and the lane report shows 1900 TCP frames and 48 UDP datagrams sent, 48 delivered, 24 accepted through the AF_XDP queues. The test asserts the counts of both modules on both sides and the lane counters. New tests without root: `tests/datapath_transport.rs` (8 tests on the datapath over `frame_pair`: routing by `local_addr` for TCP and UDP, one listener for two workers, a host listened on twice, the port that stays open, port 0, the reset of a session for an unheld host, shutdown), `tests/datapath_run.rs` (3 tests: the example plan through the agent over in memory links with every session passing and the lane counters checked, an unknown profile refused at `prepare`, `Active::abort` closing the transport), 5 unit tests in `src/transport.rs` for the routing without a datapath, and 3 in `src/backend.rs` (the profile of each side, the unknown profile, `start_on_queues`). `cargo clippy -p fps-agent --all-targets -- -D warnings` is clean.

Findings:

- A connection that the hub resets can fail the `connect` of the client with `ConnectionReset` or its first read, depending on which frame the client stack handles first. Both are failed sessions with a reset reason, as on the kernel when a listener closes right after `accept`.
- `OwnStats::sockets_open` is not zero when a run ends (48 in the in memory test), most likely because sockets in TIME_WAIT stay in the table of the stack, so a test cannot use it to check that every session closed.
- The agent still starts one lane (queue 0 of each port), and the plan has no field for the queue count of a port. With several lanes a client host and its server host must sit in one lane (`Connector` answers `UnknownDestination` otherwise), and the host ranges of the plan workers do not follow lanes, so the package that adds lanes has to check that.
- A UDP listen on port 0 and the data ports of a scenario instance over the datapath (the `sip_rtp` call scenarios) are covered by the transport tests only. No plan runs them on AF_XDP yet. The coordinator may want a realism or smoke run of `sip_rtp` on the datapath before TRN-31.
