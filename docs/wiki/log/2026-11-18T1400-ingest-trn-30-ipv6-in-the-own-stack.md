## [2026-11-18] ingest | TRN-30 IPv6 in the own stack

TRN-30 makes the own TCP stack (`engine/fps-tcp-own`), the user space UDP layer (`engine/fps-udp-own`), and the datapath (`engine/fps-datapath`) speak IPv6 next to IPv4. The splitter of the datapath answers neighbor discovery for the host pools, so a peer reaches the own stack over IPv6. The dns scenarios (TRN-29) and the loss workload (TRN-22) complete over IPv6 on an AF_XDP veth pair. It edits only those three crates, its handoff, this entry, and `Transport.md`; `Cargo.lock` changed for the dev-dependencies.

- `fps-tcp-own`: `wire` builds and parses the 40 byte IPv6 header (no extension headers, no header checksum) and the TCP pseudo header of RFC 8200 section 8.1; `parse_frame` takes both Ethernet types. `Tuple` and `Conn` hold `IpAddr`, and `Station` keeps its caches by `IpAddr`, so one station serves both families with one MAC address per host, as `fps-hosts` does. The MSS is the MTU minus 40 for IPv6 and minus 20 for IPv4, minus the 20 byte TCP header (1,440 at an MTU of 1,500), and an IPv6 peer that sends no MSS gets 1,220 (the 1,280 byte minimum MTU). `Station::receive` hands ICMPv6 neighbor solicitations to the `Responder`. `HostSlice::address6`, `ip`, and `index_of`, `Pools::pair_v6` and `Pools::sized_v6` are new; `OwnStack::connect_addrs(local, remote, port)` opens a session of either family, and `connect` and `connect_hosts` keep IPv4 for a pool that has both. A connection with mixed families is `InvalidInput`.
- `fps-udp-own`: the same for UDP. The UDP checksum is required over IPv6 (a zero checksum counts as a bad UDP checksum), the traffic class and flow label are ignored, an IPv6 datagram above the MTU leaves as fragments with a fragment header (next header 44), and received IPv6 fragments are dropped and counted (`rx_fragments`) as for IPv4. `UdpArm::connect(source, destination)` takes the family from the addresses and returns `InvalidInput` for a mix (it returned `Unsupported` for IPv6 before).
- `fps-datapath`: `classify` has `Class::Ipv6Tcp`, `Ipv6Udp`, and `Ipv6Other` (another ICMPv6 type, another next header, and any extension header); ICMPv6 types 133 to 137 stay `Nd`. The splitter gives an `Nd` frame to the `Responder` first: a solicitation for a host of the lane is answered on the queue that took it (`nd_replied`), a solicitation for another address is `nd_ignored`, a malformed one is `malformed`, and everything else (router advertisements, say) goes to the ND hook as `nd_unsupported`. `Connector::connect` and `connect_udp` find the lane by the address family of the hosts, and `Feature::Ipv6` and `Feature::Nd` are gone (a public enum variant, nothing in the workspace used them).

Tests: 163 unit and 30 integration tests of `fps-tcp-own` (6 new IPv6 integration tests: bulk both ways, MTU 1,280, loss, corruption, dual stack, tagged many hosts), 22 layer and 15 wire tests of `fps-udp-own` (12 new), and in `fps-datapath` 4 classifier tests, 11 `memory.rs` tests (3 new: ND answers and the MAC of the stack, IPv6 TCP and UDP sessions on two lanes, the classes), and `dns_scenarios.rs`, which now runs every test over both families:

- `dns_scenarios_complete_over_ipv6_in_memory` and `dns_scenarios_complete_over_ipv6_on_a_veth_pair`: every flow of the seven dns scenarios with IPv6 pools (`fd00:1::/64` clients, `fd00:2::/64` servers).
- `dns_client_over_af_xdp_completes_against_a_kernel_server_over_ipv6`: the client side over AF_XDP, the server side over kernel sockets bound to `fd00:2::1` on the other end of the veth. The kernel verifies the IPv6 checksums, and it resolves the client hosts with neighbor solicitations that the splitter answers (the test requires `client_nd_replied > 0`). The sandbox kernel has no IPv6, so this one ran only in CI.
- `loss_workload_completes_over_ipv6_in_memory`, `..._over_ipv4_in_memory`, `..._over_ipv6_on_a_veth_pair`, `..._over_ipv4_on_a_veth_pair`: `fps_tcp::workload::loss_transfer` (TRN-22) runs unchanged on the datapath, which `DatapathStack` in the test makes a `TcpStack`. A veth end that an AF_XDP socket owns sends around the queueing disciplines, so `netem` cannot impair it (TRN-26): each arm is wrapped in a `LossyQueue` that drops 2 percent of the received frames from a seeded generator. The run must confirm every byte, the drops must be counted, and the stacks must receive more frames than the data needs, which means they sent segments again.

Findings:

- A connection grows by 24 bytes and a connection table entry by 28, because `Tuple` and `Conn` hold two `IpAddr` of 17 bytes where they held two `u32`. The memory budget test of `Conn` went from 176 to 200 bytes. Per socket this is below the noise of the buffers, but the million socket rows of TRN-20 will read slightly higher. An IPv4 only build could keep the old size with a compact key; not done.
- An IPv6 frame from the kernel carries a traffic class that no checksum covers, so a bit flip test must skip those bits.
- The own stack still sends no neighbor solicitation and no ARP request: neighbors come from the pools, so the tests seed them through `Pools` and the kernel resolves the stack, not the reverse. Next hop resolution for a peer outside the pools is TRN-35.
- Over IPv6 the UDP layer does not reassemble, and the stack does not read ICMPv6 (no packet too big, no destination unreachable, no echo). Extension headers are not parsed: a frame with one is `Ipv6Other` and dropped.
- The splitter had to claim ND solicitations before the hook, because the `Responder` already answers them with the MAC address of the stack; a test compares the advertisement with the source MAC of a SYN.

- Module development (`Module-Development.md`, "Watch out for"): replace the TRN-29 entry about large UDP datagrams with this wording. **A UDP flow that sends more than 1,472 bytes (IPv4) or 1,452 bytes (IPv6) in one datagram is not heard on the AF_XDP backend.** The user space UDP layer fragments large datagrams on send and does not reassemble received fragments, so a peer that fragments is dropped and counted (`rx_fragments`); keep the datagrams of a module at or below the MTU minus the IP and UDP headers. Package: TRN-29, TRN-30.
- `Cargo.lock` changed: `fps-hosts` is a dev-dependency of `fps-udp-own` and `fps-tcp` of `fps-datapath` (the loss workload of the harness runs on the datapath). No root `Cargo.toml` edit was needed.
