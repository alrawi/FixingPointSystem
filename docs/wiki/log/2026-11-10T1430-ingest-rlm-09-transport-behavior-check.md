## [2026-11-10] ingest | RLM-09 Transport behavior check in the realism runner

The realism runner has a seventh check, `transport_behavior`, and the report format is 0.9.0. It compares the SYN and the SYN-ACK of every TCP connection with the operating system profile of the host that sent them, in the IP TTL (or hop limit), the do not fragment flag, the MSS, the window scale, SACK permitted, and timestamps. The labels file names one profile for every host (`transport.os_profile`, or `--os-profile`) or one per IP address (`transport.hosts`), and `client_hops` and `server_hops` give the routers between the hosts and the capture point, because the TTL comparison is exact (the profile TTL less the hops). A server answers only the options that the client offered, so a SYN-ACK is compared in those options with the SYN of its connection. The option order and the SYN window of the SYN decide only with `strict: true` (`--transport-strict`), because the Linux kernel sets both and the kernel backend cannot reproduce the order of windows11 and macos14 or the window of macos14. Without strict they appear in `deviations` with `enforced: false`.

The check reads the profile files of the kernel backend (`engine/fps-backend-kernel/profiles/`) and does not copy them: `socket.ttl` and `socket.mss` give the TTL and MSS, and `reference` gives the window scale, the SYN window, the option list (which also says whether SACK and timestamps are offered), and the do not fragment flag. The runner parses the TCP headers itself, so the check needs no tool, and its tests run in the sandbox. `tests/test_transport.py` builds one capture per profile from option bytes written out in the test, and each passes; a SYN with TTL 64 against windows11 fails with `the profile expects 128, the capture shows 64 in 5 of them`; a TTL one too high or low, a wrong MSS, window scale, timestamp, SACK, or do not fragment setting, an answer with an option that the SYN lacked, and a malformed option list fail too.

Finding: the committed harness fixtures (`modules/*/fixtures/*.pcapng`, recorded without an OS profile) match the `linux6` profile in the TTL, MSS, SACK, timestamps, option order, and SYN window, but their window scale is 10 and the profile says 7, because the namespaces of the harness allow a larger receive buffer than `tcp_rmem_max` of the profile. The two loopback fixtures (ftp, pop3) show the MSS 65495 of the loopback interface. `realism/examples/transport.labels.yaml` replaces the window scale with `expect: {window_scale: 10}` and passes on the http1 fixture; against `windows11` the same fixture fails in the TTL, the window scale, and timestamps.

### Shared page notes

- [Transport](Transport.md): the capture test `engine/fps-backend-kernel/tests/netns/profiles.sh` keeps its client arm captures as a workflow artifact of the `capture` job of `trn.yml`. A step there can score them with the same profile that the test used, for example `python3 -m realism score --pcap windows11.pcapng --labels L --os-profile windows11 --server-hops 1` (the labels need one session rule, or `default`, for the conformance check), which gives the real per profile evidence that the sandbox cannot record. The kernel backend does not reproduce the option order of windows11 and macos14 or the SYN window of macos14 (the limits table), so leave `--transport-strict` off for them. The profile comparison also depends on the namespace sysctls of `profiles.sh` (`tcp_timestamps` off for windows11, the `tcp_rmem` maximum for the window scale), which the test already sets.
- [Testing](Testing.md): the optional tests of the realism runner list gained `realism/tests/test_transport.py`, which needs no tool.
- [Home](Home.md) and [Implementation Plan](Implementation-Plan.md): none. The report format is now 0.9.0 (the `transport_behavior` entry), so consumers that pin 0.8.0 need the bump. [Realism](Realism.md) is updated.
