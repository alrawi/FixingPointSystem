## [2026-11-10] ingest | RLM-07 Mix accuracy check

We added the `mix_accuracy` check to the realism runner in `realism/mix.py`. It measures the achieved mix in two ways, from the run metrics (`sessions.attempted`, `bytes.tx`, and `bytes.rx` per scenario) and from nDPI on the capture (sessions and application payload bytes per application), and compares each with the configured weights of the test configuration (`profile.mix`, `profile.basis`) for the session basis, the byte basis, or both. The tolerance is 2 percentage points by default and configurable, and the comparison is exact. Per application and basis the entry reports the configured share, both achieved shares, both deltas, the counts, and a reason in words for each failing source. A scenario maps explicitly to an application in the labels (`mix.scenarios`), and the application gives the nDPI names of the conformance check. Sessions that nDPI names as no application of the mix form an `(unmatched)` row with a configured share of 0. The check is opt in: a `mix` section in the labels, or `--test-config`, `--run-report`, `--mix-tolerance`, or `--mix-basis`. The report format is at 0.8.0. A run report that is 3 points off for one application fails, and shares within 2 points pass, in `realism/tests/test_mix.py` with synthetic run reports and pcapgen captures (a stub, a fake ndpiReader, and the real ndpiReader when installed). The [Realism](../Realism.md#mix-accuracy-check) page describes the check, and the runner README gives the formats. The evidence is `docs/handoff/RLM-07.md`.

### Shared page notes

- Contract note for the controller (CTL): the `RunReport` of `GET /v1/runs/{id}/report` has no counts per scenario, so the check reads the series of `GET /v1/runs/{id}/metrics?view=scenario&side=client`, saved as a file (alone, or under `metrics` next to the report). A report that carries a `scenarios` table with `scenario`, `sessions`, and `bytes` would let the check run on one file, and the check already reads that table. Gate 2 (`tests/gates/gate2/`) can save the metric series of a run next to its capture and call `python3 -m realism score --test-config ... --run-report ...`.
- [Testing](../Testing.md): the tests run under `make test-rlm`. `realism/tests/test_mix.py` runs the real ndpiReader when it is installed, as `test_ndpi_reader.py` does.
- The report version moved to 0.8.0 and the four test modules that asserted 0.7.0 now assert 0.8.0. A package that adds an entry at the same time takes the next minor version, so two such packages may conflict on that line of `realism/report.py` and on the four assertions.
- Metric catalog (CON): `mix.share_pct` and `mix.abs_error_pp` have the label `application` only, so this entry leaves `metrics` empty, as the structure check does. A label for the source (`metrics` or a classifier) would let the check report them.
- Follow up for RLM: a scenario with several connections per session (`web_browse`) needs a way to count nDPI sessions per scenario instance, for example through the structure reconstruction of RLM-08. Until then the bytes basis is the way to check such a mix.
