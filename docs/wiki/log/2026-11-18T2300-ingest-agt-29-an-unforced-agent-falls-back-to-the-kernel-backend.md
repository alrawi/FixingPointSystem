## [2026-11-18] ingest | AGT-29 An unforced agent falls back to the kernel backend

AGT-29 (issue #679) makes an agent that nobody forced to AF_XDP run a plan that its datapath refuses on the kernel backend, and fills the fields that CON-35 added to the heartbeat. It edits only `engine/fps-agent/` (the backend, run, select, session, and convert modules, `Cargo.toml`, and the tests), `Cargo.lock` (one dependency edge, `serde_norway`, which the module crates already use), `docs/handoff/AGT-29.md`, this entry, and the Agent page (the new section "A plan that the datapath refuses").

- `fps-agent connect` sets `Config::fall_back` when the selection chose AF_XDP by its rules (its reason is not `Forced`). `run::prepare_selected` hands it to `backend::resolve_with_fallback`: an unforced agent runs a plan that `check_af_xdp` refuses on the kernel backend and keeps the cause in `Prepared::fallback` (the same text that a forced agent gets as its error), and `prepare` logs it. A forced agent, the standalone mode, and `prepare_on` refuse as before.
- A pool with both an IPv4 and an IPv6 prefix is refused by the datapath (`BackendError::Unsupported`, "the run would use IPv4 alone"). It passed before and ran over IPv4 alone. The kernel backend serves it, so an unforced agent falls back.
- `check_af_xdp` refuses a mix entry whose scenario is on the exclusion list of TRN-36. The agent includes `engine/fps-datapath/realism/profiles.yaml` with `include_str!`, reads the `excluded` mapping of each module with `serde_norway`, and refuses every plan for AF_XDP when the list does not parse. A unit test pins the three entries, compares the built in list with the file on disk, counts the modules with an `excluded` key in the raw text, and checks that every entry names a scenario file of its module.
- `fn heartbeat` names `run_backend` and `run_ports` and no longer uses `..Default::default()`. The run driver sets them after `Prepared::start_backend` returns (`select::backend_of` of the started backend, and `StartedBackend::run_ports`: every `PortBinding` of the plan in plan order with the mode of its bound sockets, `XDP_MODE_UNSPECIFIED` under the kernel backend) and sends a heartbeat at once. They stay in STOPPED and FAILED and clear on the next `Prepare` or the release of the plan.
- `select::select_with_transport` and `select::selection_input_with` take the transport fact as an argument. They exist so that a test can ask for the selection after the flip of TRN-31 without changing `TRANSPORT_AVAILABLE`, which stays `false`.

Decisions.

- The unforced test is the reason of the selection and not a new flag of the command line, because the selection already says whether the operator forced the backend.
- The fallback hides nothing: the report names the backend that ran, and the log names the cause. No cause travels in the protocol, as CON-35 decided.
- A plan that names `BACKEND_AF_XDP` explicitly and reaches an unforced agent that selected AF_XDP falls back like any other. A plan for the kernel backend that reaches an agent that selected AF_XDP is still refused with `ERROR_CODE_FAILED_PRECONDITION` (AGT-24). The controller sets `plan.backend` from the inventory (CTL-54), so the two agree in practice.

Findings.

- **`enterprise_mix_10g.yaml` cannot run through an agent on any backend today, and the datapath has nothing to refuse in it.** The acceptance of the package expects the datapath to refuse it and an unforced agent to run it on the kernel backend. The network of the example is in the shape that the datapath serves: two interfaces (`eth1`, `eth2`), one client pool, one server pool, one family, no VLAN, known OS profiles, and no excluded scenario. `check_af_xdp` accepts the plan, and an unforced agent keeps AF_XDP (`tests/fallback.rs`, `the_enterprise_mix_with_two_ports_is_a_plan_that_the_datapath_serves`). The agent refuses the plan for another reason, on both backends: `assemble` says `mix entries web_browse and web_get both listen on tcp 172.16.0.2:8080`, because the example http1 scenarios `web_browse` and `web_get` both accept on `server_port: 8080` and the controller assigns no ports (its golden plan `controller/internal/compiler/testdata/enterprise_mix_10g/agent-a.json` has the same two entries). `tests/fallback.rs` pins that refusal for a forced and an unforced agent (`the_enterprise_mix_is_refused_by_the_agent_on_both_backends_before_any_fallback_matters`). The vetting agent needs to pick one: a CON change that gives one of the two entries a `params: {server_port: ...}` in the example (the datapath then serves it, so it still does not exercise the fallback), or a different example for the fallback acceptance, or a new refusal of the datapath that the own stack really needs. I added no refusal that has no reason.
- `http_smoke.yaml` meets the acceptance: both ports are `local/lo`, the datapath refuses the plan ("same interface lo"), an unforced agent runs it on the kernel backend (session test with loopback pools, which reports `BACKEND_KERNEL` in the heartbeats of RUNNING and STOPPED and clears it on the next prepare), and a forced agent refuses it with the same text.
- A DHCP pool still ends at `prepare` on an unforced agent: the fallback chooses the kernel backend, and `assemble` refuses `dhcp4` for both backends until HST-04.
