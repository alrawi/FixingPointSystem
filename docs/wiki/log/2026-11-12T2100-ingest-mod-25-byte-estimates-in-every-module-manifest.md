## [2026-11-12] ingest | MOD-25 byte estimates in every module manifest

MOD-25 gives every scenario of the 12 first party modules that had none an `expected_bytes` entry measured from the module tests, corrects the four hand written `sip_rtp` estimates, and adds a guard test `default_parameters_move_the_expected_bytes` to each of the 14 modules with scenarios (`hls` had one). The guard runs every scenario of the manifest with its default parameters, adds the payload bytes of both directions of every connection, and fails at a difference of 2 percent or more. It also fails for a key of `expected_bytes` that names no scenario, which the validator does not check. The first CI run of this branch removed `FPS_GATE2_BASIS` from `.github/workflows/qa-gate2.yml`, and the mix failed on the bytes basis (see the findings), so the variable stays in the workflow and the waiver continues.

What was measured:
- Scenarios whose sizes come from the session generator vary a lot between sessions (`ftp/retr_epsv` between 46000 and 413000 bytes, the mail scenarios between 36000 and 650000). Their guard averages over `ESTIMATE_SESSIONS` session ids under the seed 42 (100 for `ftp`, `smtp`, `imap`, `pop3`, 40 for `ssh`, 20 for the others, 10 for `smb2`), so the estimate is reproducible. A mean over 20 sessions moved by up to 10 percent against the mean over 100, so the estimate of the random scenarios still has an error of a few percent, and the calibration of the run corrects it.
- TLS scenarios count the plaintext above the TLS layer (`Run::c2s` and `Run::s2c`), and the plaintext before STARTTLS counts. UDP flows count datagram payloads. Spawned flows count through `net.conns()` (the FTP data connection, the RTP media).
- The values are rounded to three significant digits from 1000 bytes up.
- `sip_rtp` had hand written values 12 to 21 percent above the measurement for `call_pcma` (175000, measured 154030), `call_g729` (50000, 41276), `call_opus` (150000, 133646), and `busy` (1800, 1574). `call_pcmu` was right.
- `modules/_template/` has 1280, which is exactly 256 plus 1024. `content` has no scenarios, `tls` has no manifest, and `strike` is MOD-27's.

[Module Development](../Module-Development.md) now says in "How to measure it" that a scenario with drawn sizes needs the mean over many session ids, what counts as payload for TLS, datagrams, and spawned flows, how the first party manifests round, and that the guard also checks the keys. [Modules](../Modules.md) has a section "Byte estimates".

Findings for the coordinator:
- **qa-gate2 on the bytes basis fails, so `FPS_GATE2_BASIS` stays.** Run 43262436363 (commit 51af583) removed the variable. The mix ran with `basis bytes, waived none` and every other row passed (the controller compiled the bytes basis from the staged manifests), but the byte shares missed the 2 point tolerance. Largest differences, run metrics against the weight: `ftp` +7.84 points (18.84% for 11%), `sip_rtp` +4.42, `smtp` -2.29, `pop3` -2.08, `imap` -1.99, `http2` -1.59, `ssh` -1.66, `smb2` -1.41, `http` (http1 and hls) -0.77 (nDPI gives the same picture). The scenario totals show the cause: `ftp/retr_epsv` moved 3880 bytes per counted session against the 7765 of `mix.yaml`, and `sip_rtp/call_pcmu` 18615 against the 37230 of `mix.yaml`, which is half. The run counts the FTP data connection and the RTP media stream as sessions of their own, so the calibration of CTL-12 and CTL-21 measures half the real bytes per scenario session and doubles the session share of these two scenarios. The estimates of the manifests do not decide this, because the stage replaces the manifest value of every mix scenario with the `mix.yaml` value. A fix belongs to the controller or the run report (count a spawned flow with the session that opened it, or count bytes per scenario session), or the `mix.yaml` estimates must become the halves that the calibration measures, which hides the defect. Not forced here, as instructed.
- `tests/gates/gate2/test_mix_config.py::test_the_stage_puts_required_modules_first_and_sets_the_estimates` fails with this package, because it asserts that the staged `ssh` manifest has exactly the one key `remote_command` (`assert ssh["expected_bytes"] == {"remote_command": want}`), which was true while the `ssh` manifest had no estimates. The file belongs to QA-05 and is outside the paths of MOD-25, so I did not edit it. The coordinator applies the one line change `assert ssh["expected_bytes"]["remote_command"] == want` on the branch before merge.
- The Gate 2 suite stages its module trees with the estimates of its own `mix.yaml` for the scenarios of the mix (`mix_config.py`, `stage_modules`), and those estimates assume the mix parameters (for example `body_size` 20000). The manifest values of MOD-25 are the default parameter values, so the two sets differ on purpose. Once the bytes basis passes, the `mix.yaml` column `expected_bytes` and the stage step could be replaced by the manifests, which needs the mix to run on default sizes or a per entry override, and is a QA decision.
- `mix.yaml` says the run report seems to count the FTP data connection and the SIP media stream as sessions of their own. The manifest values count them with their scenario session, as the schema defines. If the controller calibration divides the bytes by those counted sessions, `ftp` and `sip_rtp` estimates there would look about twice too high. Nobody settled this, and the first qa-gate2 run on the bytes basis shows whether it matters.
- qa-gate2 could not run locally (it needs root, namespaces, and Zeek); the CI run above is its only result. The guard tests of the 14 crates ran here with `cargo test --offline -p <crate> --test scenarios default_parameters`. The disk of the sandbox was full, so the build used a tmpfs target directory.
