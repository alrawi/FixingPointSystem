## [2026-11-09] ingest | MOD-10 FTP module

MOD-10 adds the `ftp` module under `modules/ftp`. Its native crate `fps-module-ftp` implements eleven template functions for the passive mode replies (`pasv_reply`, `epsv_reply`) and their parsers (`pasv_port`, `epsv_port`), the multi line `FEAT` reply, `ls -l` listings, synthetic credentials and file names, and three readers (`number`, `arg`, `length`) that carry transfer sizes between the two sides. Five scenarios cover a listing over PASV (`list_pasv`), a PDF download over EPSV (`retr_epsv`), a ZIP upload (`stor_pasv`), a session with a listing, a download, and an upload on one control connection (`mixed_session`), and a batch of downloads (`batch_download`). Each is a scenario instance with a `control` flow and spawned data flows, so it is the first module that uses `spawn`: the server binds the passive port in the spawned flow before it announces it, the client reads the port out of the 227 or 229 reply with `set` and spawns the same flow after its transfer command, and the spawned side reads the port through the variables of its parent. The files come from `content.binary` with a fixed seed, so the server can measure a file before it sends it. We updated the [Modules](../Modules.md) page and `modules/ftp/README.md`.

The acceptance, one control and one data connection per transfer, is verified by `modules/ftp/fixtures/structure_check.py`. RLM-08 does not exist yet, so the script reads the capture with the CAP-01 extractor `python3 -m capture sessions --payloads`, attributes each data connection to a control connection, compares its port with the 227 or 229 reply, and fails on a refused, repeated, orphaned, or reset connection. It passes on the committed capture of 40 control and 80 data connections, and the unit tests of the script cover every failure. The first recording of the fixture had a refused data connection for every transfer, because the client dialed before the spawned server side had bound the port, so the scenarios now spawn the server side before the reply. The Zeek check `zeek_check.py` could not run in the sandbox, which has no Zeek. The first CI run showed what Zeek 9.0.1 logs: `ftp.log` has a `PASV` or `EPSV` row with the data channel for every transfer and a `RETR` or `STOR` row for every file transfer, with no data channel in the second, and no row for `LIST`, and `files.log` has an `FTP_DATA` file for every data connection, so the check now counts listings through `files.log` and compares the ports of the files with the announced ports. The nDPI 4.2 classifier labels 40 of 40 control connections FTP_CONTROL in the realism job.

### Shared page notes

- `engine/fps-agent/src/modules.rs` dispatches only `http1` and `dns` (the MOD-07 and MOD-08 notes still hold). A plan with an ftp scenario fails every call until the agent also routes `ftp` to `fps_module_ftp::Ftp` and `content` to `fps_module_content::Content`. The dispatch needs a field `ftp: Option<fps_module_ftp::Ftp>` in the module set, an arm for `fps_module_ftp::MODULE_NAME` that checks `catalog_diff(&manifest.functions, &native)` against `fps_module_ftp::FUNCTIONS` like the arm of `http1`, a `"ftp"` arm in the render dispatch, and the dependency `fps-module-ftp` in `engine/fps-agent/Cargo.toml`. The agent must also run the scenario as a `ScenarioInstance` and give it a `FlowEnv` whose opener binds a data port on `accept` and tolerates a `connect` that arrives before the listener, because the control flow spawns the data flow and a plan that runs only single sessions fails at `spawn`.
- Scenario language: a spawned flow cannot be waited for, and a flow cannot read until the peer closes. The module works around both (a delay before `226`, and sizes that travel in `SIZE`, `ALLO`, and the variable `list_entries`). A CON package could add an `expect` stop rule `until_close` and an action that waits for a spawned flow, which would also give the `226` reply a real ordering. A reference to the address of the local host (the client address for `PORT`, the server address for the 227 reply) would remove the variable `server_ip` and make active mode possible. Both are contract changes that MOD-10 does not make.
- Testing: the table of Testing can list `lint-mod-ftp test-mod-ftp e2e-mod-ftp` and the workflow `mod-ftp` with the smtp and imap rows.
- Realism: `realism/labels.py` has no default label names for `ftp`, and the module labels name the classifier names in `expected.yaml`, so nothing needs to change. RLM-08 can replace `structure_check.py` with its scenario graph check for the control and data connections. Passive data connections have no nDPI label in this module, because nDPI classifies a data connection only when it recognises the content, so they stay unlabelled.
- `mk/mod-ftp.mk` and `.github/workflows/mod-ftp.yml` are new files in the style of the imap module. The workflow runs on `ubuntu-24.04`, a GitHub hosted runner, and never on a self hosted one, and it also runs the unit tests and the structure check of the fixture. The `realism` workflow already selects the module, because it ships `fixtures/capture.sh` and `fixtures/expected.yaml`.
- `Cargo.lock` gained the entry of `fps-module-ftp`, as for the other modules.
