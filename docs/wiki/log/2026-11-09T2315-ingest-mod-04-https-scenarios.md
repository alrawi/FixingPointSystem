## [2026-11-09] ingest | MOD-04 HTTPS scenarios

MOD-04 adds four http1 scenarios over TLS: `https_fetch` (Chrome 136, TLS 1.3, port 8443), `https_keepalive_browse` (Firefox 139, TLS 1.3, port 8444), `https_fetch_tls12` (Safari 18.5, TLS 1.2, port 8445), and `https_keepalive_browse_tls12` (Edge 134, TLS 1.2, port 8446). Each side runs `tls_upgrade` as its first action. The client names the browser profile and the SNI `www.example.test`, and the server names `server-tls13` or `server-tls12`. The browsers offer `h2` and `http/1.1`, the servers select `http/1.1`, and the certificate comes from the run authority of the TLS module.

The tests in `modules/http1/tests/https.rs` run the scenarios over TLS in memory and check the version, ALPN, SNI, the encrypted wire, the key log, and the JA4 of every ClientHello against the `expected_ja4` of its profile. The fixture `http1.pcapng` now holds 120 plain and 80 TLS sessions, and it embeds the TLS keys as a decryption secrets block (`editcap --inject-secrets`). The labels give each port a `tls_profile` and the JA4. The realism runner reports nDPI conformance 1.0 for both groups (HTTP for the plain sessions, TLS for the https sessions), no tshark parser errors, and 80 of 80 decrypted sessions with 80 of 80 matching JA4. We described the module in [Modules](../Modules.md#https-scenarios).

nDPI cannot see inside TLS, so the acceptance item "nDPI classifies at least 99% of decrypted fixture sessions as HTTP" is measured by `fixtures/decrypted_check.py`: it decrypts the capture with tshark and the embedded keys, writes the plaintext as plain TCP sessions with the same endpoints, and scores that view with the realism runner. nDPI 4.2.0 classifies 80 of 80 decrypted sessions as HTTP, and tshark parses 200 requests and 200 responses in the 80 TLS sessions of the capture. The view is synthetic (built from tshark's output), which the README states.

### Shared page notes

- Workflow `.github/workflows/mod-http1.yml` (out of the paths of MOD-04): add `modules/tls/**` to both `paths` lists, because the http1 tests now depend on `fps-module-tls`, and add this step to the `module` job after "Score the committed fixture":

  ```yaml
      - name: Check the HTTP inside the TLS sessions of the committed fixture
        run: python modules/http1/fixtures/decrypted_check.py modules/http1/fixtures/http1.pcapng
  ```

  The job already installs `libndpi-bin` and `tshark`, and `tools/contracts/requirements.txt` gives the realism runner its Python packages. The `harness` job needs nothing: `capture.sh` runs the check itself and `editcap` comes with `tshark`. The test `modules/http1/tests/fixture.rs` runs the same check inside `cargo test`, skips itself without the tools, and fails instead with `FPS_REQUIRE_CAPTURE_TOOLS=1`, so the `rust` job runs it only where the tools exist.
- Contract and engine: the scenario schema allows `transport: {module: tls, profile: ...}` on a flow, but `fps-flow` rejects the keyword in every runnable mode (`unsupported: a transport module`), and the validator does not look at it. The https scenarios therefore use `tls_upgrade`. Decide whether the schema should drop `transport` (a CON package) or the engine should implement it as an upgrade right after `connect` or `accept` (an ENG package). Until then the keyword is a trap, because a scenario that names it validates and then fails to load.
- [Transport](../Transport.md#browser-profiles-and-ja4), for the TRN workstream: the expected JA4 of a browser profile holds only for the first handshake of a connector. A connector with `ClientResumption::InMemory` sends `session_ticket` (0x0023), and its second TLS 1.3 handshake adds `pre_shared_key` (0x0029), which changes the extension count and hash. A connector with `ClientResumption::Disabled` never sends `session_ticket`, so its JA4 has 10 extensions and the hash `648ed004696a` for Chrome. The module tests of MOD-04 build a connector per session, which keeps every handshake at the documented value. `TlsProfiles` in `fps-runtime` shares one connector per profile, so AGT-14 must build a connector per session, or the labels of a run must list the fingerprints of resumed sessions too.
- AGT-14: the agent must register the profile names of the https scenarios, which are the four browser profile names on the client side and `server-tls13` and `server-tls12` on the server side (TLS 1.3 only and TLS 1.2 only, ALPN `http/1.1`, a certificate for `www.example.test`), and it must ship the key log with the capture so the realism runner decrypts it. `modules/http1/tests/common/tls.rs` is a reference for the registry.
- [Realism](../Realism.md#encryption-check), for the RLM workstream: nDPI has no decrypted view, so a module over TLS cannot meet an acceptance item about the protocol inside TLS with the conformance check alone. `decrypted_check.py` builds a decrypted view from `tshark -z follow,tls,raw,N` and scores it with the runner. A later RLM package could move that into the runner as a check (an option `decrypted_view: true` on the `tls` labels) so MOD-06 and MOD-20 do not copy the script.
- MOD-06 and MOD-20 will want the same profile registry. `modules/http1/tests/common/tls.rs` and `common/http.rs` are candidates for a shared test crate under `tests/`.
- [Testing](../Testing.md): `make test-mod-http1` now also runs `tests/fixture.rs`, which calls python3, tshark, and ndpiReader.
- The root `Cargo.lock` gained `fps-module-tls` and `rustls` in the dev dependencies of `fps-module-http1`, both already locked.
- The sandbox of this package had `ip`, `tcpdump`, `tshark`, `editcap`, and `ndpiReader` after `apt-get install iproute2 tcpdump`, and network namespaces worked, so the committed capture comes from the QA-01 harness and not from a loopback recording.
