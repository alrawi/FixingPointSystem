## [2026-11-09] ingest | AGT-08 mutual TLS and enrollment in the agent

`fps-agent connect` dials an `https://` controller over mutual TLS with rustls (the ring provider, as in `fps-module-tls`) and keeps `http://` for a controller that runs with `insecure_plain_grpc`. The new module `fps_agent::identity` trusts the controller CA from a CA file (`--tls-ca`), from the CA that an earlier enrollment stored, or from a pinned SHA-256 fingerprint (`--tls-ca-sha256`, the `ca_sha256` that the controller logs). When `--cert-dir` holds no valid certificate, the agent makes an ECDSA P-256 key (file mode 0600), sends a CSR with the common name set to `--agent-id` and a one time token to `POST /enroll` over HTTPS at `--enroll-address` (default: the controller host, port 8445), writes the key and certificate atomically, and deletes the token file or unsets the variable. The token comes from `--enroll-token-file` or from `--enroll-token-env` (default `FPS_ENROLL_TOKEN`) and never from the command line. A task calls `POST /renew` at `renew_at` on its own HTTPS connection, which never touches the open session, so the agent never redials just to renew (D12 item 12). A handshake failure, `UNAUTHENTICATED`, a refused token, and a missing trust anchor are permanent: the agent aborts any run and exits with code 2 and a message that names the cause. An unreachable controller and `PERMISSION_DENIED` still redial with the limit of D12 item 11. A token file that exists at a dial replaces a valid certificate, which is how an operator re-enrolls an agent after `fps-controller revoke`. `tests/mtls.rs` runs a fake enrollment endpoint and a fake controller over mutual TLS (14 tests), `tests/controller_e2e.sh` now mints a token with the real controller, enrolls the real agent, runs a plan over mutual TLS, and checks the handshake failures against the real controller, and a throwaway Go server around the real `pki` package accepted the agent's CSR, issued and verified its certificate, and refused it after `Revoke` with exit code 2. The [Agent](../Agent.md#mutual-tls-and-enrollment) page describes the design.

### Shared page notes

- [Image](../Image.md) and `image/` (not edited here): to drop `insecure_plain_grpc` from `image/files/etc/fps/controller.yaml` the image needs four changes.
  1. **Provision a token.** On the all in one VM an `ExecStartPre=` helper of `fps-agent.service` (next to `fps-init-token` of the controller unit) runs when `/var/lib/fps-agent/pki/agent.crt` and the token file are both missing. It waits up to 30 seconds for the admin socket `/var/lib/fps/pki/admin.sock`, then runs `fps-controller token -agent-id "$FPS_AGENT_ID" -ttl 10m -config /etc/fps/controller.yaml` with `umask 077` into `/var/lib/fps-agent/enroll.token`. On a separate agent VM the operator mints the token on the controller (`fps-controller token -agent-id <id>`) and hands it over through the cloud-init user data that `fps-role` reads, which writes the same file. Never put a token in `FPS_AGENT_EXTRA_ARGS` or any other command line. The agent deletes the file after it enrolls, so a reboot does not enroll again, and a leftover file makes it enroll again.
  2. **Pass the flags.** `fps-agent-start` builds the default URI as `http://${FPS_MGMT_ADDR}:8444` and it must say `https://${FPS_MGMT_ADDR}:8444`, and it adds `--cert-dir /var/lib/fps-agent/pki --tls-ca /var/lib/fps/pki/ca.crt --enroll-address "${FPS_MGMT_ADDR}:8445" --enroll-token-file /var/lib/fps-agent/enroll.token`. The unit gets `StateDirectory=fps-agent` with mode 0700. An agent on another VM needs the CA certificate in its cloud-init payload for `--tls-ca`, or `--tls-ca-sha256` with the weaker first exchange that the Agent page describes. A controller URI that names a DNS name or an address other than `FPS_MGMT_ADDR` needs `-tls-names` on the controller.
  3. **Open the enrollment port.** `isolation.nft` lists `{ 22, 8443, 8444 }` for the management address and needs 8445, and `fps-controller.service` needs `-enroll-listen ${FPS_MGMT_ADDR}:8445`, because the controller listens on `localhost:8445` by default.
  4. **Remove the stopgap.** Delete `insecure_plain_grpc: true` and its comment. `agent_auto_enroll: true` can stay, and it should, because the inventory lives in memory and a restart of the controller empties it while the agents keep valid certificates.

  The agent now exits with code 2 on a failure that redialing cannot fix, and `fps-agent.service` has `RestartPreventExitStatus=2`, so systemd does not restart it. That fits a bad CA or a refused token, and after a revocation the operator mints a new token, writes it to the token file, and restarts the unit.

- Findings for the coordinator and the owner. (a) The controller sends only its leaf certificate in the TLS handshake. If `serverCertificate` in `controller/internal/pki/tlsconfig.go` also sent the CA certificate (`Certificate: [][]byte{der, caDER}`), the agent could verify a pinned fingerprint before it sends the token, and `--tls-ca-sha256` would be as safe as a CA file. This is a CTL follow up of one line plus a test, and the agent code would then need a verifier that looks for the pinned certificate in the chain. (b) A pinned fingerprint that does not match is detected after the exchange, so the token is spent. (c) The agent renews with the key it enrolled with. A key rotation needs one atomic switch of the key and certificate pair, for example one file with both. (d) `Register` and `Session` now end on SIGTERM while a silent controller holds the call, which `session.rs` did not do before.
