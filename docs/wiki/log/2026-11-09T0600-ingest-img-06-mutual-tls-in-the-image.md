## [2026-11-09] ingest | IMG-06 mutual TLS in the image

The image drops the `insecure_plain_grpc` stopgap and follows the four steps of the AGT-08 log entry. `fps-agent.service` runs the new helper `/usr/libexec/fps/fps-enroll-token` as root before the agent: it moves a token that cloud-init wrote to `/etc/fps/enroll.token` into `/var/lib/fps-agent/enroll.token`, and in the all-in-one role, when the agent has neither `agent.crt` nor a token file, it waits up to 30 seconds for the admin socket and runs `fps-controller token -agent-id <id> -ttl 10m` with umask 077 and standard output redirected into that file. No token is on a command line, in a unit, or in a log. `fps-agent-start` dials `https://` and passes `--cert-dir`, `--enroll-token-file`, `--enroll-address`, and `--tls-ca` (the controller CA file) or `--tls-ca-sha256`. The agent role takes the CA from `/etc/fps/controller-ca.pem` or the `role.env` key `FPS_CA_SHA256`, and the controller address of enrollment from the optional key `FPS_ENROLL_ADDRESS`. `fps-role` refuses a token in `role.env`. The unit has `StateDirectory=fps-agent` (0700), the controller unit has `-enroll-listen ${FPS_MGMT_ADDR}:8445`, and `isolation.nft` opens 8445. `fps-role` also had a parser bug that the new key exposed: its key pattern `[A-Z_]+` rejected a name with digits, so `FPS_CA_SHA256` fell into "cannot read the line". The pattern is `[A-Z0-9_]+` now. The offline tests gained `tests/enroll-token-test.sh` (helper and agent arguments), new cases in `role-test.sh` and `static-check.sh`, and `vm-checks.sh` and `boot-test.sh` check mutual TLS in the VM.
