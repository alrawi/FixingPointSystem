## [2026-11-10] ingest | IMG-07 The agent session gate in the image boot test

The job "Build, boot, and run" of `image.yml` failed twice on 2026-11-10 (jobs 129666780207 and 129934010691) and passed on rerun. We found the cause in the VM journals of the failing jobs and described it in the section The agent session gate of [Image](../Image.md). The controller marks the agent online when it reads the open message of a session, but it sends nothing more until it has a command or a heartbeat to answer. The agent waits for the first frame of the response before it heartbeats, so an idle session has no heartbeat. The controller ends it 5 to 6 s later, and the agent dials again. A command that reaches an unopened session in the last second before that end finds an agent that already counted five seconds of silence, and the agent drops the session, so the run fails in `prepare` with `agent session lost`. Both failed jobs ran on KVM, so a slow guest and a clock step do not explain it.

We changed `image/` only. `image/tests/vm-run.sh` gets a gate that starts the first command on a session that the agent opened and held for 3 s, or that the controller registered at most 2 s ago, and that fails when there is none. `image/boot-test.sh` gets `FPS_TEST_REPEAT` (boots in a row, stop at the first failure) and `FPS_TEST_NEGATIVE=agent-unreachable` (one more boot with the agent pointed at the loopback, which must fail at the agent checks). `image/tests/session-gate-test.sh` replays the journals of the failed job and `image/tests/boot-loop-test.sh` tests the loop and the negative boot with a fake boot. Both run in `make test-img`.

### Shared page notes

- [Controller](../Controller.md): the cause belongs to `controller/internal/agents/service.go`. `Manager.Session` should call `stream.SendHeader(metadata.MD{})` right after `m.open` returns, so that a client that waits for the response headers (the Rust agent, through tonic) opens its session at once and starts its heartbeats. A regression test needs a client that waits for the headers before it sends a heartbeat; the Go client of `fakeagent` does not wait, and the tonic fake of `engine/fps-agent/tests/session.rs` receives the headers when its handler returns, so neither saw the gap. Until that change, an idle agent session ends every 5 to 6 s, and `GET /v1/agents` shows `online` for a session that carries no heartbeat.
- [Agent](../Agent.md): the agent could also heartbeat while it waits for the response headers, which makes it independent of the controller. `session()` in `engine/fps-agent/src/session.rs` sends the first heartbeat only after `client.session(...)` returned.
- [Testing](../Testing.md): the boot test has two new settings, `FPS_TEST_REPEAT` and `FPS_TEST_NEGATIVE`, and one new check in the HTTP and DNS run (`run: the agent local has a session that takes the first command`).
- Coordinator, outside the catalog paths of IMG-07: (1) `mk/img.mk` lists scripts by name in `IMG_SHELL_FILES`, so `make lint-img` does not ShellCheck `image/tests/session-gate-test.sh` and `image/tests/boot-loop-test.sh` until they are added. Both pass `shellcheck -x`. (2) To run the loop in CI, add the two variables to `env:` of the step "Boot the all-in-one role and run HTTP and DNS" in `.github/workflows/image.yml`: `FPS_TEST_REPEAT: "10"` and `FPS_TEST_NEGATIVE: agent-unreachable`. The step needs no other change, because the script writes `boot-N/` and `negative/` below `FPS_TEST_ARTIFACT_DIR`. The 10 boots take about 8 minutes on KVM, and the negative boot about 3 more. A repository variable can turn the loop on for pull requests only, for example `FPS_TEST_REPEAT: ${{ github.event_name == 'pull_request' && '10' || '1' }}`.
