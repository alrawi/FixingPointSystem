## [2026-11-09] ingest | MOD-08 IMAP module

MOD-08 adds the `imap` module under `modules/imap`. Its native crate `fps-module-imap` implements fourteen template functions. The client counts its tags up from `A001` with `imap.next`, and the server copies the tag out of the command line in `last` with `imap.tagged`, so the tagged responses match the commands. `imap.fetch` parses a `FETCH` command and renders the requested items, with the body items as literals `{n}` that carry MIME messages from the content module. The same crate renders `SELECT` and `EXAMINE` data, `SEARCH` and `STORE` responses, and `EXPUNGE` numbers, and `imap.literal_marker` and `imap.literal_size` handle the literals that the client sends. Five scenarios cover a message list with header literals (`mailbox_sync`), whole messages from a read-only mailbox (`fetch_messages`), `SEARCH`, `STORE`, and `EXPUNGE` (`search_store`), a literal password and an `APPEND` literal with continuation requests (`login_append`), and `IDLE` with a pushed `EXISTS` (`idle_push`). We updated the [Modules](../Modules.md) page and `modules/imap/README.md`.

nDPI 4.2 classifies any flow with an `AUTHENTICATE` command as IMAPS, so the module has no `AUTHENTICATE PLAIN` scenario and the acceptance (at least 99% IMAP) holds. A port of the nDPI dissector to Python classifies all 40 sessions of the committed capture as IMAP at the fifth payload packet. The real ratio comes from the realism job in CI. The module has no STARTTLS scenario, and ENG-20 adds the engine action that it needs.
