## [2026-11-10] ingest | AGT-14 TLS profiles, TLS key export, and labeled criteria in the agent

The agent builds the TLS profiles of a plan, ships the TLS key log in the capture file, and applies the labels of a criterion. `fps_agent::tls` scans the compiled scenarios of the mix for `tls_upgrade`, refuses a plan at prepare when an action names a profile that the table of its role lacks, and builds a `TlsProfiles` for `RuntimeConfig::tls`: the four browser profiles of TRN-05 on the client side, `server-tls13` and `server-tls12` (one version, ALPN `http/1.1`, a certificate for `www.example.test`, `localhost`, and the server names of the actions) on the server side. The authority of a run is derived from the run seed, so a client agent and a server agent trust each other without an exchange. Every connector and acceptor writes its secrets to a `KeyTap`, which keeps lines only while a capture with `export_tls_keys` runs. The capture assembly puts them into the joined pcapng as one decryption secrets block per section, ahead of the packets, so the download decrypts alone. `Criterion.labels` select series (catalog labels only, `side` picks the side), and the refusal of labeled criteria in `convert.rs` is gone. `tests/tls.rs` runs https through the agent with a server side criterion, a client process and a server process with one seed, a capture that decrypts with the lines of the file alone (a `ring` decrypter), and a ClientHello shape check over three handshakes. `tests/controller_e2e.sh` runs `http1/https_fetch` under the real controller with a `where: {side: server}` criterion and a negative control. We described it in [Agent](../Agent.md#tls-profiles).

### Shared page notes

- Outside the catalog paths: `modules/tls/native/src/authority.rs` gained `RunAuthority::from_pkcs8_der` (additive, one unit test), because `ServerIdentity` can only come from a `RunAuthority` and `generate` draws from the system random source. The root `Cargo.lock` lists `fps-module-tls` and `num-bigint` (both already locked) in the dependencies of `fps-agent`.
- [Testing](../Testing.md): `make test-agt` now runs `tests/tls.rs`, which needs no external tool. The e2e script installs the first party `http1` module instead of the example one (same name and version), and its first test runs `http1/single_fetch`.
- [Controller](../Controller.md) lines 244 and 595 are stale: the Rust agent applies labels and puts the key log into a capture only when `export_tls_keys` is true. [Contracts](../Contracts.md) line 175 says the agent refuses labeled criteria, which no longer holds.
- No SMTP STARTTLS scenario exists yet (MOD-20), so the acceptance item about SMTP STARTTLS is met with https in the e2e script and the agent tests, and the STARTTLS path is covered by ENG-20's runtime test. MOD-20 needs a client profile that is not a browser. It can use `chrome-136` with `server-tls13` today, or add a profile to `tls::client_profiles` and `tls::build`.
- A real REST capture of an https run still needs AGT-12 (the REST contract requires a port and the agent refuses one), and CI has no tshark in the `controller-e2e` job. The decryption is verified in `tests/tls.rs`.
- Follow up for ENG: `TlsProfiles` shares one connector per profile. The agent works around the resumption that this causes by disabling tickets on its own servers, which does not help against a third party server that issues them. A factory that builds a connector per session in `fps-runtime` would remove the workaround. The runtime also records no `tls.*` metrics yet.
- Follow up for CON: the seed derived authority means that anyone who has the plan can sign a certificate that the clients accept. A plan field that carries a certificate and key would fix that if a run ever needs it.
