## [2026-11-10] ingest | ENG-23 Multi flow scenario instances in the runtime

`fps-runtime` runs scenarios with more than one flow. A worker whose `FlowRef` points at a scenario with several flows drives one `fps_interp::ScenarioInstance` for every session start (client) or accepted connection (server), through a new `InstanceEnv` that implements `FlowEnv` over the kernel backend. The entry flow dials, or takes the accepted connection, as a single session does. Every other flow dials the rendered port and retries a refused connect for up to two seconds, or binds the rendered port on the address of the entry connection, accepts one connection, and releases it, retrying a bind that finds the port in use. Every flow side gets its own capture tap, session id, native functions, and extension instances, and counts in the session series of its flow under `application`, `scenario`, and `side`. A scenario with one flow keeps the single session path, with no extra series and no extra allocation. The config check refuses a spawned entry flow and a scenario with a UDP flow. The acceptance test runs `modules/ftp` `mixed_session` between a client runtime and a server runtime: eight instances give 32 sessions on each side, all succeeded, and the capture of the client sessions shows one control and three data connections per instance. We updated [Engine](../Engine.md).

### Shared page notes

- Agent, for AGT-16 (`engine/fps-agent`, not edited here because AGT-14 edits it). In `assemble.rs`, delete the `s.flows.len() != 1` refusal and refuse instead a scenario with any `L4::Udp` flow among several flows (`s.flows.len() > 1 && s.flows.iter().any(|f| f.l4 == L4::Udp)`), because the runtime refuses it at `Runtime::start` with a less specific error. The rest of `assemble` already reads flow 0 for the L4, the accept port, and `FlowRef::new(scenario, 0)`, which is the entry flow that the runtime expects. In `modules.rs`, `compile` calls `Scenario::parse_with`, which refuses `spawn` (`LoadError::Unsupported`); call `Scenario::parse_instance(&s.source, ctx.as_ref())` for every scenario (it accepts what `parse_with` accepts), and `with_params` and constant folding stay as they are. The ftp scenarios need nothing else: the server workers bind data ports themselves, and `ClientConfig::port` replaces only the entry connect, so `ExternalServer.port` in a client simulator topology reaches the control connection and the data connections go to the ports that the 227 and 229 replies announce.
- Testing: the table can list `cargo test -p fps-runtime --test instances`. `engine/fps-runtime` gained the dev dependencies `fps-module-ftp` and `fps-module-content`, so `Cargo.lock` gained two entries in the dependency list of `fps-runtime`.
- Follow up for a package on `engine/fps-interp` (ENG-07): `ScenarioInstance` builds its sessions without a `TlsUpgrader`, so a `tls_upgrade` action in an instance flow fails with `internal`. An `InstanceConfig` field or a `FlowEnv` method that returns the upgrader would fix it, and `fps-runtime` would pass `TlsProfiles` through. The same package could pass the session id to `FlowEnv::stream`, `datagram`, and `functions`: the runtime now predicts it by counting starts (a side's id is the first id plus the number of sides started before it, valid while an instance runs one side per flow) and a debug assertion checks the prediction against every `SideRecord`.
- Follow up for SIP (MOD package) and a runtime package: a worker instance runs TCP flows only. A scenario with spawned RTP flows needs an `InstanceEnv::datagram` opener that connects or binds `KernelDatagram` sockets as the UDP workers of the agent do, and the agent has its UDP workers in `udp.rs` outside this runtime.
- Capture (CAP): the ring writes a session when it ends, so a capture of an instance has the control connection after its data connections and the file is not in time order, which the `packets` helper of the `fps-capture` tests rejects. Wireshark and `reordercap` accept it, and the test of this package parses frames without the order check. A capture of such sessions could sort within the flush if a consumer needs time order.
- Metrics: the series carry no `flow` label, because the metric catalog has none, so flows of one module share their series (`application=ftp` counts control and data connections together). A distinct application per flow needs a different `module` on the flows.
