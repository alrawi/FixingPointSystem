## [2026-11-09] ingest | MOD-09 POP3 module

MOD-09 adds the `pop3` module under `modules/pop3`. Its native crate `fps-module-pop3` implements thirteen template functions for plain POP3 on port 110. The server greeting carries a timestamp banner from `pop3.banner`, and the client computes the `APOP` digest, the MD5 of the banner and a synthetic secret, with `pop3.apop_digest` from the greeting line in `last`. The server answers each command with a function that reads the command line from `last`: `stat_reply`, `list_reply`, and `uidl_reply` agree on sizes and Dovecot style identifiers, and `retr_reply` and `top_reply` write dot stuffed multi line responses that carry MIME messages from the content module. Six scenarios cover `USER` and `PASS` with `CAPA`, `STAT`, `LIST`, `UIDL`, and `RETR` (`retrieve_all`), an accepted `APOP` (`apop_login`), an `APOP` that the server rejects followed by `USER` and `PASS` (`apop_fallback`), `TOP` previews (`top_preview`), `RETR` with `DELE` and `RSET` (`fetch_delete`), and a short polling session (`poll_new_mail`). We updated the [Modules](../Modules.md) page and `modules/pop3/README.md`.

nDPI 4.2 detects POP3 from a stage counter (`+OK` and `-ERR` packets) plus the distinct commands from the list `AUTH`, `APOP`, `USER`, `PASS`, `CAPA`, `LIST`, `STAT`, `UIDL`, `RETR`, `DELE`, `STLS`. It needs a `PASS` that saved a password, or a stage above 3, which cannot happen because `mail_pop_stage` is a bit field of two bits in `ndpi_typedefs.h`. A session that logs in with `APOP` alone is therefore never identified by DPI (`ndpiReader` 4.2.0 guesses it by port, which the realism runner counts as unknown), and the first capture of this package showed 8 of 40 sessions unknown in the realism job. The module keeps `apop_login` and its `capture.sh` leaves it out of the fixture with `--skip apop_login`. `apop_fallback` tries `APOP`, gets `-ERR [AUTH]`, and logs in with `USER` and `PASS`, so nDPI identifies it at payload packet 6. With that, `ndpiReader` 4.2.0 classifies 40 of 40 sessions of the committed capture as POP3 with the confidence DPI, and the realism runner reports the ratio 1.0. The module has no STLS scenario, and ENG-20 adds the engine action that it needs.

### Shared page notes

- `engine/fps-agent/src/modules.rs`: `NativeFunctions` dispatches only `http1` and `dns`, as the MOD-07 and MOD-08 notes say. A plan with a pop3 scenario fails every call until the agent also dispatches `fps_module_pop3::Pop3` for `fps_module_pop3::MODULE_NAME` (and `fps_module_content::Content` for `content`), and `engine/fps-agent/Cargo.toml` lists `fps-module-pop3 = { path = "../../modules/pop3/native" }`. AGT-13 adds the registry, so MOD-09 did not edit the agent.
- Testing: the module has no Zeek log check, for the reason that the imap module gives, and relies on the parser error check of the realism runner and on tshark.
- Realism: `realism/labels.py` has no default label names for `pop3`. The label in `expected.yaml` names the classifier name `POP3`, so nothing needs to change. nDPI also has a `POPS` name for port 995, which this module does not use.
- `mk/mod-pop3.mk` and `.github/workflows/mod-pop3.yml` are new files in the style of the smtp and imap modules. The workflow runs on `ubuntu-24.04`, a GitHub hosted runner, and never on a self hosted one. The `realism` workflow already selects the module, because it ships `fixtures/capture.sh` and `fixtures/expected.yaml`.
- `Cargo.lock` gained the entry of `fps-module-pop3`, as for the other modules.
- The sandbox of this package had `tshark` and `dumpcap`, and `apt-get install libndpi-bin` gave `ndpiReader` 4.2.0, the version of the CI runners, so the nDPI ratio was measured locally. It had no `zeek` or `ip`, so the capture comes from loopback and the Zeek parser check runs in CI only.
- nDPI follow up: a nDPI release that widens `mail_pop_stage` would let `apop_login` join the fixture. A report to the nDPI project is the owner's call.
