## [2026-11-18] ingest | AGT-28 the agent runs IPv6 host pools on the datapath

AGT-28 lets the agent start the AF_XDP datapath for a plan whose host pools have an IPv6 prefix and no IPv4 prefix. It edits only `engine/fps-agent/`, its handoff, this entry, and `Agent.md`. It changes no other crate, no workflow, and not `Cargo.lock`.

- `backend::layout` no longer refuses a pool without an IPv4 prefix ("IPv6 is TRN-30"). It reads the family of each pool (`family_of`): IPv4 when the pool has an IPv4 prefix, because `assemble` picks the host addresses that way (`Pools::addresses`, `source_addr`), and otherwise IPv6. A pool with neither prefix is a plan error, and a client pool and a server pool in different families are a plan error as well (`host pool clients runs over IPv6 and host pool servers over IPv4, and a lane carries one family`), because the datapath finds the lane of a session by the family of its hosts and such a plan could not open one session. A pool with both prefixes runs over IPv4, as before.
- The pools reach the stack unchanged. `slice_of` already built `HostSlice` values from the parsed `HostPool`, which holds the IPv6 prefix, so `Pools::pair_v6` and `Pools::sized_v6` (test constructors of `fps-tcp-own`) are not needed in the agent: the agent builds the `Pools` struct itself from the plan. The gateway wiring of AGT-26 (`datapath_config`) reads `HostPool::gateway()`, which holds an IPv6 gateway as well, and `Route::of` of the datapath serves it per family, so an IPv6 gateway turns the neighbor resolution on and the datapath asks for it with neighbor solicitations (TRN-35). No other code of the agent changed: the workers (`assemble`, `udp`) and the transport already carried `IpAddr`.

Evidence. Unit tests on fake hosts (`backend::tests`, no root): an IPv6 only plan passes the check and the stack sees `fd00:1::1` and `fd00:2::2` as hosts 0 and 1 with no IPv4 address; mixed families, and a client pool with both prefixes against an IPv6 only server pool, are refused; an IPv6 gateway turns the neighbor resolution on and no gateway leaves it off; a TCP session between two IPv6 hosts of the plan pools runs through `start_on_queues` on in memory links and the server sees the client host; and a connect to an address behind an IPv6 gateway makes the client arm send a neighbor solicitation (`neighbor_requests >= 1`, none on the server arm). The acceptance test is `tests/afxdp_veth.rs` (root), which now holds the same forced AF_XDP run twice: `a_forced_af_xdp_run_starts_the_datapath_on_a_veth_pair` (IPv4) and `a_forced_af_xdp_run_over_ipv6_pools_starts_the_datapath_on_a_veth_pair`, where both pools carry only an IPv6 prefix (`fd00:1::/64`, `fd00:2::/64`). The helper in the namespace checks that the plan pools have the family, runs a 4096 byte session between two hosts of the pools and checks the peer address, and runs the standalone `run` on the plan: the http1 and dns entries complete with client and server counts equal, no failed session, verdict pass, and the lane report shows TCP frames and UDP datagrams. The two tests use their own namespace and plan directory, because they run in one process. Sandbox run (root, kernel 6.18 without IPv6, debug build, 4.2 s for both): over IPv6 http1 63 and dns 24 sessions, all passed on both sides, none failed, 1,807 TCP frames and 48 UDP datagrams through the lane; over IPv4 the same counts with 1,791 TCP frames.

Findings:

- The kernel does not need IPv6 for this test. The AF_XDP socket takes the frames of the pair before the IP layer, and no kernel socket is a peer, so only the veth pair is needed. A kernel without IPv6 therefore runs it (the kernel server test of TRN-30 is the one that needs it).
- The test does not pin `other_dropped` over IPv6: a kernel with IPv6 sends multicast listener reports and router solicitations on a new veth end, and the splitter counts them as other protocols or as unsupported ND.
- A plan with a pool of each family cannot run on a lane, and the agent names it at `prepare`. Dual stack lanes (one pool with both prefixes on one side and a pool with both on the other) run over IPv4 only, as `connect` and the worker addresses choose IPv4 first. An IPv6 run of a dual stack pool needs a plan field that names the family; none exists, and it is a contract change, so it is not added here.
