## [2026-11-10] ingest | QA-09 Parser findings of the Gate 1 run and the reused 5-tuple rule

The Gate 1 suite now keeps the findings of the parser error check as files in OUT (`parser-findings.json`, `.csv`, and `.pcapng` with the frames of the sessions that carry a finding), plus `tcpdump.log` and `capture_dropped` in `context.json`. `FPS_GATE1_REPEAT=N` runs the suite N times in a row (`OUT/run-N`, stops at the first failure, `repeat.json`). `prove-corruption.sh` runs after `prove-threshold.sh` and shows that a capture with a corrupted chunk size in one HTTP response still fails the gate.

Cause. The artifacts of the two failed runs (MOD-12 push, first attempt of CTL-39) could not be read from the sandbox, so the cause was first inferred and then confirmed by the first CI run of this branch. Both failed runs had fewer `http1` sessions in the capture than the agent attempted (1337 and 1339 of 1340). A session that the capture stop cuts is still a session of the capture, so this is not a boundary cut. Two connections with one 5-tuple form one session of the realism runner, and `http1/single_fetch` lets the server close first, so the server holds the old connection in TIME_WAIT and the client kernel may pick the same source port again. In the last 86 CI runs 16 had merged `http1` sessions, both failures were among them, and none of the 70 others had a finding. Locally tshark 4.2.2 reported nothing in 24 runs with the real agents and in one capture with 259 reused sessions. The first CI run of the branch (42921139910, 1338 of 1340) wrote one finding to `parser-findings.json`: the Zeek weird `premature_connection_reuse` in a session with two connections, which is the finding that failed the earlier runs. The gate does not count that weird in sessions with more than one TCP connection, and every other finding still fails it.
