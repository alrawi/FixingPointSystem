## [2026-11-18] ingest | AGT-24 the agent starts the selected backend

AGT-24 makes a run start the backend that the agent selected, lets a forced `--backend af_xdp` run work while `TRANSPORT_AVAILABLE` is false, and reads the bound mode of an AF_XDP port from its sockets. It edits only `engine/fps-agent/`, its handoff, this entry, and `Agent.md`. It does not set `TRANSPORT_AVAILABLE`, and without a forced backend the selection stays the kernel backend until TRN-31.

- `select::selection_input` sets `af_xdp.transport_available` when the operator forces AF_XDP. Kernel support and the driver still decide, so a forced run on a host without AF_XDP sockets or without a driver that takes XDP fails with the cause and never falls back. The tests that pinned the refusal with `NoTransport` changed with it (`src/select.rs`, `tests/select.rs`), and the unforced selection is still tested to be the kernel backend.
- `fps_agent::backend` (new). `resolve(plan.backend, selected)` returns the backend that the run starts: the selection when there is one (a plan that names another backend is refused with `ERROR_CODE_FAILED_PRECONDITION`, and one that names none is accepted), the plan in the standalone mode. `assemble` takes the resolved `BackendKind` and no longer reads `plan.backend`. `Config::backend` carries the selection from `fps-agent connect`, `run::prepare_on` is `prepare_with` plus the selection.
- `start_af_xdp` opens one AF_XDP queue per lane on the interface of the client pool and on the interface of the server pool, hands each pair to a lane of `fps_datapath::Datapath` (TRN-27), and starts it. `BoundPort` holds the attach mode and the bind mode of every queue as the sockets report them and maps them to the contract enum: generic attach is `XDP_MODE_GENERIC`, driver attach with all queues in zero copy is `XDP_MODE_ZERO_COPY`, else `XDP_MODE_NATIVE`. `StartedBackend::report` writes the mode into `PortInfo.xdp_driver_mode`, and `Prepared::start_backend` logs one line per port.
- A plan that the AF_XDP backend serves is refused at `prepare`, before a queue binds, when it needs more: a topology other than `TOPOLOGY_APP_SIM`, one side only, more than one client or server pool in the mix, both pools on one interface, IPv6, DHCP, different VLANs, or a UDP flow. The messages name TRN-29 and TRN-30.
- The standalone `run` and `connect` use `start_backend`, then `start_on`. For AF_XDP `start_on` stops the datapath again and returns `Unimplemented`, see the finding below.

Evidence: `engine/fps-agent/tests/afxdp_veth.rs` is the acceptance test. It makes a namespace with a veth pair, `dpa` and `dpb`, and runs a helper process inside it. The helper prepares the example plan with `BACKEND_AF_XDP` and its two ports on the pair, starts the backend, and reads `XDP_MODE_NATIVE` for both ports (native attach, copy mode, from `XDP_OPTIONS` of the sockets). It reports the mode through `PortInfo`, sends a 4096 byte TCP session between a client host and a server host through the two queues and checks every byte (17 TCP frames went through the splitters), runs the standalone `run`, which logs `backend af_xdp bound port client0 interface dpa attach native queues copy xdp_driver_mode XDP_MODE_NATIVE` and then ends with `Unimplemented`, and starts the backend a second time to show that the queues were released. Sandbox run (root, kernel 6.18, debug build): 0.5 s. The own stack sends no ARP requests, and the station tables of the pools hold every host MAC address, so the harness seeds no neighbors. No kernel socket is a peer, so the transmit checksum offload of the veth pair does not matter here (TRN-26 found that a kernel peer needs it off).

Other tests: 7 unit tests in `src/backend.rs` (the resolution, the shapes that are refused, the mode mapping, the report), 2 new and 2 changed unit tests in `src/select.rs`, 2 in `tests/select.rs` (forced AF_XDP selects and dials before the flip, with the report), and `tests/session.rs` (`a_plan_for_another_backend_than_the_selected_one_fails_prepare`).

Findings:

- **No worker can run on the datapath yet, and TRN-12 cannot add that.** The TCP workers of `fps-runtime` open sessions through `fps_backend_kernel::Connector` and `KernelListener` and nothing else (`worker.rs`, `opener.rs`, `data_ports.rs`, `instance.rs`). The datapath has the same calls (`Datapath::connector().connect`, `Datapath::listen`, a session that implements `SessionIo`), but no trait joins the two. So a forced AF_XDP run binds the queues, starts the datapath, reports the mode, and then ends with `Unimplemented` that names `fps-runtime`. TRN-12 (paths `engine/fps-backend-afxdp/`, `engine/fps-datapath/`) cannot close the gap, because it needs a change in `engine/fps-runtime/` (an ENG package) and the wiring in `engine/fps-agent/` (`Prepared::start_on`, which is the one place to call `Datapath::connector` and `Datapath::listen`). Suggested shape: a `Transport` trait in `fps-runtime` with `connect(source, destination)` and `listen(address)` returning boxed `SessionIo`, an implementation for the kernel backend, and `WorkerConfig` carrying an `Arc<dyn Transport>`. The agent then passes `Datapath::connector()` and `Datapath::listen()` for AF_XDP and removes the `Unimplemented` of `start_on`. The datapath serves one `listen(port)` for all server hosts and a worker listens per address, so the server workers need one listener per port.
- **The bound mode cannot reach the controller yet.** `Register` comes before any plan, so its `PortInfo.xdp_driver_mode` stays the driver table hint. The contract has no message that sends the mode of a bound port later (a field on `Heartbeat` or on the `StartResult` would do), and a change to `contracts/` is a CON package. Until then the mode is in the agent log and in the return value of `start_backend`.
- The datapath serves one lane per queue pair and the agent starts one lane (queue 0 of each port). More lanes are a setting of `AfXdpSettings`, and the plan has no field for the queue count of a port.
- The plan field `PortBinding.mtu` is not applied by either backend.

### Shared page notes

- Transport page, section "Backend selection", the paragraph that starts "Nothing carries TCP over AF_XDP before TRN-12": replace it with the text below. It says the old thing that is no longer true (a forced AF_XDP run is refused with `NoTransport`).

  > Every host selects the kernel backend until TRN-31 sets `TRANSPORT_AVAILABLE`, so AF_XDP is never the default today. An operator who forces AF_XDP gets it on a host whose kernel and driver can run it (AGT-24): the agent sets `transport_available` for a forced run, because the datapath of TRN-27 is a transport, and the constant only keeps AF_XDP from becoming the default before the own stack has loss recovery and congestion control. A forced run on a host without AF_XDP sockets or without a driver that takes XDP is still refused with the cause. The tests in `tests/select.rs` cover a virtio-net guest with and without zero copy, an old kernel, a generic only driver, a driver without XDP, and forced backends. The expected bind mode is a plan, not a measurement: a run that starts the AF_XDP backend reads the mode that each socket really runs in (`BoundPort`, [Agent](Agent.md#starting-the-selected-backend)).

- Testing page: `cargo test -p fps-agent --test afxdp_veth` needs root (it re-runs through `sudo -n`), AF_XDP, and `ip`. `CI=true` or `FPS_REQUIRE_AFXDP=1` turns every skip into a failure. It runs in the `rust` job of `ci.yml` (`cargo test --workspace`, `CI=true`) on the hosted runner, where `sudo -n` works.
- Workflow (coordinator files): no change is needed for the acceptance.
