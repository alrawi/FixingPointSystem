## [2026-11-17] ingest | TRN-18 A minimal own TCP stack on the bench harness

`engine/fps-tcp` gained `OwnStack`, a minimal TCP stack of our own behind the `TcpStack` seam of TRN-17, and `tcp_bench --stack own` runs the three workloads on it. The stack is two TCP hosts that exchange IPv4 frames over a pair of `FrameIo` queues of `fps-backend-afxdp` (the in memory pair by default, so no root, and AF_XDP queues through `OwnStack::with_links` in TRN-12). It does connection setup with SYN, SYN-ACK, and ACK and an RFC 6528 style initial sequence number, data transfer with sequence and acknowledgment numbers and a receive window with window updates, FIN and RST teardown with the full state set including TIME-WAIT and half close, and IPv4 and TCP checksums. Retransmission is minimal and documented as such: one timer per connection, a fixed timeout that doubles, go back N, a reset after 8 timeouts. There is no congestion control, no window scaling, no fast retransmit, and no out of order queue. The component page [Transport](Transport.md#the-own-tcp-stack) lists what it does and leaves out. The only new dependency is the path crate `fps-backend-afxdp`, and `cargo deny check` passes with no new license.

The sandbox results (2 vcpu, shared host, not the GitHub runner and not fat-nuc) are committed in `engine/fps-tcp/results/sandbox-2vcpu-trn18/`, with the kernel reference run again in the same session because the sandbox booted differently since TRN-17. Sessions per second at 32 concurrent sessions are 32,000 to 36,000 for the own stack and 14,000 to 49,000 for the kernel across six runs, so they are the same within noise. Throughput over four uploads is 14.8 Gbit/s for the own stack and 19.0 Gbit/s for the kernel in one run. The own stack reached 1,000,629 sockets in 64 shards in 0.76 s for the last step at 228 B of resident growth per socket, where the kernel run stopped at 19,815 sockets at the open files limit of 20,000. The idle poll is flat at 0.4 us for one shard from 1,000 to 16,000 sockets, and 23 to 38 us for a pass over 64 shards up to 1,000,629 sockets, because the timers sit in a heap with one entry per connection and nothing walks the sockets.

Finding, the own stack scales by state and not by descriptors. A connection is about 200 bytes with empty buffers, and a poll with idle sockets costs the same for ten sockets and for a million. The cost of that choice is the code that the stack leaves out, which a production stack must still write: a round trip estimate, fast retransmit, selective acknowledgment, congestion control, window scaling, an out of order queue, and the corner cases of the state machine. The tests exercise loss, corruption, and delay on a link that is built for the purpose, but the throughput and rate numbers come from a lossless link, so they show the cost of the state machine, the checksums, and the frame copies, and nothing about loss recovery.

Finding, the numbers of the two stacks do not measure the same memory. The kernel stack's `bytes_per_socket` leaves out the kernel memory of a socket, and the own stack's figure is the whole cost of a socket. TRN-10 should not read 228 B against 0.3 to 0.5 KB as a win of the own stack by a factor of two.

Finding, a user space stack holds its closed tuples. The client side of every finished session stays in TIME-WAIT for the hold (one second by default, `--own-time-wait-ms`), so `sockets_open` at the end of a rate run is the listener plus the sessions of the last second, where the kernel stack reports 1. The test of the rate workload for the own stack allows this. TRN-20 will meet the same behavior in smoltcp.

Finding, the rate workload is latency bound for a user space stack. One session costs several driver passes and task switches, so the own stack does 32,000 to 36,000 sessions per second at 32 and at 256 concurrent sessions, and its p50 grows from 0.85 ms to 6.3 to 7.1 ms. A multi core rate needs `--threads`, and TRN-12 will decide how the engine shards its sessions.

Finding, a bug that the tests caught. Entering TIME-WAIT dropped the receive buffer, which discarded data that an application had not read yet after a half close. The buffer now stays until the session reads it or is dropped, and the test `shutdown_sends_a_fin_after_the_data_and_the_peer_reads_to_the_end` covers it.
