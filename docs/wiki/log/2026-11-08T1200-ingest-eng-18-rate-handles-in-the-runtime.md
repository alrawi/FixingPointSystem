## [2026-11-08] ingest | ENG-18 rate handles and paused worker wake in the runtime

The crate `engine/fps-runtime/` now exposes the rate handles of its client workers. Each client worker builds its schedule before it reports ready and reports the `RateHandle` with the name of its mix entry, and `Runtime::start` registers all handles in one `fps_sched::RateControl`, which `RuntimeHandle::rate_control()` returns as an `Arc`. The entry name is the new optional field `FlowRef::entry`, or the scenario name when it is `None`. A client worker now sleeps at most 100 ms, so a worker paused at rate 0 or held at the cap sees a new target within 100 ms. An invalid schedule now fails `Runtime::start` and no longer ends the worker after the start. Two loopback tests cover the change: one pauses a scenario, resumes it, and changes its rate twice through `RateControl` and finds every window within 15 percent on wall time, and one uses a snapshot interval of 30 seconds to show that a paused worker wakes within 300 ms of a resume, which fails without the bounded sleep. The [Engine](../Engine.md#run-time-rates) page describes the behaviour and the API.

### Shared page notes

- AGT-05 (`engine/fps-agent/`): keep `let control = handle.rate_control();` from the TCP `RuntimeHandle`, set `FlowRef::entry = Some(mix_entry.id.clone())` for every flow in `assemble.rs` (today `FlowRef::new` leaves it `None`, so the registry keys by scenario name, which is wrong when two entries share a scenario), and serve `UpdateRates` with `control.update(&[(entry_id, Objective::SessionsPerSecond(total))])`, or `control.scale(...)` for CTL-21 factors. The UDP runtime in `fps-agent/src/udp.rs` has its own workers and no handles yet, so UDP mix entries are not in the registry and AGT-05 must decide how `UpdateRates` treats them (the Engine page notes the gap).
- Testing page: the runtime rate test measures wall time with a 15 percent tolerance, which is flaky only on a host that starves threads for more than about 100 ms.
