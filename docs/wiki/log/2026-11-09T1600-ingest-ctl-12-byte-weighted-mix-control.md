## [2026-11-09] ingest | CTL-12 byte weighted mix control

The new package `controller/internal/mixcontrol/` estimates the bytes per session of each mix entry and returns one rate multiplier per entry, so that the byte share of each scenario converges to its weight. It is pure (standard library only, no clock, no random source, time passed in). The CTL-24 calibration loop in `controller/internal/runs/` owns it when the test sets `profile.basis: bytes` and the objective is `throughput_bps`: one loop per run sends `UpdateRates`, with `compiled rate * calibration factor * multiplier` per entry and one command per agent and window. The multipliers keep the weighted mean bytes per session of the compiled mix, so the factor of CTL-24 still scales the total to the objective. The schema already has `profile.basis`, so no contract change was needed. `CalibrationConfig.ByteMixOff` turns the control off, and the loop window is 1 s (the catalog value) unless the configuration sets one. The simulation with a fake agent (scenarios of 20 kB, 200 kB, and 200 B per session, manifest estimates off by 2x to 5x) reaches byte shares within 2 points of the weights within 30 simulated seconds and stays there for 120, with the throughput within 5 percent of the objective. The [Controller](../Controller.md#byte-weighted-mix-control) page describes the package and the loop.

### Shared page notes

- [Implementation Plan](../Implementation-Plan.md) and [Testing](../Testing.md): `make lint-ctl-mixcontrol test-ctl-mixcontrol test-ctl-bytemix` are new targets in `mk/ctl.mk`. `fakeagent.Traffic.BytesByScenario` and `Agent.ScenarioBytes()` give tests scenarios with different bytes per session.
- Follow up for CTL-05 (`controller/internal/compiler/`): the compiler still normalizes the weights as session shares for the `bytes` basis, so the controller corrects the mix from the first window and the first seconds of a run show the session weighted byte shares. A compiler that turns byte weights into session shares with the manifest estimates (and `throughput_bps` into rates from them) would start the run near the target. `mixcontrol.Entry` keeps the byte weight and the compiled session weight apart, and `newByteMix` in `internal/runs/bytemix.go` is the only place to change.
- Follow up for the run loop: a `bytes` basis with a `sessions_per_second` or concurrency objective gets no control yet. The `PreserveSessions` mode of `mixcontrol` exists for `sessions_per_second`, but the run loop only starts for `throughput_bps` objectives, and concurrency objectives would need `concurrent_sessions` targets in `UpdateRates`.
- The OpenAPI run schema has no field for `Run.Calibration`, which now also carries the multipliers (same note as CTL-24). Gate 2 (`tests/gates/gate2/`) can read the multipliers from the log line `byte mix step`, or from the run record once the schema has the field.
- The edits outside `internal/mixcontrol/` are additive: `internal/runs/calibration.go` and `orchestrator.go` (one call), the new `internal/runs/bytemix.go`, and `internal/fakeagent/rates.go`.
