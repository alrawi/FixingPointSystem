## [2026-11-18] ingest | TRN-22 a lossy link and loss workloads for the TCP harness

TRN-22 gave the harness a link with random loss, delay, reordering, and a rate limit with a bounded queue, a netem counterpart for the kernel stack, and a loss workload in `tcp_bench`.

- `impair.rs`: the model of one direction (bottleneck with tail drop, random loss, delay with a share of frames that skip it), seeded and repeatable, with the retransmission counter at the link and the `tc` commands (`tbf` root, `netem` child) for the kernel.
- The own stack lives in `fps-tcp-own`, which this package may not edit, so `lossy.rs` wraps its frame queues (`LossyOwn` over `FrameIo`), with a ticker that pumps the stack when a held frame falls due. smoltcp takes the model in its pair driver (`SmolConfig::impair`). `QueueDevice` gained `take_tx` and `push_rx`, and `StackStats` gained `retransmits`, `link_lost`, and `link_queue_dropped`.
- `netns.rs`: the kernel stack in a client, a router, and a server namespace, with the qdiscs on the router so the kernel sees drops in the middle of a network and not in its own qdisc (where `RetransSegs` counted 7,900 to 14,200 refused retransmissions per MiB). The server and the client are this binary again (`--netns-peer`, started with `ip netns exec`), so no `setns` and no unsafe code.
- `tcp_bench --workload loss` reports goodput, retransmissions, completion, and the time to complete per transfer, for loss levels (default 0, 0.1, 1 percent) with a delay of 20 ms per direction. The kernel run goes through `sudo -n` and exits with 3 (1 with `CI=true` or `FPS_REQUIRE_NETEM=1`) when it cannot run or the kernel has no `sch_netem`.
- Results are in `engine/fps-tcp/results/sandbox-2vcpu-trn22/`, with `host.txt`. The own stack completes 3 of 3 at 0 and 0.1 percent (12.2 and 8.0 Mbit/s) and 2 of 3 at 1 percent (one timeout at 60 s); smoltcp completes 3 of 3 at all three levels. The kernel rows at loss and delay were not measured, because the sandbox kernel has no `sch_netem`. The rate limit rows (8 Mbit/s, 64 KiB queue) ran on all three stacks.

Tests: model unit tests (loss rate and repeatability, reordering, rate and queue, retransmission counting with wrap, Ethernet framing, `tc` argument lists), report and command line tests, `tests/lossy.rs` (both stacks over delay, loss, rate, queue overflow, and a transfer that cannot finish), and `tests/netns.rs` (root, skips without root, sudo, or a qdisc).

### Shared page notes

- Testing page: `cargo test -p fps-tcp --test netns` runs the kernel namespace scenarios. It has no default harness, runs itself again through `sudo -n` as a normal user, skips with a message without root, sudo, `ip`, or a qdisc, and fails instead of skipping when `CI=true` (root, sudo, `ip`) or `FPS_REQUIRE_NETEM=1` (also a missing `sch_netem` or `sch_tbf`). A missing qdisc is a property of the runner image, so `CI=true` alone does not fail on it.
- `sch_netem` is missing on the agent sandbox kernel (`CONFIG_NET_SCH_NETEM` is not set; `tbf` is built in). I could not check the GitHub hosted runner. If `tc qdisc add ... netem` fails there, the hosted runner needs the extra kernel modules package of its kernel, installed through `tools/ci/apt-install.sh` (a coordinator file; this package installs nothing), and `sudo modprobe sch_netem`. Until then the delay and loss scenarios of `tests/netns.rs` skip, and the kernel rows of the acceptance are not measurable on it.
- Workflow `tcp-bench.yml` (coordinator file): to measure the acceptance rows on a hosted runner, add a job that runs, as one session, `tcp_bench --stack kernel --workload loss`, `--stack own --workload loss`, and `--stack smoltcp --workload loss` with `--out`, after the module step above. The command runs itself through `sudo -n`. Set `FPS_REQUIRE_NETEM=1` in that job.
- `Cargo.lock` changed: `fps-tcp` depends on `fps-backend-afxdp` (already in the workspace) for `FrameIo`. No root `Cargo.toml` edit was needed.
- Transport page: this package added the section "The impaired link and the loss workload (TRN-22)" to `docs/wiki/Transport.md`, the component page of the workstream.
- Module development: nothing changes for module authors.
