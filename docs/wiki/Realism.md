# Realism

This page describes the realism runner under `realism/`, which the RLM workstream owns. The runner scores a capture against the applications that the traffic was meant to carry and writes a JSON realism report. RLM-01 created the runner with the conformance check, RLM-02 added the parser error check, and RLM-04 added the encryption check, RLM-05 added the content variety check, RLM-08 added the session structure check, RLM-06 added the temporal distribution check, and RLM-07 added the mix accuracy check, RLM-14 added the message count check, and RLM-10 added the host identity check. The [runner README](https://github.com/alrawi/FixingPointSystem/blob/main/realism/README.md) gives the command, the options, and the report fields in full.

## Checks

The [specification](https://github.com/alrawi/FixingPointSystem/blob/main/docs/spec/specification.md#defining-realistic-traffic) defines protocol conformance with two targets. At least 99% of the sessions of every application are classified as that application, and a reference implementation reports zero parser errors. The report carries one entry per check.

| Check | Tools | Passes when | Package |
|---|---|---|---|
| `conformance` | nDPI through `ndpiReader -d` | At least 99% of the labelled sessions of every application carry the intended label | RLM-01 |
| `parser_errors` | tshark expert information and Zeek `weird.log` | At least one parser ran and no parser reported an error | RLM-02 |
| `encryption` | tshark with the exported TLS keys, and JA4 computed by the runner | Every sampled TLS session decrypts and every sampled ClientHello has the JA4 of its client profile | RLM-04 |
| `content` | Payloads reassembled by the runner, no external tool | No application has more than 1% duplicate payloads, and the size distribution agrees with the labels where they give one | RLM-05 |
| `session_structure` | Scenario files and the sessions of the capture, no external tool | Every scenario instance has the connections that its flow graph allows, in the order of its `after` and `spawn` edges | RLM-08 |
| `temporal` | Session start times and payloads read by the runner, no external tool | Every inter arrival time, payload size, and packet gap sample that the labels give a target for agrees with it in a KS test at α (default 0.01) (paced media: every stream keeps its packet time), and none has too few observations | RLM-06, RLM-15, RLM-22 |
| `mix_accuracy` | Run metrics per scenario and nDPI through `ndpiReader -d`, no other tool | Per basis (sessions, bytes, or both), the share of every application from the run metrics and from nDPI lies within 2 percentage points (configurable) of the configured weight | RLM-07 |
| `transport_behavior` | The SYN and SYN-ACK of every connection read by the runner, and the OS profiles of the kernel backend, no external tool | The TTL, do not fragment flag, MSS, window scale, SACK permitted, and timestamps of every handshake equal those of the profile of the sending host (the option order and the SYN window too in strict mode) | RLM-09 |
| `messages` | tshark on the capture, or on the decrypted view, no other tool | Every session that a rule of the `messages` labels selects has the expected number of requests, responses, commands, replies, or RFC 5322 messages, and every rule selects a session | RLM-14 |
| `host_identity` | Ethernet frames, VLAN tags, and ARP packets read by the runner, no external tool | No IP address sends from more than one MAC address in one VLAN, the number of hosts lies in the range of the `hosts` labels (when they give one), and a frame has an Ethernet source address | RLM-10 |

Every tool runs as a separate process, so the runner links none of their code. We chose the counting rules of the parser error check for three reasons.

1. tshark counts one error per frame, so a frame with several expert items counts once.
2. Zeek counts the weirds of one connection at one packet time once, and it leaves out weirds that come from session state, such as `dns_unmatched_reply`, because they do not mean that a message failed to parse.
3. An application reports the largest count of any one parser, so a fault that both parsers see counts once. A capture with one malformed DNS message therefore reports exactly one parser error.

4. A tshark finding does not count when it is a port collision (RLM-19, from QA-11). The kernel picks the client port of a session at random, and tshark binds about 900 TCP and UDP ports to a dissector, so a session whose client port is one of them (UDP 41170 is Manolito, TCP 44322 is the Performance Co-Pilot proxy) gets malformed packet findings from a dissector that does not fit its payload. The rule applies when the client port of the session is bound to a dissector for the transport and the server port is not bound to the same dissector. The entry lists each such finding under `not_counted` with the rule and the dissector, and the job summary of a module says how many findings did not count. The rule never applies to Zeek or to a finding without a session, and a real malformed packet in a session whose client port is free still fails the check.

5. A finding that the labels declare does not count either (RLM-20, issue #491). A module whose traffic is malformed on purpose lists, in the `expect_findings` of a session rule, the Zeek weirds and the tshark expert items that the sessions of the rule must produce. A declared finding is reported under `expected_findings` and stays out of every count, a declared item that no session of its rule produced fails the check (`missing_findings`), and a finding that no rule declares fails it as before. We chose declarations per rule and per item, and not a number of tolerated errors, so that a malformed scenario cannot hide a second, unplanned fault, and a scenario that stops being malformed fails too. An item of a parser that did not run is listed as unchecked and does not fail the check. A rule that sets `expect_every_session` (RLM-23, issue #551) holds each of its sessions to its declaration instead: every session of the rule must show every item, and `missing_findings` names each session that lacks one with its `session`, `transport`, `client`, and `server`. We kept the setting optional and per rule, because a rule that spans a well formed and a malformed scenario cannot demand it, and a scenario that shares a server port with another shares its rule. [`realism/README.md`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/README.md) (Parser errors) has the exact rules.

The parser error check reports `realism.parser_errors` with the labels `application` and `parser` for each labelled application and each parser that ran, and for the application `all` of each parser, which totals the findings of the parser including its unlabelled and unattributed ones. Its `realism.check_failures` is `errors_total`, plus one for each missing expected finding, plus 1 when no parser ran (see [Metric series](#metric-series-of-each-check)).

## Report

[`realism/schema/realism-report.schema.json`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/schema/realism-report.schema.json) defines the report, which is the seam to the controller and the gate suites. A new check adds a definition under `$defs` and one `if` and `then` entry in `$defs.check.allOf`. The report format is at version 0.21.0. Version 0.2.0 added the `parser_errors` entry, version 0.3.0 added `skipped_parsers` to it, version 0.4.0 added the `encryption` entry, version 0.5.0 added the `content` entry, version 0.6.0 added the `session_structure` entry, and version 0.7.0 added the `temporal` entry, version 0.8.0 added the `mix_accuracy` entry, version 0.9.0 added the `transport_behavior` entry, version 0.10.0 added the metric series and `metrics_basis` to the `mix_accuracy` entry, version 0.11.0 added the `messages` entry, version 0.12.0 added the metric series of every check (RLM-17), version 0.13.0 added the `host_identity` entry (RLM-10), version 0.14.0 gave the `messages` check its `realism.check_failures` series (CON-25), version 0.15.0 gave the `host_identity` check its series (CON-27), version 0.16.0 added the `packet_gap` property to the `temporal` entry (RLM-15), version 0.17.0 carried metric catalog 0.8.0 (CON-28), and version 0.18.0 added `not_counted`, `not_counted_total`, and `port_collision_ports` to the `parser_errors` entry (RLM-19), version 0.19.0 added `expected_findings`, `expected_total`, `missing_findings`, and `unchecked_expectations` to it (RLM-20), and version 0.20.0 added `path` and `min_samples` to the comparisons of the `temporal` entry and its `rungs` list (RLM-22), and version 0.21.0 added `session`, `transport`, `client`, and `server` to the entries of `missing_findings` (RLM-23). The labels file stays at `version: 1`, because a new section is optional and changes no other section.

## Metric series of each check

Report format 0.12.0 carries the series of metric catalog 0.5.0, which CON-23 defined and RLM-17 emits. Every check of the kinds `conformance`, `parser_errors`, `encryption`, `content`, `session_structure`, `temporal`, `mix_accuracy`, `transport_behavior`, `messages`, and `host_identity` has exactly one `realism.check_failures` series, with the label `check` set to its kind. Its value is the number of reasons for which the check failed, it is 0 exactly when the check passed, and the schema requires both. A check that fails without a reason of its own (a classifier run that scored nothing, a missing parser, no TLS session in the sample, no TCP handshake) still shows 1, so the failure reaches `RunReport.realism` even when no other series exists.

| Check | Series next to the failures series | Value of `realism.check_failures` |
|---|---|---|
| `conformance` | `realism.conformance_ratio` per scored application | Applications that failed, plus 1 when none was scored |
| `temporal` | `realism.ks_statistic` and `realism.ks_p_value` per comparison with a catalog label, including the KS comparisons of packet gaps (CON-28) | The length of `failures` |
| `parser_errors` | `realism.parser_errors` per application and parser, and per parser with the application `all` | `errors_total`, plus 1 when no parser ran |
| `encryption` | `realism.decrypted_ratio` and `realism.ja4_match_ratio`, not rounded, when sessions were sampled | The length of `failures` |
| `content` | `realism.duplicate_ratio` per application | The length of `failures` |
| `session_structure` | `realism.structure_failures` per scenario, summed for scenarios of one name | `failures_total` |
| `mix_accuracy` | `mix.share_pct`, `mix.abs_error_pp`, and `mix.max_abs_error_pp` with `source` `classifier` | `failures_total` |
| `transport_behavior` | `realism.transport_deviations` per enforced field and side, summed over the hosts | `failures_total` |

The `messages` check carries the `realism.check_failures` series since report format 0.14.0 and catalog 0.6.0 (CON-25), and the `host_identity` check since report format 0.15.0 and catalog 0.7.0 (CON-27). Both values are `failures_total`, so a failing check reaches `RunReport.realism`, and neither check carries another series. A report holds at most one check of each kind: the runner writes one entry per kind, and a document with two checks of one kind is invalid, because the second repeats the failures series of the first (see `contracts/changes/CON-27.md`). [`realism/tests/test_check_metrics.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/tests/test_check_metrics.py) pins the literal series of every kind for a passing and a failing check, and validates the examples of `contracts/examples/realism/check-metrics.yaml` against the schema.

## Delivery to the controller

`python3 -m realism score --attach-run ID` (RLM-16, `realism/deliver.py`) sends the report that it wrote to `PUT /v1/runs/ID/realism` (`attachRealismReport`) and prints the answer of the controller on standard error, so that `realism` of the run report holds the results. The report format does not change, because the body is the report as written. The run token comes from `--token-file`, `FPS_TOKEN_FILE`, or `FPS_TOKEN`, in that order, never from the command line, and `score` takes no abbreviated options so that `--token SECRET` cannot mean `--token-file SECRET`. The runner reads the token and checks the URL before it scores, redacts the token in server text, never follows a redirect, and refuses `http` to a non loopback host without `--insecure-http`. A failing report is delivered too. The exit code stays 0 or 1 for the checks when the controller accepts the report, and becomes 2 when it answers anything else: 409 for a run that has not ended, whose detail names the state, 422 with one line for each finding of the schema check, and every other status with its problem detail. The tests run a fake controller on loopback (`realism/tests/test_deliver.py`). [README](https://github.com/alrawi/FixingPointSystem/blob/main/realism/README.md#delivering-the-report-to-the-controller) has the options.

## Seams for tests

Each tool sits behind a protocol with a stub, so unit tests never need the real program.

| Protocol | Real implementations | Stub |
|---|---|---|
| `Classifier` in `classifier.py` | `NdpiClassifier` | `StubClassifier` |
| `ParserRunner` in `parsers.py` | `TsharkRunner`, `ZeekRunner` | `StubParser` |

Component tests replace each program with a small fake executable that prints fixed output, so they reach every error path of the process boundary. The modules `test_ndpi_reader.py` and `test_parser_tools.py` run the real tools and skip each tool that is not installed. Both workflows run [`realism/ci/install-tools.sh`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/ci/install-tools.sh), which installs tshark from Ubuntu, a pinned nDPI release built from source, and one pinned Zeek version from the package repository of the Zeek project, so CI runs every optional test. We run the checks locally with `make lint-rlm test-rlm`.

## Encryption check

The specification asks for real TLS handshakes with common browser fingerprints, checked by decrypting with exported session keys and by computing JA4. RLM-04 implements both in [`realism/encryption.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/encryption.py) and [`realism/ja4.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/ja4.py).

**Configured client profile.** A client profile of the [TLS module](Transport.md#tls-module) fixes the versions, cipher suite order, groups, ALPN, and SNI of a ClientHello, and it carries no fingerprint. The expected fingerprint therefore lives in the labels file, in a `tls` section that maps each profile name to its JA4 (one string or a list), and a session rule with `tls_profile` ties sessions to a profile. A browser profile of TRN-05 documents its JA4 and the labels file of a run copies it. The [runner README](https://github.com/alrawi/FixingPointSystem/blob/main/realism/README.md#encryption) shows the format.

**Sample.** Only sessions whose rule names a `tls_profile` take part. The check takes at most `tls.sample` of them (default 100), spread evenly over the order of their first packet, so the result does not depend on which sessions come first.

**Decryption.** The runner starts tshark once on the capture. tshark applies the keys that a pcapng capture carries in its decryption secrets blocks, which `fps-capture` embeds, and the key log in the NSS format that `--keylog` names, which the agent exports next to the capture. A session counts as decrypted when tshark reads the Finished message of both sides. TLS 1.2 and 1.3 both encrypt that message, and tshark shows it only with the right secrets, so a key log that lacks the handshake secrets, or belongs to other sessions, decrypts nothing. Two other signals do not work. The field `tls.app_data` exists without keys, and `tls.app_data_proto` is set without keys too. The entry reports the decrypted share against `tls.min_decrypted` (default 1) and says whether keys came from the capture, from a sidecar file, or from neither. A TLS 1.3 key log that holds the handshake secrets and lacks the application traffic secrets still counts as decrypted, which the check does not yet catch.

**JA4.** `ja4.py` follows the [FoxIO specification](https://github.com/FoxIO-LLC/ja4/blob/main/technical_details/JA4.md). It ignores GREASE values, takes the version from the highest entry of `supported_versions`, sets the SNI flag from extension 0x0000, counts ciphers and extensions up to 99, takes the first and last character of the first ALPN value (hex when either is not alphanumeric), hashes the sorted cipher suites, and hashes the sorted extensions without SNI and ALPN followed by the signature algorithms in wire order, each truncated to 12 hexadecimal characters of SHA-256. The unit test reproduces the worked example of the specification, `t13d1516h2_8daaf6152771_e5627efa2ab1`, from a ClientHello with GREASE values. The runner reads the ClientHello bytes of each session from tshark, which gives the TCP payload and the reassembled segment data of the frame, parses them itself, and compares its JA4 with the `tls.handshake.ja4` field of tshark 4.2. A disagreement fails the session, because one of the two misreads the hello.

**Verdict.** The check passes when at least `min_decrypted` of the sample decrypts and every sampled ClientHello has a JA4 that its profile lists. A mismatch fails with a reason such as `JA4 t13d1517h2_... is not the JA4 of profile chrome (...): part a (version, SNI flag, cipher and extension counts, ALPN) is t13d1517h2, expected t13d1516h2; cipher suite hash is ..., expected ...`. The check also fails when no session carries a `tls_profile`, and when tshark is missing, so a skipped tool never passes. The entry carries `realism.decrypted_ratio` and `realism.ja4_match_ratio` (not rounded) when at least one session was sampled.

**Tests.** [`realism/tests/tlsgen.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/tests/tlsgen.py) runs a TLS client and server of the Python `ssl` module against each other in memory, writes the flights as TCP segments, and keeps the client secrets as a key log, so no network, root, or dumpcap is needed. The tests cover a matching and a mismatched profile for TLS 1.2 and 1.3, embedded and sidecar keys, a capture without keys, wrong keys, a client without ALPN, and TLS on port 8443. The expected JA4 of the matching fixtures comes from tshark, because the ClientHello of the Python module depends on the installed OpenSSL. The tests skip without tshark or openssl, and the `rlm` workflow has both.

## Content variety check

Traffic that repeats one body, or that always sends the same size, does not look like the application it imitates. RLM-05 implements the check in [`realism/content.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/content.py). It runs when the labels have a `content` section or the command has `--max-duplicate-ratio`, so a labels file without either behaves as before.

**Units.** The runner reassembles each direction of a TCP session itself, from the sequence numbers, the first copy of a byte winning, and it cuts the stream at a hole. It does not use the `capture/` extractor of CAP-01, as RLM-04 decided for the encryption check, so the realism runner stays independent of it. A unit is one HTTP/1 message when the application is HTTP (the name starts with `http`, or the client stream starts with a method), one UDP datagram, or one whole TCP direction otherwise.

**What counts as the same payload.** The unit is hashed with SHA-256 after normalization. For HTTP the hash covers the start line, the headers in wire order with lower case names, and the body without chunked framing, and it leaves out the headers that change per message without changing the content, which are `Date`, `Expires`, `Last-Modified`, `Age`, `ETag`, the conditional headers, cookies, and trace identifiers. We keep the start line and the other headers in the hash because a message with an empty body, such as a GET, would otherwise have the same hash in every session. DNS ignores the transaction identifier. We chose these rules to flag a generator that replays one message, and not a client that asks twice for the same resource, which is why a labels file can drop more headers with `ignore_headers`.

**Duplicate ratio.** For each application and direction, `(units - distinct hashes) / units`. The check fails when the ratio of any application is above `max_duplicate_ratio` (default 0.01, set in the labels or with `--max-duplicate-ratio`). We test each application and not the capture as a whole, so a varied application cannot hide a repeated one. The failure names the most repeated payload, its size and copies, and the sessions that carry it.

**Sizes.** The entry reports count, minimum, maximum, mean, standard deviation, coefficient of variation, and the quantiles p5 to p99 of the unit sizes, per application and direction. A `sizes` entry in the labels gives the expected median and, optionally, the expected coefficient of variation with a relative tolerance (default 25%), and the check fails when the observed values are outside it. Fixed size traffic therefore fails an expected `cv`, and without an expectation the dispersion is only reported.

**Encrypted sessions.** The runner skips sessions with a `tls_profile` and sessions whose stream starts with a TLS record, and it counts them in `skipped_encrypted_sessions`. The encryption check of RLM-04 reads only the Finished messages from tshark and does not expose plaintext, so there is nothing to reuse. The check also fails when no payload could be analysed, so a capture of only TLS sessions never passes. [`realism/tests/test_content.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/tests/test_content.py) builds repeated and varied captures, segmented and reordered TCP streams, and encrypted sessions in code, and the entry carries `realism.duplicate_ratio` for each application with payloads.

## Session structure check

A scenario instance opens several connections. The `web_browse` scenario of the [specification](https://github.com/alrawi/FixingPointSystem/blob/main/docs/spec/specification.md) resolves a name and then fetches the page, because its page flow runs `after` the lookup flow, and an FTP session opens one control connection and one data connection per transfer, because the control flow spawns each data flow. A generator that drops a connection, repeats one, or runs them in the wrong order makes traffic that no real client makes. RLM-08 implements the check in [`realism/structure.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/structure.py) and [`realism/scenario_graph.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/scenario_graph.py). It runs when the labels have a `structure` section that lists scenario files, or when the command has `--scenario FILE`, so a labels file without either behaves as before.

**What web_browse means here.** The name belongs to two files. The scenario of the specification has two flows, `lookup` (DNS over UDP) and `page` (HTTP, `after: lookup`), and the ENG-07 test of `engine/fps-interp/tests/instances.rs` runs it. The example [`contracts/examples/modules/http1/scenarios/web_browse.yaml`](https://github.com/alrawi/FixingPointSystem/blob/main/contracts/examples/modules/http1/scenarios/web_browse.yaml) has one flow, `browse`, with two requests on one keepalive connection, so it has no ordering to check. The acceptance of RLM-08 needs the first one, and the repository kept it only as a string in a test. [`realism/examples/web_browse.scenario.yaml`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/examples/web_browse.scenario.yaml) is a copy of it for the realism tests, and [`web_browse.labels.yaml`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/examples/web_browse.labels.yaml) shows the labels that turn the check on. The fixtures are generated in `realism/tests/test_structure.py` with pcapgen, because no captured web_browse run exists.

**Graph.** The reader takes each flow as one connection with its transport (`l4`) and its server port, when the `accept` or `connect` action gives a literal or a `{{ vars.name }}` reference. It takes the `after` lists and the `spawn` actions as edges. A `spawn` inside a `loop` repeats `count` times, inside a `branch` it may not happen, and a count that the file does not fix allows any number. The client and the server program of a parent both run `spawn` for one child, and the child counts once.

**Reconstruction.** The runner groups the sessions that match a flow by client address, walks them in order of their first packet, and puts each in the open instance of its client while that instance still has room for the flow. Otherwise it opens a new instance, and a client that was silent for longer than `structure.max_gap_s` also opens one. We chose this slot filling over opening an instance at each root flow, because a page fetch before its lookup must join the instance of that lookup so that the failure names the broken edge and not two incomplete instances. The limits are these. A client address that runs two instances at once cannot be split, clients behind one address look like one, a missing connection shifts the later connections of that client into other instances (the failure says that an instance opened because the one before had no room), flows without a fixed port, such as FTP data connections, are interchangeable and take the connections in spawn order, and two scenarios that share a transport, a port, and a client address cannot be told apart in one capture, so the labels give each its own `match` or the run records one scenario per capture.

**Rules.** Per instance and flow, the number of connections must lie within what the graph allows. Per `after` edge, every connection of the later flow must start no earlier than every connection of the earlier flow completed, where a session completes at its last packet with payload, FIN, or RST. We leave out the closing ACK, because the engine starts the next flow when the close action returns. Per `spawn` edge, every connection of the child must start between the first and the last packet of a connection of its parent. `structure.tolerance_s` (default 0) loosens both. The check also fails when a scenario matches no session and when `expected_instances` disagrees. A failure names the scenario, the instance with its client address and first packet, and the violated edge with both sessions, for example `edge after lookup -> page violated: page (session 1, tcp 10.0.0.10:40001 -> 10.0.1.80:8080) starts at +0.000000 s, before lookup (session 2, udp 10.0.0.10:40000 -> 10.0.1.53:53) completes at +0.030999 s`. The entry carries `realism.structure_failures` for each scenario, the number of rules that its instances break.

**The ftp fixture check.** [`modules/ftp/fixtures/structure_check.py`](https://github.com/alrawi/FixingPointSystem/blob/main/modules/ftp/fixtures/structure_check.py) cannot be replaced yet. This check covers its count of one data connection per transfer and its rule that a data connection starts while the control connection is open, and the tests run it on the `mixed_session` scenario. It does not read the 227 and 229 replies, so it cannot check that a data connection goes to the announced port. It does not require that each session ends with a FIN of both sides, and it does not reject active mode commands. The committed `ftp.pcapng` records five scenarios on one address and one control port, so no one scenario file describes it. A replacement needs the fixture script to record one scenario per capture, or a `match` that separates them, and the port and FIN rules would stay in a script or move into a later check.

## Temporal distribution check

Real users arrive at random and fetch objects of very different sizes, and a generator that opens sessions on a metronome, or whose object sizes cluster around one value, does not look like that population. The specification asks for configurable arrival processes, think times, and heavy tailed object sizes, tested against the target distribution with the Kolmogorov Smirnov (KS) test. RLM-06 implements the check in [`realism/temporal.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/temporal.py) and the tests in [`realism/ks.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/ks.py). It runs when the labels have a `temporal` section or the command has `--ks-alpha` or `--ks-min-samples`, so a labels file without either behaves as before.

**What it compares.** Three properties, each per application and for all sessions together.

* `inter_arrival` is the gap in seconds between the first packets of consecutive sessions, in order of those first packets. An application takes the sessions that the labels name as that application, and `overall` takes every session of the capture, labelled or not. A Poisson process of `r` sessions per second has exponential gaps with `mean_ms` of `1000 / r`, and the sum of Poisson processes is Poisson with the summed rate, so one labels file can give a target for each application and one for the whole capture.
* `payload_size` is the size in bytes of each payload unit of the [content check](#content-variety-check), which is one HTTP/1 message with its headers, one UDP datagram, or one whole TCP direction, for the `client` direction, the `server` direction, or `both`. TLS sessions are skipped and counted, as in the content check, because the runner has no plaintext for them.
* `packet_gap` is the gap in seconds between consecutive packets with payload inside one session, which RLM-15 added. Each direction of a session is a stream and a gap never spans two directions, so the two directions of an RTP call that run in lock step give two streams with their own pacing. A packet without payload, such as a TCP acknowledgment, does not count. Arrival times of sessions cannot see this pacing, so before RLM-15 only module scripts measured it. Since MOD-24 the sip_rtp module states its pacing as a `temporal.packets` label. A stream that mixes playlist and segment requests has no single packet gap, so RLM-22 added the `path` of a target, `min_samples` per target, and the `rungs` bytes (see below), and since MOD-31 the hls module states its segment cadence and bytes as labels.

**Targets.** The labels write a target with the vocabulary of a scenario `delay` in [`contracts/schemas/scenario.schema.json`](https://github.com/alrawi/FixingPointSystem/blob/main/contracts/schemas/scenario.schema.json), so a delay that a scenario uses can be pasted as the target of the arrivals it should produce.

| `dist` | Arrival parameters | Size parameters |
|---|---|---|
| `constant` (or `ms` alone) | `ms`, `tolerance_ms` | `value`, `tolerance` |
| `exponential` | `mean_ms` | `mean` |
| `uniform` | `min_ms`, `max_ms` | `min`, `max` |
| `lognormal` | `mu`, `sigma`, `unit` (`s` or `ms`) | `mu`, `sigma` |
| `pareto` | `alpha`, `scale_ms` | `alpha`, `scale` |
| `empirical` | `sample`, `sample_file`, or `reference` | the same, in bytes |

`mu` is the natural logarithm of the value in the `unit`, and a size `mu` is the logarithm of the size in bytes. A Pareto distribution has the density of the scenario schema, with `scale` as its smallest value. An `empirical` target is a list of values in seconds or bytes, a file of numbers separated by white space or commas, or a reference capture (`reference: {pcap: ..., labels: ...}`, both relative to the labels file) whose own sessions give the sample. The test is then the two sample KS test. The test configuration has no arrival process or size distribution of its own. It holds a load objective and phases, and the scenario schema holds `delay` for think times, so the target distributions are an input of the labels and the check does not read them from the test configuration.

```yaml
temporal:
  alpha: 0.01          # default
  min_samples: 30      # default
  arrivals:
    overall: {dist: exponential, mean_ms: 142.9}
    applications:
      http1: {dist: exponential, mean_ms: 200}
      dns: {dist: uniform, min_ms: 100, max_ms: 900}
  sizes:
    applications:
      http1:
        - {direction: client, dist: lognormal, mu: 5.5, sigma: 0.4}
        - {direction: server, dist: pareto, alpha: 1.8, scale: 500}
  packets:             # gaps between the packets of one direction of a session
    applications:
      rtp: {dist: constant, ms: [20, 30], tolerance_ms: 5, within: 0.9}
      hls_vod:                                                  # the segment requests of a keepalive connection
        {direction: client, path: '/v\d+/seg\d+\.ts$', dist: constant, ms: 400, tolerance_ms: 40, mean_tolerance_ms: 20, min_samples: 3}
  rungs:               # bytes per rung of an adaptive bit rate playback
    applications:
      hls_vod: {path: '/v(\d+)/seg\d+\.ts$', duration_ms: 400, bits_per_second: [160000, 320000, 640000], walk: up, streams: 3, min_samples: 4}
```

**Decision.** A comparison passes when the p value of the KS test is at least α (`--ks-alpha`, `temporal.alpha`, default 0.01, and the option wins). The statistic, the p value, the sample size, and the method go into the report beside a failure reason in words, for example `inter-arrival times of application http1: the KS test rejects exponential (mean 0.2) at alpha 0.01 (statistic 0.2133, p value 0.0012, n 200); the observed median is 0.2412 s, the target median is 0.138629 s`. The p value is exact for up to 100 one sample observations and for two samples with up to 10000 pairs, and it is the asymptotic Kolmogorov distribution with the correction of Stephens above that. We wrote the test in pure Python, as the runner needs only the standard library, and we checked it against the table of critical values and against `scipy.stats` values that the tests state. The specification names α = 0.05 for the gate and the check defaults to 0.01, so the gate suite passes `--ks-alpha 0.05` or sets `temporal.alpha`.

**Paced media.** The constant of a `packet_gap` target is the packet time of paced media, so it is not the exact test of the other constants. A real sender wakes up a few milliseconds late, and a loaded host sends a burst after a stall: the committed sip_rtp fixture, recorded in the namespace harness, has gaps from 0.09 ms to 63.7 ms in a stream of 20 ms packets. The constant therefore takes `ms` as one packet time or a list (the fixture has calls of 20 ms and 30 ms in one application), a required `tolerance_ms`, and `within`, the share of the gaps that must be on time (default 0.9, the share that the removed `rtp_check.py` of the sip_rtp module used). The check judges every stream with at least `min_samples` gaps on its own against the listed time that is nearest to its median gap, so a call with jittered packets fails even among many good calls, and the reason names the worst stream. Streams with fewer gaps are only counted (`streams.too_short`), and a capture without any long stream reports `insufficient_data`. Every other distribution of `packets` runs the usual KS test on the gaps of all streams together. The gaps of one stream are not independent, so such a p value is a rough measure.

**Requests of one kind and bytes per rung.** RLM-22 gave the labels what `modules/hls/fixtures/hls_check.py` of MOD-15 did by hand, which MOD-24 could not move into them. MOD-31 moved the checks into the `expected.yaml` of the hls module and deleted `hls_check.py` and `hls.playbacks.json`; the evidence for the committed capture is now `modules/hls/fixtures/test_temporal_labels.py`. A keepalive connection of HLS alternates playlist and segment requests, so a third to a half of its client gaps are under a millisecond, a playback has 8 to 16 gaps against the 30 that a stream needs, and the labels read no bytes. Three additions close the gap, and the module author writes them in `expected.yaml`.

* A `packets` target of the client direction takes `path`, a regular expression on the request target. The stream of a session then holds only the matching requests, and a gap is the time between two of them. `join_ms` joins the matching requests of all sessions of the application into one stream while the gap to the next stays below it, for a playback whose segments each use a connection. A path target belongs under `applications`, and two targets of one application and direction differ by their path. The reader of the sessions is [`realism/exchanges.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/exchanges.py), which follows HTTP/1.1 `GET` requests with a `Content-Length` response and fails a target for a session that it cannot follow.
* Every target takes `min_samples`, which replaces the value of the section and of the command line for this target, and a paced constant takes `mean_tolerance_ms`, the distance of the mean gap of each stream from its packet time. The pair gives `hls_check.py` its minimum of four segments (3 gaps), its 10% jitter (`tolerance_ms: 40` with `within: 0.9`), and its 5% mean (`mean_tolerance_ms: 20`).
* The `rungs` section gives each application the request path of a segment (its first group is the rung), `duration_ms` of media per response, and `bits_per_second` per rung. A stream with at least `min_samples` requests needs every body within `body_tolerance_bytes` (188) of `rate * duration / 8`, the share of each rung in the bytes of the stream (response head and body) within `share_tolerance` (0.05, relative) of the share that the rates give, the bit rate of the stream within `rate_tolerance` (0.05) of the mean rate of its rungs, and with `walk: up` rungs that rise through the whole ladder. `streams` is the number of judged streams that the capture must hold. The code is [`realism/rungs.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/rungs.py).

The report format rose to 0.20.0. The comparisons of the temporal entry gained `path` and `min_samples`, and the entry gained `rungs`, one item per application with the judged streams (requests, bit rate, configured bit rate, rung shares, failures), the counts of judged, failed, and too short streams, and a reason in words. The fields are optional, so a report of 0.19.0 stays valid, and the controller copy of the schema and `ui/src/api/schema.d.ts` carry them. The metric catalog has no series for the bytes, and a comparison with a path adds none, because two paths of one application would give two series with the same labels, so both show only in `realism.check_failures` and in `failures`.

**Too little data.** A comparison with fewer than `min_samples` observations (`--ks-min-samples`, `temporal.min_samples`, default 30) in the capture, or in its reference sample, reports `insufficient_data` with the counts, and it fails the check, because a pass on a handful of points proves nothing. The same holds for an application that has no session. The check also fails when the labels name no target, so asking for it with no target never passes.

**Constants.** A constant has no spread, so the check is exact. The observations must all lie within `tolerance` of the value, the statistic is the larger share of observations below or above that band, and the p value is 1 or 0. Capture timestamps have the resolution of the file, so a constant gap needs a tolerance of at least that resolution.

**Limits.** Each comparison is a test at level α, so a report with many targets rejects about α of them by chance even when the traffic is right. Byte sizes are discrete, which makes the KS test against a continuous target conservative, and ties make the exact p values approximate. The gaps come from the first packet of a session in the capture, so a mirror that drops or reorders frames changes them. The check does not yet compare the think times between the actions of one session, which would need the timing of the actions inside a session.

**Metrics.** The entry reports `realism.ks_statistic` and `realism.ks_p_value` for each application whose property the [metric catalog](https://github.com/alrawi/FixingPointSystem/blob/main/contracts/metrics/catalog.yaml) names, `inter_arrival` for arrivals, `request_bytes` for client payloads, `response_bytes` for server payloads, and since CON-28 (catalog 0.8.0, report format 0.17.0) `request_gap` for the gaps of the client streams, `response_gap` for those of the server streams, and `packet_gap` for both directions. The comparisons over all sessions and the payload sizes of both directions have no series, so they stay in `comparisons` only. A paced comparison of packet gaps (the `constant` target) has no series either, because its statistic is the share of gaps outside the tolerance and its p value is 0 or 1, which are not a KS statistic and a p value, so only the `realism.check_failures` series reports it. The same holds for a comparison with a `path` and for the `rungs` (RLM-22).

**Evidence.** [`realism/tests/test_ks.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/tests/test_ks.py) holds the known values of the KS tests and checks that exponential samples reject at the rate of α and shifted ones nearly always. [`realism/tests/test_temporal.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/tests/test_temporal.py) builds pcapgen captures whose arrivals and sizes come from seeded Poisson, uniform, lognormal, and Pareto generators. Captures from the target pass, and captures with a 75% longer mean gap, a metronome, a shifted lognormal size, or a wrong constant fail with their reason. [`realism/tests/test_packet_gaps.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/tests/test_packet_gaps.py) checks the packet gaps: streams of 20 ms and 30 ms pass, a call with jittered packets, a burst after a stall, and a call with the wrong packet time fail with a named reason, and the committed sip_rtp fixture passes with `ms: [20, 30]` and fails with either time alone. [`realism/tests/test_http_rungs.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/tests/test_http_rungs.py) proves the labels against the committed hls capture without touching `modules/hls/`. The capture passes with the labels above, and the bit rate and rung shares of its 7 playbacks equal the numbers that `hls_check.py` recorded before MOD-31 deleted it, which the test keeps. The same capture with its time stretched by 1.15 or 0.8 fails for all three kinds of playback, a stretch of 1.06 (every gap inside 40 ms, the mean 24 ms off) fails only with `mean_tolerance_ms`, and a ladder that differs from the bytes fails. Synthetic keepalive playbacks fail for a body that is 20% short, a padded response head that moves the share, a bit rate that is 5% off on the wire, rungs out of order or with a rung skipped, a rung outside the ladder, a stream with too few requests, a count of streams that is wrong, and a session that is not HTTP/1.1.

## Mix accuracy check

A test sets its traffic mix as weights per scenario, by sessions or by bytes (`profile.basis`), and the controller steers the run towards them (CTL-12, CTL-34). RLM-07 checks the result in [`realism/mix.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/mix.py) with two measurements that do not share a fault. The run metrics (`sessions.attempted`, `bytes.tx`, and `bytes.rx` per scenario) show what the engine believes it sent, and nDPI on the capture shows what is on the wire. A scheduler that sends the wrong mix fails both, an application that nDPI does not recognise fails only the second, and a counter bug of the engine fails only the first. The check runs when the labels have a `mix` section or the command has `--test-config`, `--run-report`, `--mix-tolerance`, or `--mix-basis`. The [runner README](https://github.com/alrawi/FixingPointSystem/blob/main/realism/README.md#mix-accuracy) gives the formats.

**Where the counts come from.** The `RunReport` of `GET /v1/runs/{id}/report` holds the run, its summary, and its verdict, and no counts per scenario, so the check reads the metric series of `GET /v1/runs/{id}/metrics?view=scenario`, which the controller keys `<application>/<scenario>`, as a file or as a `metrics` member of a bundle with the report. It takes the last (cumulative) sample of each key and, for bytes, the sum of `bytes.tx` and `bytes.rx` of the client side, which counts each payload byte once. A plain table of sessions and bytes per scenario is accepted as well, for a later report that carries one.

**Mapping.** Mix entries are scenarios and nDPI names protocols, so the labels map each scenario to an application explicitly (`mix.scenarios`). The application gives its nDPI names in the way the conformance check does (`applications.<name>.ndpi`, with built in names for `http1` and `dns`), and an entry may list its own. Scenarios that share an application form one row, because nDPI cannot tell them apart, and two applications that accept one nDPI name are refused at the start. A scenario of the mix without a mapping stops the run with exit code 2 and not with a pass.

**Rules.** The configured share of an application is its weight over the sum of all weights. The achieved share from the metrics is its count over all scenarios of the run report, and from nDPI its count over all labelled sessions of the capture (or all sessions when the labels have no rules). We divide by all sessions and not by the recognised ones, because nDPI naming a few sessions of an application as `Unknown` would otherwise pass unnoticed. Those sessions form an `(unmatched)` row with a configured share of 0. Bytes are the application payload bytes of both directions, as the catalog defines `bytes.tx` and `bytes.rx`, and the runner counts the same payload bytes in the capture. A share passes when it lies within the tolerance of the configured share (default 2 points, inclusive), compared exactly as fractions, so no rounding decides a difference of exactly 2.0 points. A scenario in the run report that the mix does not list fails, and so does a run that counted nothing.

**Basis.** The check uses `profile.basis` of the test configuration by default, `mix.basis` of the labels or `--mix-basis` replaces it, and `both` runs the two bases and fails when either fails. Running both on a test whose basis is `bytes` shows what the sessions look like, which is only informative, because the weights are byte shares.

**Run report forms.** The run report file is a metric series of the scenario view, a bundle with it, a table `{"scenarios": [{"scenario": "http1/web_get", "sessions", "bytes"}]}` (the file form of CTL-38), or the `RunReport` of the REST API, whose `scenarios` list (CON-21) has the application and the scenario apart. RLM-13 reads the last form: sessions are `sessions_attempted` and bytes are `bytes_tx` plus `bytes_rx`.

**Metric series.** RLM-13 fills the `metrics` of the entry with the catalog gauges `mix.share_pct`, `mix.abs_error_pp`, and `mix.max_abs_error_pp` (catalog 0.4.0) for what the classifier saw, with `source` `classifier` and the classifier label, so a reader never mistakes them for the run's own counters, which carry `source` `metrics` or no `source`. The catalog gives them no label for the basis, so one report carries the basis that `metrics_basis` names (the test configuration's `profile.basis`, or the only basis that ran), and none when the labels list the weights and both bases ran. How the controller receives the report is the business of the upload package (CON-22), and the series are in the report whatever it does.

**Evidence.** [`realism/tests/test_mix.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/tests/test_mix.py) builds captures with known session and byte shares and synthetic run reports. A run report that is 3 points off for one application fails and names the application, the source, and the delta, shares within 2 points pass (2.00 points exactly passes), the tolerance and the basis are configurable, and the command line test runs a fake ndpiReader through the real command. An optional test runs the real ndpiReader on a synthetic capture.

**Limits.** A scenario that opens several connections per session, such as `web_browse` with its lookup and page fetch, has more sessions in a capture than in the metrics, so use the bytes basis for it or give the helper connections their own application. The capture must hold the whole run: a packet limit or a port filter that leaves out an application makes it fail for that application.

## Transport behavior check

A real host shows its operating system in the first packets of every TCP connection, in the IP TTL, the do not fragment flag, and the options of the SYN. RLM-09 checks in [`realism/transport.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/transport.py) that the SYN and the SYN-ACK of every connection agree with the operating system profile (`windows11`, `linux6`, or `macos14`, [TRN-03](Transport.md#operating-system-profiles)) of the host that sent them. The runner reads TCP headers itself, so the check needs no tool, and it reads the profile files of the kernel backend, so the check and the backend share one source of truth: `socket.ttl` and `socket.mss` are what the kernel sets, and `reference` is the SYN of the real system.

**Fields.** The TTL (exact, less the routers between the host and the capture point, which the labels give as `client_hops` and `server_hops`), the do not fragment flag, the MSS, the window scale, SACK permitted, and timestamps. A server answers only the options that the client offered, so a SYN-ACK is compared in those options with the SYN of its connection and carries none that the SYN lacked. The labels name one profile for every host or one per IP address, and `expect` replaces a value of the profile for a capture whose stack differs from it in a known way.

**Strict mode.** The Linux kernel decides the option order and rounds the SYN window to whole segments, so the kernel backend cannot reproduce the option order of windows11 and macos14 or the SYN window of macos14 (see the [limits](Transport.md#limits)). The report lists both as deviations that do not fail the check, and `strict` makes them fail, which suits captures of real systems.

**Evidence.** [`realism/tests/test_transport.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/tests/test_transport.py) builds one capture per profile from option bytes that the test writes out (the public SYN signatures, not the profile files), and each passes. A SYN with the TTL of Linux (64) against windows11 fails with `the profile expects 128, the capture shows 64 in 5 of them`, and a TTL that is one too high or too low, a wrong MSS, window scale, timestamp, SACK, or do not fragment setting, a server answer with an option that the client did not offer, and a malformed option list fail as well. The committed fixtures of the kernel backend (`modules/*/fixtures/*.pcapng`) agree with the `linux6` profile in every field but the window scale, which is 10 in the harness namespaces and 7 in the profile, and they fail the `windows11` profile in TTL, window scale, and timestamps. The report format is 0.9.0.

## Message count check

nDPI names a session from its first packets, so a session can classify as HTTP, SMTP, or IMAP and still lack its response, its message, or its fetch. The decrypted view made that visible, and MOD-22 removed the module scripts that counted it. RLM-14 implements the check in [`realism/messages.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/messages.py). It runs when the labels have a `messages` section, and the [runner README](https://github.com/alrawi/FixingPointSystem/blob/main/realism/README.md#message-counts) shows the format.

**Rules and counts.** A rule names a protocol (`http1`, `http2`, `smtp`, or `imap`), selects TCP sessions with the match fields of a session rule, and lists what each of them must show: `requests` and `responses` for HTTP, and `messages`, `commands` by name, and `replies` by SMTP code or IMAP status for SMTP and IMAP. A count is a number or a range. We chose per session counts and not totals, because a total of 200 requests hides one session that lost its response and another that sent two. The fixtures have a few session shapes each (the http1 scenarios send one or four requests, selected by their server port), so each shape has its own rule.

**Reading the view.** The runner starts tshark once for each protocol of the section, with `-d tcp.port==P,PROTOCOL` for the server ports of the selected sessions, and counts the occurrences of one field per kind of message: `http.request.method` and `http.response.code`, `http2.headers.method` and `http2.headers.status`, `smtp.req.command` and `smtp.response.code`, `imap.request.command` and `imap.response.status`, and `imf.from` for a message. We take `imf.from` and not the message identifier, because RFC 5322 requires the `From` header and only recommends `Message-ID`. tshark reads an IMAP `BODY[]` literal as an RFC 5322 message, which replaces the literal and header test of the old script, and it reads the HEADERS frames of HTTP/2 through its HPACK tables, so the http2 count needs no second pass. The tool sits behind the `MessageProbe` protocol with a stub, like the other tools.

**Verdict.** The check fails for each session outside its range, with a reason such as `missing smtp message: found 0, expected 1` or `surplus http1 request: found 5, expected 4`, for a rule that matches no TCP session, and when tshark is missing. `python3 -m realism decrypted` runs it on the view and prints the first five reasons under `messages:`. The entry carries the series `realism.check_failures` with `check` `messages` and the value `failures_total` (see [Metric series](#metric-series-of-each-check)).

**Fixtures.** The example labels of `realism/examples/decrypted/` carry the counts that the committed fixtures pass: http1 80 sessions with 200 requests and 200 responses (one request on the ports 8443 and 8445, four on 8444 and 8446), http2 40 sessions with 180 of each (seven on port 8443, two on 8444), smtp 8 sessions that each show the two EHLO, the authentication, two recipients, six replies 250 and one message, and imap 8 sessions that each show seven commands completed with OK and two messages, which are the 16 literals of the old script. `realism/tests/test_messages.py` checks the labels with tshark alone, so it runs where nDPI 4.14 is missing, and it also cuts one session of each fixture in half and requires the failure and its reason. The Zeek check of the imap view and the SMTP message check of Zeek stay with the modules.

## Host identity check

The specification asks for a configured host count reached with zero address conflicts. RLM-10 implements the check in [`realism/hosts.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/hosts.py). It runs when the labels have a `hosts` section, or with `--host-identity` or `--host-count N`, and the [runner README](https://github.com/alrawi/FixingPointSystem/blob/main/realism/README.md#host-identity) shows the format.

**Hosts and conflicts.** A host is an IP address per VLAN that is the source or destination of an IP packet or the sender of an ARP packet, without multicast, broadcast, reserved, and unspecified addresses. A conflict is an IP address that sends from two or more Ethernet source addresses in one VLAN. We key hosts by VLAN and address, because two VLANs may reuse an address, and we bind addresses to MACs only through the sender of a frame, because the destination MAC of a packet to a remote host is the router. One MAC with many IP addresses is no conflict, and the labels list router MACs under `gateway_macs` for a capture that sees both sides of a router. ARP senders count, because a duplicate address shows there first, but the probe sender 0.0.0.0 does not.

**Verdict.** The check fails for each conflict, for a host count outside the range, for a capture without IP hosts, and for a capture without any Ethernet source address, so a raw IP capture never passes as free of conflicts. The entry carries only `realism.check_failures` with `check: host_identity` (catalog 0.7.0, CON-27), whose value is `failures_total`.

## Pinned nDPI and the decrypted view

RLM-12 gave the realism CI a current nDPI and replaced the copies of `decrypted_check.py` with one command.

**nDPI 4.14.** Ubuntu 24.04 ships nDPI 4.2.0, which has no HTTP/2 protocol, so the http2 module could not conform. The file [`realism/ci/ndpi.version`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/ci/ndpi.version) holds the release and the commit of its tag, and [`realism/ci/build-ndpi.sh`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/ci/build-ndpi.sh) fetches that commit, checks the id, builds `ndpiReader`, and links it ahead of the Ubuntu package. We pin a commit and not a tarball because a GitHub archive of a tag is not byte stable and a commit id is content addressed. `install-tools.sh` runs the script, so both workflows share one nDPI. We build in the script and not in a workflow cache step, because the workflows are outside the RLM paths. The script is idempotent for a runner that restores `/opt/ndpi`. Two things of nDPI 4.14 differ from 4.2 and the classifier handles both: the flow CSV separates fields with `|` instead of commas, and `ndpiReader -h` exits with 1.

**Evidence for HTTP/2.** `realism/tests/test_ndpi_http2.py` runs the real reader on ten synthetic h2c sessions and on the cleartext sessions (ports 8081 and 8082) of `modules/http2/fixtures/http2.pcapng`. The test needs 99% of them as `HTTP2`. On the machine of the work package the 4.14 reader named 40 of 40 fixture sessions `HTTP2`, and the test prints the same line in the CI log.

**`python3 -m realism decrypted`.** The command decrypts the TLS sessions of a capture with tshark, writes their plaintext as plain TCP sessions with the same addresses, and scores that view with a labels file, so nDPI and the parsers read what a decrypting proxy would show. It replaces the scripts of http1, smtp, imap, and http2, which differed only in the protocol and in whether the plain start of a STARTTLS session joins the view (`--plaintext upgrade`) or stays out (`inside`). What the scripts also counted per protocol (requests, SMTP commands, IMAP literals) first dropped out, and RLM-14 brought it back as the [message count check](#message-count-check). The SMTP message check of Zeek (`zeek_check.py`) and the Zeek `conn.log` check of the imap view stay with the modules, and the command scores the Zeek and tshark parser errors of the view. The [runner README](https://github.com/alrawi/FixingPointSystem/blob/main/realism/README.md#decrypted-view) gives the options, and `realism/examples/decrypted/` the labels of the four fixtures. Run on the fixtures with nDPI 4.14.0 and tshark 4.2.2, the command decrypted 80 of 80 (http1), 8 of 8 (smtp), 8 of 8 (imap), and 40 of 40 (http2) TLS sessions, and nDPI named every view session `HTTP`, `SMTP`, `IMAP`, and `HTTP2`.

**TLS ports of the decrypted check (RLM-18).** MOD-23 traced a failed http2 module job (39 of 40 TLS sessions) to the way the check listed ClientHellos. It ran plain `tshark -Y "tls.handshake.type == 1"`, and tshark takes TCP port 8443 for TLS only by its heuristic, which needs a record header in the first segment of the client. A ClientHello cut after 1 to 4 octets was missed, while the encryption check, which passes `-d tcp.port==P,tls`, counted it. `read_sessions` now takes `tls_ports` and `Tshark.run` passes the Decode As option for each of them (443 excepted) on every run, and `run` takes the ports from the TCP `server_port` of the session rules of the labels. With `--view-port` the labels name the port of the view, so none is added, which leaves the smtp and imap captures (STARTTLS, view ports 587 and 143) on the heuristic as before. `realism/tests/test_decrypted.py` cuts the ClientHello of three sessions on port 8443 after 1 and after 4 octets: the old call lists none, and the new one lists all three and the command passes with `--sessions 3`. MOD-24 removed the wrapper `modules/http2/fixtures/tshark-tls-ports.sh`, so the http2 module reads its capture with plain tshark.

**STARTTLS ports of the decrypted check (RLM-21).** RLM-18 left the smtp (capture port 5587, view port 587) and imap (1143, view 143) jobs on the heuristic, because their labels name the port of the view. Decoding a STARTTLS port as TLS is also wrong, since the session starts in clear text. tshark upgrades such a session itself when the port decodes as the application protocol, so `--starttls-port PORT:PROTOCOL` (`smtp`, `imap`, or `pop`) names the capture port and each tshark run passes `-d tcp.port==P,PROTOCOL` (`read_sessions` and `run` take `starttls_ports`). A real tshark 4.2 run on three STARTTLS sessions with a ClientHello cut after 1 and after 4 octets listed 0 to 2 of 3 sessions, as plain TLS and as TLS from the first byte, and all three as the protocol. The smtp and imap module workflows pass `--starttls-port 5587:smtp` and `--starttls-port 1143:imap`. The report format stays 0.17.0.

## Module realism job

RLM-03 added the `realism` workflow in [`.github/workflows/realism.yml`](https://github.com/alrawi/FixingPointSystem/blob/main/.github/workflows/realism.yml), which scores fresh traffic of every native module that a pull request touches. It runs three jobs.

| Job | What it does |
|---|---|
| `detect` | Lists the changed paths of the pull request and runs `python3 -m realism modules`, which prints a matrix of the selected modules |
| `module` | Records a fresh capture of each selected module in the QA-01 namespace harness, scores it with nDPI, tshark, and Zeek, and uploads the capture and the report as the artifact `realism-<module>` |
| `negative-control` | Breaks the http1 request line in its own checkout and requires the same run to exit with 1 |

A native module takes part when its directory under `modules/` holds `native/Cargo.toml`, `fixtures/capture.sh`, and `fixtures/expected.yaml`. Today these are `dns` and `http1`. The capture script must accept an output directory, write `<module>.pcapng` there, and take a prebuilt peer from `FPS_FIXTURE_PEER`, as the scripts of MOD-01 and MOD-02 do. A changed path under `modules/<name>/` selects that module. A changed path under `realism/`, `engine/`, or `tests/harness/`, or a change to the root Cargo files, `mk/rlm.mk`, or the workflow, selects every module, because it can change the traffic or the score of each of them. A push to `main` also selects every module.

[`realism/ci/module-realism.sh`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/ci/module-realism.sh) runs one module. It calls the capture script of the module and then scores the capture with `--parsers tshark,zeek`, so a missing parser stops the run with exit code 2 instead of passing. It writes `<module>.realism.json` next to the capture and adds one row per check to the job summary. It exits with 1 when the conformance check or the parser error check fails. We run every module locally as root with `make e2e-rlm-modules`.

The negative control shows that the job can fail. [`realism/ci/negative_control.py`](https://github.com/alrawi/FixingPointSystem/blob/main/realism/ci/negative_control.py) removes the space after the method, so every request starts with a line such as `GET/a HTTP/1.1`. In the first run of the job, nDPI classified none of the 120 sessions as HTTP, so the conformance ratio dropped to 0, and Zeek 9.0.1 reported one parser error in each of the 120 sessions. The same run of the unchanged modules passed both checks with tshark 4.2.2 and Zeek 9.0.1. The script exits with 2 when the renderer no longer contains the lines it edits, so a change to `modules/http1/native/src/message.rs` that moves them fails the control instead of hiding it.
